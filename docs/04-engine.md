# Движок: что переиспользовать и что в нём сломано

В `engine/` лежат рабочие скрипты. Ими собраны оба отчёта в `examples/`. Логику не дублировать, скрипты вызывать как есть.

## audit.py

Чек-лист, фиксация нарушений, расчёт оценки. Состояние проверки — файл `inspection.json` в рабочей папке.

| Команда | Что делает |
|---|---|
| `index` | Поиск пунктов по словам |
| `detail` | Критерии по пунктам: при каких условиях D1, D2, D3 |
| `zones` | Список зон |
| `init` | Создать проверку: пиццерия, город, аудитор, вид, дата, язык |
| `add` | Добавить нарушение: пункт, класс, зона, формулировка |
| `photo` | Прикрепить фотографию к записи |
| `drop` | Удалить запись |
| `info` | Записать текст в блок `info` — **не использовать**, см. дефекты |
| `list` | Показать записи |
| `score` | Посчитать оценку |

Ключевая строка расчёта:

```python
cost = float(pen.get(lvl, 0))
```

Отсюда работает приём с `D0`: уровня нет в `scoring.json`, значит вычет ноль.

## report.py

Сборка PDF (`pdf`) и текста письма (`letter`).

Кириллический шрифт берётся из системы. В проекте шрифт надо положить рядом и указывать путь явно, иначе на чистом контейнере вместо букв будут квадратики.

## manage.py

Правка чек-листа с валидацией, импорт из xlsx, мягкое удаление. Нужен для будущей админки чек-листов, в MVP не участвует.

## Дефекты, которые надо исправить

**Нет команды `edit`.** Есть `add` и `drop`, но поправить формулировку, класс или зону уже созданной записи нечем. На обеих проверках это решалось ручной правкой `inspection.json`. В боте без `edit` работать невозможно — это первое, что надо дописать.

**Два места для информационных записей.** Блок `info` не виден ни в `list`, ни в `score`. Дубль обнаруживается только в готовом PDF. Либо убрать команду, либо показывать блок наравне с остальным.

**Шаблон письма пустеет на «чистых» проверках.** В тело письма попадают только D2 и D3. Проверка, где все нарушения D1, даёт письмо без содержания — а это как раз частый случай на хороших точках. Обе белградские проверки такие.

## Что уже поправлено в этой копии

Четыре правки против оригинала, все внутри `report.py`:

1. **Приложение с информационными записями.** Добавлен раздел и пояснение, что записи не являются нарушениями и на оценку не влияют.
2. **Разделение находок.** Нарушения (D1/D2/D3) и информационные записи разведены по разным разделам отчёта.
3. **Формат даты и имя файла.** ISO-дата показывается как `21.08.2026`. Имя файла — `Аудит <пиццерия> - <аудитор> - <дд.мм.гггг>.pdf`, одинаково для русского и английского.
4. **Плоское приложение.** Информационные записи перестали группироваться по зонам — они идут подряд по номеру.

## Неочевидное поведение движка

Найдено чтением кода, в комментариях не написано. Всё проверено запуском.

- **`INSPECTION_FILE`** — путь к файлу состояния задаётся переменной окружения, читается при импорте. Для бота с папкой на чат это ровно нужный механизм.
- **`CHECKLIST_DIR` и тихий форк чек-листа.** `manage.py` при любой правке создаёт `checklist_data/` в текущем рабочем каталоге, и дальше `audit.py` из этой папки считает по форку, а из соседней — по оригиналу. Именно так INF09/INF10/INF11 однажды оказались в форке, а не в `data/`, и пакет уехал без них. При папках на чат это даст разную методику в разных чатах — форк надо либо запретить, либо помечать в проверке.
- **`load_zones()` тихо уравнивает доли.** Если сумма `share_pct` не равна 100, все веса перезаписываются на 100/N. Сделать кухню тяжелее зала правкой одного числа не выйдет.
- **`cap_zone_loss_at_share: false`.** Вычеты по зоне могут превысить её долю: 25×D1 в зале дают «потеряно 12.5 из 10%», и колонка «Осталось» в PDF перестаёт сходиться с итогом.
- **Зона вне списка пункта проходит с предупреждением, а не с отказом.** Флаг `zone_unusual` пишется в состояние и больше нигде не читается.
- **Уникальность «пункт + зона» движком не проверяется.** Два одинаковых `add` создадут две записи и вычтут дважды. Проверять обязан бот.
- **Номера записей переиспользуются.** `n` берётся как максимум плюс один, поэтому после `drop` последнего новый `add` получит тот же номер. Аудитор в чате оперирует номерами — нужен сквозной счётчик.
- **`save_state` пишет поверх файла** без временного файла и переименования, без блокировки. Параллельная обработка альбома даст потерянную запись или битый JSON.
- **`init` перезатирает всё состояние** и не валидирует ни `--unit`, ни `--date`. Пустая пиццерия проходит, дата в формате `21.08.2026` ломает расчёт сроков и оставляет в письме пустой прочерк. Отдельной команды правки шапки нет — нужна вместе с `edit`.
- **Пропавшее фото не заметно.** `report.py` проверяет существование файла и при промахе молча вставляет пустоту. Относительные пути резолвятся от рабочего каталога процесса.
- **Три рендерера PDF** — wkhtmltopdf, затем chromium, затем weasyprint. Эталоны собраны первым; у chromium нет нумерации страниц. Вид отчёта зависит от того, что стоит на машине, — рендерер надо зафиксировать.
- **Заголовок нарушения в PDF — утвердительная формулировка пункта.** Партнёр видит «D1 Печь без загрязнений», а ниже «Зафиксировано: нагар». Так устроен чек-лист IMF, но выглядит это странно.
- **`--lang en` даёт смешанный отчёт.** Переводятся рамка, формулировки пунктов, названия зон и процессов. Текст находки, пиццерия, город и аудитор остаются как введены — состояние не умеет хранить две языковые версии.
- **Зависимости нигде не перечислены.** Нужен `requirements.txt`: Pillow для сжатия фотографий, `openpyxl` для импорта чек-листа, хотя бы один из трёх рендереров PDF.

## Что в отчёте обещано, но не выводится

- **Сроки устранения.** Считаются (`due`), в PDF не печатаются, а текст письма ссылается на них: «отчёт со сроками устранения по каждому пункту — во вложении». Либо печатать, либо убрать фразу из письма.
- **Партнёр.** `init --partner` сохраняется, в шапку отчёта не попадает.
- **Письмо при оценке A** безусловно требует план действий и говорит о нарушениях D2 и D3, которых в такой проверке нет. Обе боевые проверки были A, и оба письма пришлось переписывать руками.

Собранный PDF должен совпасть с приложенным.

## Производительность

Меряли, а не прикидывали: сборка PDF с 19 фотографиями — 1,3 секунды. Фиксация одной записи — секунды. Очередь, фоновый воркер и отдельное хранилище в MVP не нужны.

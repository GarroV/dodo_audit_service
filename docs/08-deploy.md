## 1. Что уезжает

**Подъём 04.09.2026, обновление 05.09.2026.** На сервере работает контейнер
`dodo_audit_service-infra-bot-1`, база не поднята — решение подъёма, см. §4.4.

**Код в каталоге и код в контейнере — разные вещи, и на сервере они разошлись.**
Сверено 06.09.2026: `git log` в `C:\projects\dodo_audit_service` показывает

Отставание сборки от `main` на 06.09.2026 — 24 коммита. Обновление сборки это

## 2. Чего на сервере нет и не появится само

**Это главный блокер подъёма, и он не в коде.**

Три вещи лежат вне git и в образ не попадают:

| Что | Почему вне git | Как попадает на сервер |
|---|---|---|
| `data/` — методика | Материалы управляющей компании | Копированием, вручную |
| `examples/` — эталонные проверки | Реальные проверки партнёров | Для работы продукта **не нужны** — только для регрессии |
| `.env` — секреты | Токены и ключи | Заполняется на сервере из `.env.example` |

Каталог методики монтируется в контейнер снаружи (`docker-compose.yml`,
`${AUDIT_DATA_DIR}:/app/data:ro`). Без него бот не работает: пунктов нет,
оценку считать нечем.

`.dockerignore` намеренно запрещает методике попадать в слой образа — вторая
линия защиты на случай, если `Dockerfile` когда-нибудь получит `COPY . .`.

## 3. Площадка

> `<HOST>` здесь и ниже — плейсхолдер: репозиторий публичный, поэтому имя
> машины в него не пишется. Реальное значение — в приватном репозитории инфраструктуры
> и в `~/.ssh/config` на ноутбуке.

Сервер — домашний Windows, доступ `ssh <HOST>`, дефолтный шелл `cmd`,
поэтому команды заворачиваются в `powershell -NoProfile -Command "..."`.

Проверено 04.09.2026: Docker Server **29.6.1** отвечает, каталога
`C:\projects\dodo_audit_service` **нет** (первый подъём), на машине работает
**18 чужих контейнеров**.

**Площадка общая.** Своё — контейнеры своего проекта, своя папка, свои порты.
Чужое не гасить, не пересобирать и не выдавать за своё.

**Долгие процессы не запускать напрямую из ssh:** sshd убивает дерево
процессов при закрытии сессии. Сборка образа и `up -d` укладываются в сессию,
но если процесс длится — заводить одноразовую задачу планировщика.

## 4. Порядок подъёма

Шаги 1–3 проверены сухим прогоном на ноутбуке, шаги на сервере — самим
подъёмом 04.09.2026. Обновление сборки идёт тем же порядком, только без
`git clone` и без копирования методики: и то и другое на сервере уже есть.

### 4.1. Образ собирается и работает — проверено

```bash
docker build -t dodo-audit:local .
```

Собран за 7 секунд на тёплом кэше, размер **1.06 ГБ**. Внутри образа
проверено запуском:

```
методика читается, пунктов: 136
оценка внутри образа: 99.5 A
PDF собран: 17989 байт
письмо собрано, знаков: 687
```

Это снимает главный технический риск: рендерер PDF и системные библиотеки
внутри образа работают, а не «должны работать».

### 4.2. На сервере — проверено подъёмом 04.09.2026

```powershell
# каталог проекта
New-Item -ItemType Directory -Force C:\projects\dodo_audit_service

# код
git clone <url> C:\projects\dodo_audit_service

# методика — копированием с ноутбука, НЕ из git
#   scp -r data <HOST>:C:/projects/dodo_audit_service/data

# секреты
Copy-Item .env.example .env    # и заполнить руками
```

Заполнить в `.env`: токен бота, ключ модели, список разрешённых
идентификаторов, часовой пояс, путь к методике, путь к состоянию.

```powershell
docker compose up -d --build
docker compose ps
docker compose logs --tail=50 bot
```

### 4.3. Один бот — один процесс

Телеграм отдаёт обновления **одному** получателю. Как только бот поднят на
сервере, локально его запускать нельзя: второй слушатель выбьет первого, и
выбитый не упадёт, а молча перестанет получать сообщения.

Перед подъёмом убедиться, что локальный бот не запущен.

### 4.4. База — на сервере НЕ поднята

Решение подъёма 04.09.2026: базу не поднимали. Без неё бот работает — слив в
историю законно необязателен, отказ не отменяет ни отчёта, ни письма, но
аудитору говорится, что история не сохранена.

Цена этого решения сегодня: владелец назвал MVP тремя поверхностями — бот, MCP
и база, — а на сервере из них живут две. **MCP без базы читать нечего**: его
инструменты чтения истории стоят поверх неё.

### 4.5. Подъём базы — порядок готов, на сервере не проверен

Локально этот порядок работает и закрыт тестами; на самом сервере не гонялся
ни разу, поэтому помечен честно. Раскатка, как и всё остальное здесь, требует
явного «да» владельца.

**1. Четыре переменные в `.env`** (имена — из `.env.example`, значения владелец
задаёт сам):

| Переменная | Что это |
|---|---|
| `POSTGRES_PASSWORD` | Пароль владельца базы. Пустой — контейнер не стартует намеренно |
| `DATABASE_URL` | Подключение **приложения**, роль `dodo_audit_app`, права намеренно маленькие |
| `DATABASE_ADMIN_URL` | Подключение **наката**: заводит роль и меняет схему. Приложению эти права не нужны |
| `DATABASE_APP_PASSWORD` | Пароль роли приложения. В git его нет и быть не может; накат ставит его роли |

Разделение не формальность: суперпользователь обходит политики доступа всегда,
и приложение под ним означало бы защиту, которая ничего не держит.

**2. Поднять и накатить:**

```powershell
docker compose --profile db up -d --wait db
docker compose exec bot python -m src.db.migrate
```

`--wait` идёт по проверке готовности самой базы, а не по факту запуска
контейнера: `up -d` отдаёт управление раньше, чем Postgres начинает принимать
соединения, и накат упёрся бы в закрытый порт. Накат идемпотентен — на
накатанной базе печатает «нечего накатывать».

**3. Проверить, а не поверить:** довести в боте проверку до конца и прочитать
её же через MCP — числа, коды, зоны и сроки обязаны совпасть с отчётом.

**Запрещённая команда: `docker compose --profile db down -v`.** Флаг `-v`
удаляет ВСЕ именованные тома проекта, а не только тома профиля, — вместе с
базой уносит `state`, состояние всех идущих проверок. Сносить поимённо:
`docker compose --profile db rm -sf db`.

## 5. Смоук на самом сервере

Проверяется на сервере, а не на ноутбуке. Меньше этого списка — подъём не
считается состоявшимся.

1. **Бот отвечает в телеграме.** Написать боту с разрешённого
   идентификатора, получить ответ. Смотреть в самом телеграме, а не в журнал
   контейнера.
2. **Посторонний не проходит.** Написать с неразрешённого идентификатора —
   ответа быть не должно.
3. **Проверка переживает перезапуск контейнера.** Начать проверку, записать
   находку, `docker compose restart bot`, продолжить: запись на месте.
4. **Отчёт собирается внутри образа на сервере.** Довести проверку до конца,
   получить PDF и письмо в чате.
5. **Оценка сходится с движком.** Процент и буква в отчёте совпадают с тем,
   что даёт движок на том же состоянии.
6. **Том состояния переживает пересоздание контейнера.** `docker compose down`
   (без `-v`!), `up -d`, проверка на месте.

**`docker compose down -v` на сервере не выполнять никогда** — флаг уносит том
вместе с незавершёнными проверками.

## 6. Откат

Готовится **до** подъёма, а не выясняется при отказе.

```powershell
# остановить, не трогая данные
docker compose down

# вернуться на прошлый образ, если он был
docker compose up -d

# полностью убрать проект (данные тома остаются)
docker compose down
Remove-Item -Recurse -Force C:\projects\dodo_audit_service
```

С подъёма 04.09.2026 откатываться есть куда: прошлый образ на сервере остаётся
до следующей сборки, и `docker compose up -d` без `--build` поднимает именно
его. Сносить проект целиком больше не нужно — это крайняя мера.

Том состояния при `down` без `-v` сохраняется — незавершённые проверки
переживают откат.

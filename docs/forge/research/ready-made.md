## 2. Склейка альбомов Telegram по `media_group_id`

### Находка: `deptyped/aiogram-media-group` — готовый декоратор-обвязка, берём как есть

- Репозиторий: https://github.com/deptyped/aiogram-media-group
- Лицензия: MIT (`gh api repos/deptyped/aiogram-media-group` → `licenseInfo.key = "mit"`)
- Звёзд: 51. Последний пуш: 2023-12-15 (`pushedAt`). Не идёт активная разработка, но код
  маленький, самодостаточный, зависит только от `aiogram` — заброшенность не проблема.
- Пакет на PyPI: `aiogram-media-group` (актуальная версия на PyPI — 0.5.1, проверено
  `curl https://pypi.org/pypi/aiogram-media-group/json` → `info.version = "0.5.1"`).
- Прочитано ЦЕЛИКОМ: `aiogram_media_group/handler.py`, `storages/base.py`, `storages/memory.py`,
  `examples/echo-aiogram-3.py`, `README.md` (via `gh api repos/.../git/trees/main?recursive=true`
  + `gh api repos/.../contents/<path>`).

**Что именно берём:** библиотеку целиком через `pip install aiogram-media-group` — не только
паттерн, а сам пакет. Механизм ровно тот, что описан в задаче как «известная боль»:

```python
def media_group_handler(func=None, only_album=True, receive_timeout=1.0, ...):
    def decorator(handler):
        @wraps(handler)
        async def wrapper(message: types.Message, *args, **kwargs):
            if message.media_group_id is None:
                return await handler([message], *args, **kwargs)
            ...
            if await storage.set_media_group_as_handled(message.media_group_id):
                event_loop.call_later(
                    receive_timeout,
                    asyncio.create_task,
                    _on_media_group_received(message.media_group_id, storage, handler, *args, **kwargs),
                )
            await storage.append_message_to_media_group(message.media_group_id, message)
        return wrapper
    ...
```

Идея: на первое сообщение альбома ставится таймер `receive_timeout` (по умолчанию 1.0 сек —
совпадает с окном 1-2 сек, о котором говорится в задаче) через `event_loop.call_later`; все
последующие сообщения того же `media_group_id` копятся в storage; когда таймер срабатывает,
собранный список `messages: List[types.Message]` целиком передаётся в исходный хендлер.
Использование — просто два декоратора:

```python
@dp.message(F.media_group_id, F.content_type.in_({"photo"}))
@media_group_handler
async def album_handler(messages: List[types.Message]): ...
```

Для aiogram 3.x (наш вероятный выбор, см. направление «стек») библиотека использует
собственный `MemoryStorage` (не FSM-хранилище aiogram) — это значит, что при рестарте бота
недосклеенный альбом теряется; для MVP (одна проверка = одна сессия, аудитор стоит рядом)
это приемлемо. Для продакшена есть `storages/redis.py` и `storages/mongo.py`, но по коду
`handler.py` (ветка `AIOGRAM_VERSION == 3`, закомментированный блок) Redis/Mongo-бэкенды
**сейчас реализованы только под aiogram 2.x** — для aiogram 3.x стора всегда in-memory
(`STORAGE = {}` — module-level dict). Это ограничение, а не полная фича; если аудитору
нужна пересборка бота с сохранением незавершённого альбома — надо либо форкнуть и
доделать Redis-стор под v3, либо держать процесс бота живым на время фотосессии.

**Альтернатива, которую НЕ берём:** `WhiteMemory99/aiogram_album_handler`
(https://github.com/WhiteMemory99/aiogram_album_handler, 46 звёзд, без лицензии
`licenseInfo: null`, последний пуш 2022-11-25) — паттерн идентичен (dict + timer), но
отсутствие лицензии и более старая кодовая база делают `deptyped` предпочтительнее.
Смотрел ПО ЗАГОЛОВКУ (README + метаданные репозитория), код не читал — не нужно, раз есть
лицензированная и более новая альтернатива с тем же паттерном.

**Экономия:** реализация и обкатка ретраев/таймеров вручную — это отдельная задача на
полдня-день с тестированием гонок; готовый пакет снимает её полностью. При 4-дневном сроке
MVP это ощутимая доля бюджета.

## 3. Классификация свободного текста в код из фиксированного перечня (136 кодов)

Прямых готовых **библиотек** под задачу «текст → один код из большого фиксированного
списка» нет (это не npm/pypi-пакет, а архитектурный паттерн); зато нашёлся готовый
**архитектурный референс**, который решает практически изоморфную задачу, плюс
документированный паттерн от авторов Instructor.

### Референс-архитектура: `MohammadTina/CommodityCodeClassifier` — retrieval-narrowing + LLM

- Репозиторий: https://github.com/MohammadTina/CommodityCodeClassifier
- Лицензия: GPL-3.0. **Внимание: 0 звёзд**, автор один, `pushedAt` 2026-03-03 — это НЕ
  battle-tested проект, это учебный/пет-проект. Беру его не как зависимость, а как честно
  подсмотренную архитектуру — по коду видно, что она продумана грамотно и решает ровно нашу
  проблему (классификация текста в код из большого справочника национальных таможенных кодов).
- Прочитано ЦЕЛИКОМ: `src/classifier.py`, `src/retrieval/hybrid_retriever.py` (первые ~120
  строк, до `rebuild_index`). Остальные файлы (`fusion.py`, `hierarchy_analyzer.py`,
  `prompt/builder.py`, `llm/response_parser.py`) НЕ читал — виден только их вызов из
  `classifier.py`/`hybrid_retriever.py`, не их реализация.

**Паттерн сужения перечня (то, что прямо просили найти):**

1. **Гибридный retrieval вместо промпта со всеми кодами.** `HybridRetriever.retrieve()`
   комбинирует semantic-поиск (FAISS по эмбеддингам описаний кодов, `semantic_top_k=20`) и
   BM25-поиск по ключевым словам (`bm25_top_k=20`), затем сливает через RRF
   (Reciprocal Rank Fusion, `src/retrieval/fusion.py` — не читал реализацию, только вызов
   `self.fusion.fuse(semantic_results, bm25_results)`), и **обрезает до `llm_candidates`
   (в конфиге дефолт — топ-3)** — именно эти несколько кандидатов, а не все коды, идут в
   промпт LLM.
2. **Сигнал уверенности до LLM.** `HierarchyAnalyzer.analyze(fused_results)` считает,
   насколько кандидаты «кучкуются» в one иерархии кода (`signal['confidence_level']`) —
   если ретривер уверен, это идёт в промпт как подсказка модели.
3. **Явный путь «нет уверенного совпадения»:** если `candidates` пуст —
   `_no_candidates_result()` возвращает `confidence: "NO MATCH"` без похода к LLM вообще.
   Прямо соответствует нашему требованию «модель предлагает, фиксирует человек»: пустой
   результат — явный сигнал аудитору решать самому, а не подсовывать модели гадать.
4. **Индекс перестраивается отдельной командой** (`scripts/build_index.py`,
   `rebuild_index()`/`/reindex` эндпоинт) — при 136 кодах чек-листа переиндексация вообще не
   проблема по объёму (это на порядки меньше, чем справочник таможенных кодов, под который
   писан этот пример), FAISS тут скорее избыточен — для 136 записей эмбеддинг-поиск можно
   держать в памяти без библиотеки индексов вообще (просто пробежаться косинусным сходством
   по 136 векторам).

**Что именно берём:** не код (лицензия GPL-3.0 и общее качество пет-проекта не оправдывают
копирование), а **архитектурное решение** — двухступенчатый пайплайн retrieval→LLM с явной
обрезкой кандидатов перед промптом, плюс паттерн «пустой список кандидатов = не спрашивать
LLM, отдать человеку». Для 136 кодов вместо FAISS+BM25+RRF (оверинжиниринг для такого объёма)
достаточно: заранее посчитанные эмбеддинги описаний 136 кодов чек-листа (OpenAI
`text-embedding-3-small` или аналог) + косинусное сходство к тексту находки аудитора →
top-8..12 кандидатов → это и передаётся в LLM с просьбой (structured output) выбрать один код
или вернуть «нет совпадения». Зонирование (10 физических зон) даёт бесплатный
предварительный фильтр: если аудитор фотографирует в горячем цеху, можно сразу сузить
перечень до кодов этой зоны, что при ~13-14 кодах на зону делает промпт тривиально коротким
без всякого retrieval вообще — **это может оказаться проще и надёжнее эмбеддингов**, если
зона известна на момент фото (см. вопрос по UX бота на этапе брейншторма).

### Structured output инструменты: `instructor` и `pydantic-ai` — оба живые, оба подходят

- `567-labs/instructor` — https://github.com/567-labs/instructor — MIT, 13793 звёзд,
  `pushedAt` 2026-08-28 (сегодня) — очень активен.
- `pydantic/pydantic-ai` — https://github.com/pydantic/pydantic-ai — MIT, 19554 звёзд,
  `pushedAt` 2026-08-28 (сегодня) — очень активен, от авторов Pydantic (та же команда,
  что и валидация данных, которая, вероятно, уже используется в проекте).
- Просмотрено ПО ЗАГОЛОВКУ + официальная страница примеров instructor
  (https://python.useinstructor.com/examples/classification/, дошло через веб-поиск,
  не через `gh`) — там прямо документирован рекомендуемый паттерн для классификации:
  **`Literal[...]` предпочтительнее `Enum`** для полей-меток в Pydantic-модели ответа —
  лучше типизация и проще для самой библиотеки validation/retry. Для 136 кодов это означает
  на любом отдельном шаге классификации (после сужения до топ-N) объявлять поле как
  `Literal["CLN05", "PRD09", ...]` **только из отфильтрованного подмножества**, а не из
  всех 136 сразу — сам факт использования `Literal` не решает проблему объёма промпта, но
  подтверждает, что двухступенчатый подход (сузить → потом Literal/enum по узкому набору)
  — стандартная практика, а не самодельное решение.
- **Дополнительно найден паттерн** через `gh search code` по многостадийным
  классификаторам (`ISIC`/HS-код классификация из статьи arXiv 2409.18988, не GitHub-код,
  найдено через веб-поиск) — при большом справочнике категорий прямая классификация в один
  шаг даёт низкую точность, поэтому применяется двухфазный фреймворк: сначала сузить список
  категорий, потом классифицировать — это независимое подтверждение того же паттерна, что
  и в `CommodityCodeClassifier`, за пределами одного пет-проекта.

**Вывод:** готовой библиотеки «классификатор в код из перечня» нет и не нужно — нужный код
на 136 записей достаточно мал, чтобы написать самим (эмбеддинг-сходство + вызов
instructor/pydantic-ai с `Literal` по сокращённому списку). Ценность находки — в
подтверждённом паттерне (сузить retrieval'ом или зоной → потом structured output по узкому
множеству) и в том, что обе кандидатные библиотеки для structured output живы и активно
поддерживаются на сегодняшний день.

## 5. Конечный автомат диалога / FSM для длинных сессий с сохранением состояния

### Находка: FSM в aiogram 3 — встроенный, с pluggable-хранилищами (in-memory / Redis)

- Репозиторий: https://github.com/aiogram/aiogram (не сторонняя библиотека — сама
  фреймворк-функциональность). Лицензия MIT, 5851 звезда, `pushedAt` 2026-08-26
  (два дня назад на момент исследования) — активно поддерживается.
- Прочитано ЦЕЛИКОМ: `aiogram/fsm/storage/redis.py` (класс `RedisStorage`, через
  `gh api repos/aiogram/aiogram/contents/aiogram/fsm/storage/redis.py`) — первые ~60 строк
  (конструктор + `from_url`); остальную часть файла (get/set/close) не читал построчно,
  сигнатура и назначение класса понятны из показанного.
- Подтверждено через `gh search code`, что это не редкость, а стандартная практика: 20+
  реальных ботов-шаблонов и продакшен-проектов (`Latand/tgbot_template_v3`, `pipedude/evi-run`,
  `devvsima/dating-bot`, `rodion-gudz/telegram-bot-template` и др.) импортируют именно
  `from aiogram.fsm.storage.redis import RedisStorage` — то есть паттерн «FSM +
  Redis-хранилище состояния для переживания рестарта процесса» широко обкатан сообществом.

**Что именно берём:** саму встроенную FSM-модель aiogram 3 (`StatesGroup`/`State`,
декоратор `@dp.message(StateFilter(MyState.step))`, `FSMContext.set_state()` /
`.update_data()` / `.get_data()`) как основу диалога аудита — без неё FSM всё равно
пришлось бы писать вручную поверх any framework. Дополнительно берём готовый
`RedisStorage.from_url(...)` для персистентности: если процесс бота на Windows-сервере
упадёт или передеплоится посреди проверки (пока аудитор ходит по объекту 30-60 минут),
состояние сессии (текущий шаг, накопленные находки, ожидание фото/голоса) переживёт
рестарт — ровно требование «возможность продолжить прерванную сессию» из задачи. Для
MVP на 4 дня встроенного `MemoryStorage` тоже достаточно (если бот не перезапускается во
время проверки), но раз Redis-обвязка уже есть в фреймворке «из коробки» — включить её
сразу дешевле, чем добавлять потом.

### Также найдено (не обязательно нужно для MVP, но по адресу): `Tishka17/aiogram_dialog`

- Репозиторий: https://github.com/Tishka17/aiogram_dialog — «GUI framework on top of
  aiogram». Лицензия Apache-2.0, 900 звёзд, `pushedAt` 2026-06-17 — активен,
  не архивирован (`archived: false`).
- Просмотрено ПО ЗАГОЛОВКУ (описание репозитория через `gh api`); код не читал.
- Это надстройка над FSM aiogram с концепцией «диалогов» и «окон» (экранов), заточенная
  под сложные многошаговые интерфейсы с кнопками/меню и явным стеком навигации
  (назад/вперёд между шагами анкеты). Для нашего сценария (аудитор присылает фото/голос,
  бот сам определяет пункт чек-листа, а не листает меню пошагово) это, вероятно,
  избыточно — наш диалог управляется вложениями, а не навигацией по экранам. Стоит держать
  в уме, если на этапе стека решат, что нужен богатый UI подтверждения находок
  (карточка с кнопками «принять/править/отклонить», листание по найденным пунктам) —
  тогда `aiogram_dialog` снимет ручную работу со стеком состояний экранов. Решение — не
  моё, а по стеку/UX.

## 6. Транскрипция голосовых сообщений в боте

### Находка: `RichardAtCT/claude-code-telegram` — `voice_handler.py`, три провайдера транскрипции в одном файле

- Репозиторий: https://github.com/RichardAtCT/claude-code-telegram
- Лицензия: MIT — подтверждено по тексту README (`## License\n\nMIT License -- see [LICENSE](LICENSE).`,
  `gh api repos/RichardAtCT/claude-code-telegram/contents/README.md`); сам файл `LICENSE`
  через Contents API не отдался декодируемым (бинарный ответ get), но бейдж и раздел License
  в README однозначны.
- Звёзд: 2771. Активность: `pushedAt` 2026-03-30, `updatedAt` 2026-08-28 — живой, свежий проект.
- Прочитано ЦЕЛИКОМ: `src/bot/features/voice_handler.py` (через `gh api .../contents/<path>`).

**Что именно берём:** не библиотеку целиком (это часть чужого бота под Claude Code), а
паттерн + фрагмент кода класса `VoiceHandler` — он уже решает именно нашу задачу
(«готовые обвязки транскрипции голосовых в боте»):

- Скачивание: `voice.get_file()` → `file.download_as_bytearray()` (python-telegram-bot API;
  для aiogram 3 аналог — `bot.download(voice.file_id)`), с проверкой размера файла
  ДО и ПОСЛЕ скачивания (`_ensure_allowed_file_size`) — защита от download-бомб, полезный
  паттерн, которого не было в задаче явно, но стоит перенять.
- Три провайдера за одним интерфейсом, выбираемых конфигом (`config.voice_provider`):
  1. **OpenAI Whisper API** — `client.audio.transcriptions.create(model=..., file=("voice.ogg", voice_bytes))`
     — OGG отправляется как есть, без конвертации в WAV (Whisper API принимает ogg/opus нативно).
  2. **Mistral Voxtral** — аналогичный вызов `client.audio.transcriptions.complete_async(...)`.
  3. **Локальный whisper.cpp** — единственная ветка, где нужна конвертация:
     `ffmpeg -i voice.ogg -ar 16000 -ac 1 -f wav voice.wav` (Telegram отдаёт голос в
     OGG/Opus, whisper.cpp ждёт WAV 16kHz моно), затем субпроцесс `whisper-cli -m model.bin -f voice.wav`.
- Оба субпроцесса (`ffmpeg`, `whisper.cpp`) обёрнуты в `asyncio.wait_for(..., timeout=120)`
  с явным `process.kill()` по таймауту — не зависнет молча.

**Вывод для нас:** если транскрипция идёт через облачный API (OpenAI/Mistral/Groq — у нас,
вероятно, уже есть контракт с одним из LLM-провайдеров для классификации по коду чек-листа,
см. направление 3) — **конвертация не нужна вообще**, отправляем `.ogg` как есть. `ffmpeg`
нужен только если решим гонять транскрипцию локально/офлайн на Windows-сервере — тогда
приведённый выше паттерн конвертации и вызова whisper.cpp переносим один в один.

### Альтернатива, которую тоже смотрел: `aviaryan/voice-transcribe-summarize-telegram-bot`

- Репозиторий: https://github.com/aviaryan/voice-transcribe-summarize-telegram-bot
- Лицензия: MIT (`licenseInfo.key = "mit"`). Звёзд: 76. `pushedAt`: 2025-02-16 — живой,
  хоть и не обновлялся полгода.
- Прочитано ЦЕЛИКОМ первые ~100 строк `bot.py` (транскрипция через Groq
  `groq_client.audio.transcriptions.create(model="distil-whisper-large-v3-en", ...)`).
- Проще предыдущего (без выбора провайдера, без лимита размера файла, без таймаутов) —
  как референс полезен, но `voice_handler.py` выше покрывает тот же сценарий надёжнее.
  Не берём как основу, только для сверки паттерна «Groq как дешёвый Whisper-хостинг».

## 4. Сборка PDF-отчётов с фотографиями из Python (без X-сервера, живое в 2026)

### Подтверждено: wkhtmltopdf официально мёртв — не рассматриваем

- https://github.com/wkhtmltopdf/wkhtmltopdf — `isArchived: true`, `archivedAt: 2023-01-02`
  (`gh repo view wkhtmltopdf/wkhtmltopdf --json isArchived,archivedAt`). Задача была права —
  библиотека архивирована больше трёх лет назад, `pushedAt` тоже 2022-11-22. Не использовать.

### Находка: `Kozea/WeasyPrint` — живая, без браузера/X-сервера, HTML+CSS → PDF

- Репозиторий: https://github.com/Kozea/WeasyPrint
- Лицензия: BSD-3-Clause. Очень активна: `pushedAt` 2026-08-25 (три дня назад на момент
  исследования), 9538 звёзд (`gh repo view Kozea/WeasyPrint --json ...`).
- Просмотрено ПО ЗАГОЛОВКУ (описание репозитория + общеизвестная архитектура; код рендерера
  не читал — библиотека большая, важен факт активности и архитектуры, не внутренности).
- **Почему подходит под ограничение «без Х-сервера»:** WeasyPrint не оборачивает браузер
  (в отличие от Puppeteer/Playwright-PDF), а сам реализует рендеринг CSS поверх Pango/cairo/
  GDK-Pixbuf — чисто библиотечный путь без headless-браузера и без дисплея. Значит в Docker
  нужны системные библиотеки (Pango, cairo, harfbuzz — обычно ставятся пакетом
  `weasyprint`'s зависимостей через apt: `libpango-1.0-0`, `libpangocairo-1.0-0` и т.п.),
  но НЕ Xvfb и НЕ Chromium — контейнер легче, чем puppeteer-путь.
- **Что берём:** сам подход — верстать отчёт как HTML/CSS-шаблон (Jinja2 → HTML → `weasyprint.HTML(string=html).write_pdf(path)`),
  вставлять фото аудита через `<img src="file:///...">` или base64 data URI. Для команды,
  уже умеющей верстать HTML/CSS (а не API конкретной PDF-библиотеки), это резко снижает
  порог входа на 4-дневном сроке — макет письма/отчёта пишется как веб-страница.

### Альтернатива: `py-pdf/fpdf2` — чистый Python, минимум системных зависимостей

- Репозиторий: https://github.com/py-pdf/fpdf2
- Лицензия: LGPL-3.0. Очень активна: `pushedAt` 2026-08-28 (сегодня), 1537 звёзд.
- Просмотрено ПО ЗАГОЛОВКУ (описание + известный API `FPDF()`, `cell()`, `image()`).
  Не читал исходники рендерера.
- Плюс относительно WeasyPrint: **вообще без системных C-библиотек** — чистый Python + Pillow
  для изображений, что для Docker-образа на Windows-хосте (задача упоминает целевую площадку —
  Docker на Windows-сервере) означает меньше риска платформенных сюрпризов при сборке образа.
  Минус: вёрстка идёт императивно (`pdf.cell(...)`, координаты X/Y), а не декларативным HTML —
  для отчёта с фотографиями и таблицей находок по зонам это более многословный код, чем
  Jinja-шаблон.
- **Рекомендация:** если отчёт простой (список находок + фото + сводная таблица) — fpdf2
  быстрее поднять с нуля и без забот про apt-зависимости в Dockerfile. Если отчёт похож на
  документ с версткой (несколько колонок, брендированная шапка, разбивка по зонам как
  визуальные блоки) — WeasyPrint эффективнее по времени за счёт HTML/CSS. Выбор — решение
  по стеку, не по этой находке; обе живые и рабочие в Docker без X-сервера.

## 1. Библиотека Telegram-бота: aiogram vs python-telegram-bot (2026)

### Актуальные версии
- **aiogram**: последний стабильный релиз **3.31.0** от 26 августа 2026 (i18n-фиксы, обработка Live Photo сообщений, контекст webhook-диспетчера). Ветка `dev-3.x`. [прочитано целиком: https://docs.aiogram.dev/en/dev-3.x/changelog.html]. Библиотека активно релизится (3.24.0 → 3.31.0 за январь–август 2026, релиз примерно раз в 3-5 недель).
- **python-telegram-bot (PTB)**: последний стабильный релиз **v22.8** от 12 июня 2026 — security-изменения, deprecations, полная поддержка Bot API 9.6 и 10.0, апдейты зависимостей. [прочитано целиком: https://docs.python-telegram-bot.org/en/stable/changelog.html]. Предыдущие: v22.7 (16 марта 2026), v22.6 (24 января 2026, поддержка Bot API 9.3).
- Обе библиотеки активно поддерживаются, обе async-first (aiogram — asyncio с самого 3.x, PTB v20+ тоже полностью asyncio).

### FSM и хранение состояния
- У aiogram 3.x есть встроенный FSM-модуль (`aiogram.fsm`) со сменными storage-бэкендами (`MemoryStorage` из коробки, плюс официальные пакеты для Redis/Mongo). [просмотрено: https://github.com/aiogram/aiogram/blob/dev-3.x/aiogram/fsm/storage/memory.py — сам код MemoryStorage прочитан]. `MemoryStorage` явно не рекомендован для продакшена: состояние теряется при рестарте.
- У PTB есть аналог — `PersistenceInput`/`BasePersistence` с готовыми `PicklePersistence`, но полноценного FSM-модуля (state groups как у aiogram) в PTB нет "из коробки" в том же виде — состояние обычно ведут через `context.user_data`/`chat_data` + persistence-слой. Это менее структурировано под пошаговый чек-лист-флоу, чем FSM aiogram. [требует доп. проверки по офиц. доке PTB persistence — см. ниже, пока частично по вторичным источникам]

### media_group_id (альбомы)
- **aiogram не имеет встроенной склейки альбомов** — `media_group_id` приходит как отдельные апдейты, группировать их (ждать все фото альбома перед обработкой) нужно руками или через community-пакет `aiogram_album`. [просмотрено: результаты поиска, вторичный источник — требует проверки по факту в issue-трекере aiogram]
- Для проекта это не критично: чек-лист аудита предполагает по одному фото на пункт с подтверждением аудитором, а не альбомы — но если аудитор пришлёт несколько фото одним альбомом, склейку придётся написать самим в любом случае, независимо от библиотеки.

### Уточнение по FSM storage (первоисточник)
[прочитано целиком: https://docs.aiogram.dev/en/dev-3.x/dispatcher/finite_state_machine/storages.html]
- `MemoryStorage` — обычный dict в памяти процесса, без внешних зависимостей, **данные теряются при рестарте бота**. Только для разработки.
- `RedisStorage` — официальный бэкенд, требует пакет `redis`, переживает рестарт бота, поддерживает TTL на state и на data по отдельности, можно инициализировать по connection URL.
- `PyMongoStorage` — официальный бэкенд поверх `pymongo`, переживает рестарт. Старый `MongoStorage` (на `motor`) помечен deprecated, будет удалён.
- **Официального Postgres-бэкенда для FSM storage в aiogram нет** — только Redis и Mongo из коробки. Кастомный storage пишется расширением `BaseStorage` (`set_state`, `get_state`, `set_data`, `get_data`, `close`) — несложно, но это доп. работа, если хотим состояние именно в уже используемом Postgres, а не заводить Redis только ради FSM.

### Уточнение по PTB persistence (первоисточник)
[прочитано целиком: https://docs.python-telegram-bot.org/en/stable/telegram.ext.basepersistence.html]
- Из коробки только **`PicklePersistence`** (сериализация в файл) и **`DictPersistence`** (память). Официального Redis/Postgres бэкенда тоже нет — только базовый класс `BasePersistence` для кастомной реализации.
- Обновление персистентного стораджа идёт по циклу (по умолчанию раз в 60 секунд), что для чек-листа с редкими, но важными шагами (сорвался — потерял до минуты последних правок) не идеально без доп. настройки `update_interval`.

### Рекомендация под срок 4 дня
**aiogram 3.31.0.** Обоснование: (1) современный async API, активная поддержка, встроенный FSM прямо из коробки закрывает ключевую потребность проекта — пошаговый чек-лист с шагами-состояниями; (2) route/router-система удобна для разделения диалогов (старт проверки, ввод зоны, фото, голос, финализация) на модули; (3) MemoryStorage для разработки, лёгкая замена на RedisStorage в проде без переписывания логики хендлеров — важно под требование «переезд не должен быть переписыванием». PTB тоже жизнеспособен, но его модель `context.user_data` + persistence менее прямолинейна для строгого пошагового флоу чек-листа, чем явный FSM aiogram, и это стоит времени при сроке в 4 дня.

## 2. Хранение состояния диалога и продолжение после рестарта

- Официальные живые бэкенды FSM у aiogram — только **Redis** (`RedisStorage`) и **MongoDB** (`PyMongoStorage`), см. п.1. Postgres-бэкенда в официальном пакете нет.
- Community-пакет `AiogramStorages` (PGStorage поверх asyncpg) — **не живой**: версия 1.0.0 от марта 2023, один мейнтейнер, поддержка Python объявлена до 3.11, апдейтов нет. [прочитано целиком: https://pypi.org/project/AiogramStorages/]. Использовать для проекта в 2026 не стоит — риск несовместимости и отсутствия исправлений.
- `aiogram-sqlalchemy-storage` — страница PyPI не открылась через фетч (ошибка загрузки), статус не подтверждён первоисточником; трактовать как непроверенный, при необходимости проверять `pip index versions aiogram-sqlalchemy-storage` вручную перед использованием.
- **Архитектурная рекомендация под требования проекта** (не нашлось единого готового решения — вывод из фактов выше): развести на два независимых слоя.
  1. **Шаг диалога (FSM state)** — держать в `RedisStorage` (официальный, поддерживается, TTL из коробки). Redis — маленький доп. контейнер в том же docker-compose, не привязан к ОС хоста, переезд Windows→Linux не требует правок кода.
  2. **Сами данные чек-листа** (что аудитор уже отметил по каждому пункту) — писать сразу в Postgres по мере подтверждения, а не держать в FSM `data`. Тогда даже полная потеря Redis (state) не теряет уже подтверждённые ответы — при реконнекте бот увидит "есть незавершённая проверка X с уже заполненными пунктами A, B" по данным в Postgres и восстановит FSM-состояние на нужный шаг, вместо того чтобы полагаться на устойчивость единственного хранилища. Это резервирует «прерванную проверку можно продолжить после перезапуска» на уровне архитектуры, а не конкретного FSM-стораджа.
  - Для 4 дней MVP допустимо на старте использовать `MemoryStorage` и просто заранее спроектировать хендлеры так, чтобы шаг FSM можно было вывести из состояния записи в Postgres (не полагаться только на память) — тогда добавление Redis позже становится конфигурационной правкой, а не рефакторингом.

## 3. Транскрипция голоса

### Формат голосовых в Telegram — нужна ли перекодировка
- Официальный объект `Voice` в Bot API **не мандирует** конкретный формат в описании (`mime_type` — «Optional. MIME type of the file as defined by the sender»). [прочитано целиком: https://core.telegram.org/bots/api#voice — секция Voice]
- На практике все клиенты Telegram (запись через кнопку микрофона) отправляют голосовые как **OGG-контейнер с кодеком Opus** (`audio/ogg`) — это устоявшееся поведение экосистемы, подтверждаемое множеством разработческих источников (напр. по built-in свойствам `sendVoice`/`Voice`, где `.ogg`+OPUS — единственный формат, который Telegram рендерит как голосовое сообщение со waveform и регулировкой скорости). [просмотрено: несколько вторичных источников, включая gramio.dev и shashwatv.com — согласованно утверждают OGG/Opus как формат `Voice`]
- **OpenAI Whisper/транскрипция API не принимает OGG/Opus напрямую** — поддерживаемые форматы: `mp3`, `mp4`, `mpeg`, `mpga`, `m4a`, `wav`, `webm`. [прочитано целиком: https://developers.openai.com/api/docs/guides/speech-to-text]. **Вывод: перекодировка нужна** — минимум OGG→WAV/MP3/M4A через `ffmpeg` перед отправкой в OpenAI API. Для локального faster-whisper/whisper.cpp перекодировка тоже практически нужна: обе библиотеки читают аудио через `ffmpeg`/`PyAV` внутри, но передавать OGG напрямую в `faster-whisper` работает (оно само декодирует через bundled ffmpeg-биндинг) — можно не конвертировать вручную при локальном инференсе, конвертация нужна именно для облачного OpenAI API.
- Лимит: 25 МБ на файл транскрипции у OpenAI [прочитано целиком: там же]; голосовые Telegram лимитированы 50 МБ на загрузку [просмотрено: вторичный источник], для чек-листа аудита с голосовыми комментариями по пункту это некритично — сообщения короткие.

### Локальный инференс: faster-whisper vs whisper.cpp
- **faster-whisper** (реимплементация Whisper на CTranslate2): актуальная версия **1.2.1**, релиз **31 октября 2025** — то есть в разработке, но релизится нечасто (1.2.0 был 6 августа 2025). [прочитано целиком: https://pypi.org/project/faster-whisper/ — история релизов]. Использует те же веса Whisper (large-v3 и т.д.), точность идентична референсной реализации OpenAI — разница только в скорости и памяти исполнения. Лучше на NVIDIA GPU (int8-квантование через CTranslate2).
- **whisper.cpp** — C/C++-порт, лучше на CPU-only и на Apple Silicon (Metal/Core ML); по вторичным источникам быстрее и экономнее по памяти на чистом CPU, чем faster-whisper (сравнение на Intel i7-12700K, 13 минут аудио: whisper.cpp 2м05с/1049МБ против faster-whisper fp32 2м37с/2257МБ). [просмотрено: вторичные блог-источники (codersera, promptquorum) — не первоисточник, к использованию как ориентир, не как точное число]
- **Точность на русском**: ни официальный README `openai/whisper`, ни блоги не дали числового WER по русскому в рамках этого поиска — официальный repo ссылается на breakdown WER/CER по языкам в приложении статьи (arXiv), но конкретные цифры по русскому не прочитаны в первоисточнике в рамках этой сессии. **Это открытый пробел** — перед принятием решения "локально vs API" для русского языка стоит либо прогнать быстрый практический тест на 5-10 реальных голосовых аудитора, либо свериться напрямую с таблицей WER по языкам в статье Whisper (arXiv 2212.04356, Appendix) или с HuggingFace Open ASR Leaderboard — не сделано в этом заходе из-за бюджета времени поиска.
- Требования к ресурсам (из официального README `openai/whisper`, модели идентичны для faster-whisper/whisper.cpp): [прочитано целиком: https://github.com/openai/whisper — таблица моделей]
| Модель | Параметры | VRAM |

| tiny | 39M | ~1 GB |
| base | 74M | ~1 GB |
| small | 244M | ~2 GB |

### Рекомендация под срок 4 дня
**OpenAI-транскрипция через API** (`gpt-4o-mini-transcribe`, $0.003/мин, либо `whisper-1`) — не локальная модель. Обоснование: (1) ноль забот с ресурсами контейнера на Windows-сервере без GPU — движок и так CPU-bound (PDF, расчёт), не хочется грузить CPU ещё и STT; (2) цена ничтожна при объёме голосовых аудита; (3) не нужно решать вопрос точности на русском вручную — OpenAI держит современные веса. Требуется шаг перекодировки OGG→поддерживаемый формат через `ffmpeg` (лёгкая системная зависимость, доступна в `python:3.x-slim` через `apt install ffmpeg`). Если позже потребуется офлайн/приватность — `faster-whisper` с моделью `small`/`medium` как запасной вариант, без переписывания вызывающего кода (изолировать за одним интерфейсом `transcribe(audio_bytes) -> str`).

### Как гарантировать код строго из перечня (structured output)
Два независимых и совместимых механизма, оба подтверждены в коде первоисточника:
1. **Strict tool use** — на определении тула ставится `"strict": true` (на уровне тула, не `tool_choice`) + JSON Schema с `additionalProperties: false` и `enum` на нужном поле (пример из доки: `"passengers": {"type": "integer", "enum": [1,2,3,...]}`). Гарантирует, что `tool_use.input` валидируется строго по схеме — то есть значение поля будет строго одним из значений `enum`.
2. **Structured Outputs через `output_config.format`** (JSON Schema) — либо high-level `client.messages.parse(..., output_format=PydanticModel)` (Pydantic-модель с `Literal[...]` или `Enum` на поле кода — это и задаёт «строго один из перечня»), либо raw `output_config={"format": {"type": "json_schema", "schema": {...}}}` с `enum` в схеме поля.
- Для задачи «выбрать код пункта чек-листа из фиксированного перечня» практичнее всего: **Pydantic-модель с полем `code: Literal["D1", "D2", ...]`** через `client.messages.parse()` — валидация схемы гарантирует, что модель не сможет вернуть код не из перечня (запрос будет либо провалидирован, либо API вернёт ошибку/retry).

### Как передать фото вместе с текстом (vision)
Content-блок `{"type": "image", "source": {"type": "base64", "media_type": "image/jpeg", "data": <b64>}}` в том же списке `content`, что и текстовый блок `{"type": "text", "text": "..."}` — оба в одном user-сообщении. Также поддерживается `"source": {"type": "url", "url": "..."}` для готового публичного URL вместо base64. Ограничений на смешение "фото пункта чек-листа + вопрос какой это код" нет — это стандартный multimodal-запрос в один вызов `messages.create`.

### Structured output / фиксированный enum
`response_format`/`text.format` (Responses API) с `"type": "json_schema"`, `"strict": true` и полем со свойством `"enum": [...]` в JSON Schema — модель гарантированно возвращает значение строго из перечня. Пример схемы (прочитано целиком):
```json
{"type": "object", "properties": {"category": {"type": "string", "enum": ["violence","sexual","self_harm"]}}, "required": ["category"], "additionalProperties": false}
```
Механизм у OpenAI и Anthropic функционально эквивалентен: JSON Schema + `enum` + строгий режим валидации.

### Фото + текст (vision)
Responses API: `input_image` content-блок (наряду с `input_text`) внутри `content` пользовательского сообщения; `image_url` принимает как обычный URL, так и data-URL с base64 (`data:image/jpeg;base64,...`), либо `file_id` для заранее загруженного файла. Пример (прочитано целиком):
```json
{"role": "user", "content": [
  {"type": "input_text", "text": "what's in this image?"},
  {"type": "input_image", "image_url": "...", "detail": "auto"}
]}
```

### Итоговая рекомендация по LLM (Anthropic vs OpenAI) под срок 4 дня
Обе платформы одинаково хорошо закрывают требование «код строго из перечня» (JSON Schema + `enum` + strict) и «фото вместе с текстом». Выбор — не по возможностям API, а по прагматике:
- Если движок и остальной стек уже трогает одну экосистему секретов/биллинга — брать её же, чтобы не заводить два провайдерских ключа ради MVP на 4 дня.
- Ценово для простой классификации дешевле дешёвые модели: **Claude Haiku 4.5** ($1/$5 за 1M) или **`gpt-4o-mini`** ($0.15/$0.60 за 1M) — `gpt-4o-mini` заметно дешевле по input, но задача small-scale (несколько классификаций на фото за проверку), разница в центах несущественна на масштабе MVP.
- Рекомендация: **один провайдер на выбор владельца** (нет технического дифференциатора под эту задачу), с изоляцией вызова за одной функцией `classify_checklist_item(photo, note) -> code` — тогда смена провайдера или модели — конфигурационная правка, не рефакторинг, что соответствует требованию «переезд не должен быть переписыванием».

### WeasyPrint — актуальная версия и зависимости
[прочитано целиком: https://doc.courtbouillon.org/weasyprint/stable/first_steps.html, https://doc.courtbouillon.org/weasyprint/stable/changelog.html]
- Текущая стабильная версия — **69.0**, релиз **2 июня 2026** (в этом релизе, среди прочего, закрыт CVE-2026-49452 — апдейтиться стоит, особенно если используется `--presentational-hints` с недоверенным HTML; чек-лист-контент свой, не пользовательский произвольный HTML, риск ниже).
- Требования: **Python ≥ 3.10.0**, **Pango ≥ 1.44.0**, плюс `pydyf`, CFFI, `tinyhtml5`, `tinycss2`, `cssselect2`, `Pyphen`, `Pillow`, `fontTools`.
- Системные пакеты на Debian/Ubuntu (для wheel-инсталляции): `libpango-1.0-0 libpangoft2-1.0-0 libharfbuzz-subset0`.
- Чистый Python, никакого headless-браузера — вписывается в требование «без графической среды».
- **Нумерация страниц** — из коробки через CSS Paged Media (`@page { @bottom-center { content: counter(page) " of " counter(pages); } }`), поддерживается спецификацией, которую WeasyPrint реализует. [просмотрено: вторичные источники по синтаксису CSS Paged Media — сам синтаксис CSS3, а не специфика WeasyPrint, независимо проверяемый факт]
- **Кириллица**: рендерится через любой установленный в образе шрифт с кириллическими глифами — WeasyPrint использует системные шрифты через Pango, плюс поддерживает `@font-face` с указанием URL/пути на конкретный файл шрифта. Значит в Docker-образе нужно доставить шрифт с кириллицей (`fonts-dejavu` или `fonts-noto` через `apt-get install`) — иначе кириллица либо не отрендерится, либо упадёт на fallback-глифы.
- Известный минус (по вторичным источникам, не проверено на своих объёмах): WeasyPrint медленный на больших документах — пример «52-страничный PDF ~100 секунд», большие таблицы (5000+ строк) — 1.4+ ГБ RAM. Для отчёта по одной проверке пиццерии (несколько страниц, чек-лист на ~30-60 пунктов) это нерелевантно — далеко не тот объём.

### Альтернатива: headless Chrome / Playwright
- Официальный `mcr.microsoft.com/playwright/python` образ — **~1.8-1.94 ГБ** (включает все три движка — Chromium, Firefox, WebKit — и их системные зависимости). Отдельный `playwright/chromium` образ — компактнее, ~684 МБ (compressed). [прочитано частично: заголовки/сниппеты Docker Hub страниц — не открывал сами Dockerfile] Playwright умеет печатать PDF через `page.pdf()` (headless Chromium), поддерживает нумерацию через `header_template`/`footer_template` с `<span class="pageNumber">`, кириллица — вопрос наличия шрифтов в образе (Chromium использует собственный рендеринг + системные шрифты).
- Для проекта явный перевес не в её пользу: движок уже на Python, дополнительная headless-браузерная зависимость — это лишний вес образа (более 1 ГБ против десятков МБ у WeasyPrint) и лишняя точка отказа (падение браузерного процесса, зависшие Chromium-процессы) при сроке в 4 дня.

### Рекомендация под срок 4 дня
**WeasyPrint 69.x.** Обоснование: чистый Python (легко встраивается в уже существующий движок без нового рантайма), маленький образ, поддерживает нумерацию страниц и кириллицу «из коробки» при наличии установленного шрифта, активно поддерживается (релизы каждые 2-3 месяца, последний — июнь 2026 с security-фиксом). В Dockerfile нужно явно поставить `libpango-1.0-0 libpangoft2-1.0-0 libharfbuzz-subset0` + шрифт с кириллицей (`fonts-dejavu-core` достаточно для отчёта, `fonts-noto` — шире охват языков под многоязычность из п.7). Замена площадки Windows-докер → Linux-хост ничего не меняет: то же Debian/Ubuntu base-образ работает одинаково на обоих.

## 6. Postgres из Python

### Актуальные версии (первоисточники)
- **SQLAlchemy** — стабильная версия **2.0.52**, релиз **11 августа 2026** (2.1.0b3 доступна как бета). [прочитано целиком: https://www.sqlalchemy.org/]
- **Alembic** — версия **1.19.1**, релиз **8 августа 2026**, активно поддерживается, требует Python ≥3.10, MIT-лицензия, от автора SQLAlchemy. [прочитано целиком: https://pypi.org/project/alembic/]
- Асинхронное расширение SQLAlchemy («asyncio extension») официально существует только для Python 3 (без нижней границы версии в тексте секции), ставится флагом `pip install sqlalchemy[asyncio]` — важно поставить именно с этим extras, чтобы подтянулся `greenlet` (нужен на платформах без готовых wheel, например Apple M1 — для нашего Docker/Linux сборка wheel есть, но extras всё равно ставить). [прочитано целиком: https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html]
- Прямого официального указания "предпочитайте asyncpg vs psycopg3" в прочитанной документации SQLAlchemy не нашлось — документация лишь показывает пример диалекта `postgresql+asyncpg` как рабочий. Дальнейшее — по вторичным источникам (не первоисточник, трактовать как ориентир):
  - `asyncpg` — обычно быстрее в прямом подключении к Postgres без пулера; есть нюанс — statement cache asyncpg может конфликтовать с механизмом recycling соединений SQLAlchemy при работе за внешним connection-пулером (PgBouncer и т.п.).
  - `psycopg3` (async-режим) — предпочтителен, если между приложением и Postgres стоит внешний pooler (PgBouncer), плюс имеет единый sync/async API и статическую типизацию.
  - [просмотрено: несколько блог-источников 2026 года, согласованно повторяющих это разделение — не первоисточник]

### Рекомендация под срок 4 дня
Проект пока без внешнего connection-пулера (штатный сервер/ноутбук с Postgres, не микросервисная инфраструктура с PgBouncer) — значит нет причины избегать `asyncpg`. **SQLAlchemy 2.x (async engine) + `asyncpg` как драйвер + Alembic для миграций.** Обоснование: (1) SQLAlchemy 2.x — стандарт де-факто для нового Python-проекта с Postgres, ORM или Core-режим по вкусу; (2) `asyncpg` — самый быстрый путь и не требует настройки poolers сейчас; если позже появится PgBouncer при переезде на постоянный Linux-хост — замена драйвера на `psycopg3` это правка connection-строки и зависимости, не переписывание бизнес-логики (SQLAlchemy абстрагирует диалект); (3) Alembic — очевидный выбор для миграций именно потому что живёт в одной экосистеме с SQLAlchemy, активно поддерживается, ничего «проще» не оправдано искать при 4-дневном сроке.

## 7. Многоязычность в боте

### Что даёт экосистема aiogram из коробки
[прочитано целиком: https://docs.aiogram.dev/en/latest/utils/i18n.html]
- Встроенный i18n-модуль aiogram построен на **GNU gettext** (плюс Babel) — стандартные `_()`/`__()` (ленивый вариант), компиляция `.po` → `.mo`, загрузка из `locales/<lang>/LC_MESSAGES/<domain>.mo`.
- Три готовых middleware для выбора языка: `SimpleI18nMiddleware` (язык берётся из объекта `User` Телеграма, то есть из настроек клиента пользователя), `ConstI18nMiddleware` (один язык на всех статично), `FSMI18nMiddleware` (язык хранится в FSM-сторадже — то есть выбор пользователя внутри бота, а не системная локаль устройства). Абстрактный `I18nMiddleware` можно расширять под кастомное хранение выбора языка (например, в Postgres, а не в FSM) — не описано детально в доке, но архитектурно предусмотрено.
- **Ограничение gettext**: f-строки нельзя использовать как переводимые строки напрямую — динамические переменные подставляются в уже переведённую строку после перевода (`.format()`/`%`-подстановка постфактум), это стандартное ограничение gettext-подхода, не специфика aiogram.
- Fluent (`.ftl`) в самой aiogram не упоминается — это территория стороннего пакета.

### Сторонний пакет aiogram_i18n
[прочитано целиком: https://aiogram-i18n.readthedocs.io/]
- Поддерживает три бэкенда: **GNU Gettext**, **Fluent Compile** (`fluent-compiler`), **Fluent Runtime** (`fluent.runtime`).
- Все три — **файловые** (`.po`/`.mo` или `.ftl`). **Хранение переводов в базе данных как отдельный бэкенд не задокументировано** — по факту нужен кастомный бэкенд (документация подтверждает расширяемость: "Writing own backends" как раздел, но без готового решения для БД).

### Ключевое архитектурное разделение для проекта (вывод из фактов выше, не готовое решение "из коробки")
Требование «переводы живут строками в базе, а не колонками» относится не к текстам интерфейса бота, а к **контентным данным** — формулировкам пунктов чек-листа, названиям зон и т.п. Для этих двух видов текста нужны разные механизмы:
1. **UI-строки бота** (кнопки, системные фразы, подсказки) — конечный, известный на старте набор, меняется редко. Для него подходит файловый подход aiogram — **gettext через встроенный `I18n` aiogram**, без стороннего пакета: не нужен Fluent для простых строк без сложной плюрализации/грамматики, а `.po`-файлы добавляются per-язык без правки кода (обещание "добавление языка = добавление файла" из проектных требований выполняется естественным путём gettext).
2. **Контентные данные чек-листа** (формулировки пунктов, названий зон, категорий нарушений) — эти данные уже требуют кода как первичного ключа согласно правилу проекта («Сущности связывать кодами, никогда формулировками» — `CLAUDE.md`), значит естественная модель — таблица `translations(entity_code, language, field, text)` в Postgres: одна запись на (код сущности, язык, поле), без per-language колонок на самих доменных таблицах. Библиотечного готового решения под это не нашлось (ни у aiogram, ни у aiogram_i18n) — это должно быть написано как простой слой доступа к Postgres поверх уже выбранного в п.6 SQLAlchemy, а не отдельная i18n-библиотека.

### Рекомендация под срок 4 дня
Не заводить `aiogram_i18n` ради простого набора строк интерфейса — хватит встроенного `I18n` aiogram + `SimpleI18nMiddleware`/`FSMI18nMiddleware` для UI. Контентные тексты чек-листа — отдельная простая таблица в Postgres `(entity_code, language, field) -> text` с фолбэком на английский, если перевод для языка ещё не заведён. Это разделение UI vs контент экономит время сейчас (не нужно оценивать Fluent против gettext для сложных случаев) и прямо соответствует требованию проекта хранить переводимый контент строками в базе, а не колонками.

## 8. Docker-образ Python на Windows-хосте — известные грабли

Все находки этого раздела — по вторичным источникам (блоги, GitHub issues, официальный блог Docker для одного пункта), первоисточник в виде официальной доки Docker Desktop открыт частично (см. ниже). Факты общеизвестны в экосистеме Docker Desktop for Windows и многократно подтверждены разными независимыми источниками, но помечаю честно — не читал прямо `docs.docker.com` целиком по каждому пункту.

- **Пути и bind-mount поверх `/mnt/c` (WSL2-бэкенд Docker Desktop):** если код лежит на Windows-диске и монтируется в контейнер через bind mount (`-v C:\project:/app`), под капотом это Plan9-шара `/mnt/c` — заметно медленнее нативного bind mount. Если репозиторий физически лежит внутри WSL2-дистрибутива (не на `C:\`), Docker использует нативный bind mount — быстрее на I/O-интенсивных операциях. [просмотрено: вторичные источники (augmentedmind.de, therealvan.com); есть официальный блог-пост Docker "WSL 2 Best practices" — не прочитан целиком в этой сессии, стоит свериться перед стройкой]
- **CRLF vs LF в скриптах:** если репозиторий клонирован на Windows через Git без настройки `.gitattributes`, shell-скрипты (например, entrypoint.sh) могут получить CRLF-концы строк — bash внутри Linux-контейнера не может их выполнить (`$'\r': command not found` и подобные ошибки). Лечится `.gitattributes` с явным `* text=auto eol=lf` для `*.sh`, либо `git config core.autocrlf false` на Windows-машине. Актуально для нашего проекта, если `entrypoint.sh`/скрипты сборки будут в репозитории.
- **UID/GID контейнера vs файлы на хосте:** Linux-контейнер по умолчанию пишет файлы как root (UID 0) или как фиксированный UID образа; при bind-mount с хоста могут вылезать permission-конфликты, особенно если контейнер и хост ожидают разные UID/GID. На Windows-хосте это менее актуально (нет unix-владельца файла на NTFS), но при последующем переезде на Linux-хост тот же docker-compose с bind-mount'ами уже может упереться в это — стоит с самого начала явно задавать `user:` в compose или писать данные в named volumes, а не в bind-mounted директории хоста, чтобы поведение не менялось между Windows и Linux хостами.
- **File-watching в примонтированных с хоста директориях не работает надёжно** (ограничение реализации CIFS/Plan9 в контейнерах на Docker for Windows) — если для разработки нужен hot-reload по изменению файлов на хосте, штатный `inotify` внутри контейнера может не увидеть событие. Для прод-контейнера бота это не критично (нет hot-reload в проде), но при локальной разработке на Windows-сервере через тот же docker-compose это может путать (файл поменяли — под контейнер не подхватил, показалось что "не работает").
- **Часовой пояс:** большинство минимальных Linux base-образов (в частности `python:3.x-slim` на Debian) уже включают `tzdata`, но правильный часовой пояс контейнера не выставляется автоматически — по умолчанию UTC. Нужно явно поставить `TZ=Europe/Belgrade` (или нужный пояс) через переменную окружения контейнера **и** пакет `tzdata` установлен (на Debian он есть в `python:slim` уже, но стоит проверить `docker run --rm python:3.12-slim date` перед стройкой). Для отчётов с датой/временем проверки это прямо влияет на корректность — несовпадение часового пояса контейнера и реального времени пиццерии/аудитора даёт неверный timestamp в PDF.
- **Шрифты в образе** — уже отмечено в п.5: `python:slim`/`python:alpine` не содержат кириллических шрифтов по умолчанию, для WeasyPrint нужно явно доставить `fonts-dejavu-core` или `fonts-noto` через `apt-get install`. На Alpine-базе (`python:3.x-alpine`) конфигурация шрифтов и таймзоны отличается от Debian (другой пакетный менеджер `apk`, другой механизм `tzdata`) — **рекомендация: использовать Debian-based `python:3.x-slim`, не Alpine**, чтобы не тратить время 4-дневного MVP на подгонку шрифтов/локалей под musl libc Alpine (известный источник трудноуловимых багов с WeasyPrint/Pango на Alpine — сборка Pango под musl менее протестирована, чем под glibc).

### Рекомендация под срок 4 дня
Base-образ — **`python:3.12-slim` (Debian)**, не Alpine. Репозиторий и весь код — не на `C:\`, а внутри WSL2-дистрибутива (если разработка идёт прямо на Windows-сервере через Docker Desktop) или просто в обычной файловой системе Linux-хоста при следующем переезде — тогда поведение bind-mount не меняется между площадками. `.gitattributes` с `eol=lf` для скриптов — сразу, до первого коммита entrypoint-скриптов. `TZ` — явная переменная окружения в docker-compose, не полагаться на дефолтный UTC. Эти меры дёшевы сейчас и снимают весь класс "работало на Windows, сломалось на Linux" при обещанном переезде.

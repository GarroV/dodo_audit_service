# Блок: bot

## Назначение

Весь разговор с аудитором: начать проверку, принять материал, показать предложение, зафиксировать подтверждённое, дать поправить, завершить и отдать отчёт.

## API-контракт

Наружу — только Telegram. Внутрь — вызовы `domain`, `recognize`, `report`.

Состояния диалога: `idle` → `starting` (пиццерия, вид, язык) → `working` (приём материала) → `confirming` (ждём подтверждения записи) → `finishing`.

Через `confirming` проходит не всякая запись: фиксация словами (T121, D064) подтверждения не ждёт — запись появляется сразу, разговор остаётся в `working`.

### Команды и кнопки

| Что | Как вызывается |
|---|---|
| Начать проверку | `/start`, дальше кнопки мастера |
| Разобрать кадр | кнопка «Разобрать» под принятым кадром (T067) |
| Записать пункт по словам | ничем: запись появляется сразу, без нажатия (T121, D064) |
| Отправить тот же материал модели | кнопка «Разобрать моделью» под такой записью (T117, T121) |
| Зафиксировать запись | кнопка с номером кандидата (T055) |
| Выбрать пункт вручную | кнопка «Выбрать пункт», страницами по 8 (T034) |
| Поправить запись | кнопки «Зона», «Класс», «Формулировка», «Удалить» под любой записью (T056) |
| Посмотреть, что уже записано | `/records`, она же в меню телеграма (T139) |
| Снять последнюю запись | `/undo` |
| Завершить проверку | `/finish`, дальше кнопки итога (T058) |

## Definition of Done блока

Пункты второй очереди (`recognize` не принят на момент первой) помечены отдельно.

**Первая очередь — T050, T051, T052, T053, T054, T059, T063**

- [x] Отвечает только Telegram ID из списка разрешённых; чужому не отвечает ничего осмысленного.
- [x] «Новая проверка» спрашивает пиццерию текстом (D051), вид и язык отчёта; проверяющий подставляется по Telegram ID, дата — сегодняшняя, руками не вводится (D032, T063).
- [x] Незавершённая проверка не перезаписывается молча: показывается, чья она и от какого числа, с выбором «Продолжить» или «Начать новую».
- [x] Комментарий связывается с фотографией тремя способами: подпись, сообщение следом, ответ на любое из ранее отправленных фото.
- [x] Альбом склеивается по `media_group_id` с окном 1–2 секунды в одну запись с несколькими фотографиями.
- [x] Пачка сообщений, пришедшая с задержкой после потери связи, обрабатывается без путаницы в привязке комментариев.
- [x] Прерванная проверка продолжается после перезапуска бота.

**Вторая очередь — T055-T058, T067, T068**

- [x] Предложения модели показываются кнопками; запись по ним появляется только после подтверждения. С фиксации словами подтверждение снято позже, решением D064 — см. пятую очередь.
- [x] Подтверждение — одна строка: пункт, класс, зона, накопленный процент. Без таблиц после каждого кадра.
- [x] Правки прямо в чате: удалить последнее, сменить зону, класс, переписать формулировку. Процент пересчитывается.
- [x] Замеры пишутся записями `D0` (`INF09`, `INF10`, `INF11`) среди находок; блок `info` не используется.
- [x] «Завершить» показывает итог и список зафиксированного, даёт поправить, затем отдаёт PDF файлом и письмо сообщением.
- [x] На кадр без комментария бот спрашивает «Разобрать?» кнопкой; без нажатия ни один кадр в модель не уходит (D043, D046).
- [x] Кадры, оставшиеся без записи, показываются при завершении проверки и не теряются молча (T068).

**Четвёртая очередь — T117**

- [x] Рядом с ответом видны слова аудитора **целиком** и сработавшая строка карты (`item.cue`).

**Шестая очередь — T123, T124, T126, T127, T128 (расхождения, найденные сверкой со спекой)**

- [x] Завершённая проверка уходит в историю сама: `push_inspection`, следом `upload_photos` теми же кадрами, что скачаны для отчёта (T123). Отказ базы отчёт не отменяет и молчанием не остаётся; незаданный `DATABASE_URL` — законная работа без базы и сбоем не выглядит.
- [x] Зона берётся из слов **текущего** комментария, а память подставляется только когда о зоне в них не сказано (T124). Названы две зоны — разбор не выбирает за человека. Зона из памяти в записи без подтверждения названа догадкой вслух.
- [x] Испорченное состояние не делает бота немым: у диспетчера есть глобальный обработчик, `/start` работает и на нечитаемом файле — это выход (T126). Аудитору уходит причина и что делать, разбор с путями — в журнал.
- [x] Отказ движка разбирается, а не пересказывается: пункт и зона названы по-человечески на языке интерфейса, занятая пара «пункт + зона» приводит к кнопкам занявшей записи (T127). Командной строки в чате нет.
- [x] Причина не называется наугад: «предложение устарело» больше не винит перезапуск, которого не было (T128).
- [x] Язык интерфейса и язык речи задаются из мастера, а не остаются умолчанием: выбор английского делает английским и разговор (T128).
- [x] Название точки длиннее замеренного предела не принимается на вводе, а не роняет сборку отчёта в конце проверки (T128).

**Седьмая очередь — T131 (язык интерфейса до начала проверки)**

- [x] Язык, которым бот говорит ДО начала проверки, — параметр развёртывания `BOT_UI_LANG`, а не константа в коде.
- [x] Демо-стенд поднимается английским целиком: приветствие, кнопка входа, вопросы мастера и надписи его кнопок. Проверено запуском демо-образа с окружением демо-профиля, а не чтением кода.
- [x] Боевой стенд не тронут: переменная не задана — русский, как с первого дня.
- [x] Неизвестный язык останавливает бота на старте (`BotConfigError`), молча русским не становится.
- [x] После начала проверки язык берётся из её собственного `ui_lang`, а переменная больше не спрашивается.
- [x] Вид проверки на кнопке — на языке интерфейса, а в шапке отчёта партнёру — на языке отчёта: два разных языка проекта, а не один.

**Восьмая очередь — T126 переоткрыта, T147, T151, T153**

- [x] Испорченное состояние не делает бота немым **ни на одной форме порчи**: пустой файл, обрезанный JSON, список вместо объекта, двоичный мусор, `findings` не список, нет прав на чтение, чужая структура JSON, каталог вместо файла — на всех восьми входах (`/start`, `/finish`, `/undo`, кадр, голос, текст, правка, сборка). `/start` на каждой из них даёт выход: повреждение названо вслух и под ним кнопка «Новая проверка».
- [x] Чужой JSON больше не выдаётся за незавершённую проверку, а каталог на месте файла — за непочатую: обе формы теряли содержимое молча при следующей «Новой проверке».
- [x] Последний рубеж отвечает, даже если язык чата не выбрался: у `on_unexpected_error` своя защита, потому что за ним обработчика нет.
- [x] Пометка «зона не из списка пункта» видна везде, где видна запись: при фиксации, после правки зоны и в списке перед сборкой отчёта. Правка — самый частый способ увести запись туда, где пункта нет, и раньше она об этом молчала.
- [x] Отказ сборки отчёта разбирается, а не пересказывается (тот же запрет, что в T127): ни удвоенного служебного префикса, ни абсолютных путей, ни инструкции ставить системные библиотеки. То же на входе в проверку — `start.failed` больше не отдаёт стек движка. Неудача письма получила свой текст: отчёт к этому моменту уже у аудитора.
- [x] Сданная проверка не называется незавершённой и не пугает стиранием: `/start` различает проверку в работе и проверку, по которой отчёт уже собран и отдан. Признака «завершена» у движка нет — бот опирается на то, что сделал сам, и хранит это в своих заметках.

**Снято требование** «фотография без комментария вызывает уточняющий вопрос и не фиксируется» — отменено решением D043 и заменено кнопкой «Разобрать?» (D046).

## Статус

`in_progress` — седьмая очередь готова и предъявлена к приёмке (T131, язык интерфейса до начала проверки). Первая (T050-T054, T059, T063), вторая (T055-T058, T067, T068), третья (T108), четвёртая (T117) и пятая (T121) приняты раньше; шестая (T123, T124, T126, T127, T128) предъявлена и ждёт приёмки.

**Седьмая очередь, T131 (задача #83, находка блока infra).** Язык интерфейса до начала проверки перестал быть константой: `DEFAULT_UI_LANG = "ru"` осталось умолчанием, но поверх него встал параметр развёртывания `BOT_UI_LANG` (`texts.default_ui_lang`). Боевой стенд переменную не задаёт и говорит по-русски, как и раньше; демо-профиль в `docker-compose.yml` ставит себе `en` и становится английским целиком. Неизвестное значение — отказ на старте (`config._parse_ui_lang` → `BotConfigError`), а не молчаливый откат: опечатка в переменной демо иначе обнаружилась бы на показе.

Правки приветствия оказалось мало, и это выяснилось на живом прогоне демо, а не по коду: надписи кнопок мастера (`Новая проверка`, `Продолжить`, `Начать новую`, три вида проверки) стояли строками прямо в `keyboards.py` — единственные строки интерфейса мимо каталога. Английский текст с русской кнопкой под ним — та же поломка, только незаметнее, поэтому они переехали в каталог, а клавиатуры мастера приняли язык параметром.

Вид проверки при этом развели по двум языкам: `KIND_LABELS` был одной строкой на два разных употребления — надпись на кнопке (язык интерфейса) и значение, уезжающее в шапку отчёта партнёру (язык отчёта). Теперь `KIND_TITLES` + `kind_title(code, lang)`, и на кнопке стоит «Planned», а в русском отчёте — «Плановая». Побочно исправилось предсуществующее расхождение: до T131 английский отчёт получал в шапку русскую «Плановую».

Проверено прогоном 04.09 в своей рабочей копии: `make fmt lint types dead bounds` зелёные целиком (`mypy --strict` на 77 файлах, `vulture`, `deptry`, `lint-imports` — 2 контракта из 2), полный `make test` с подключённым Postgres — **1315 тестов, 0 пропущено, покрытие 98 %**, 3 мин 16 с. Без базы в оболочке тот же набор даёт 1150 пройденных и 165 пропущенных (весь блок `db`), и общее покрытие тогда 94 % — цифра о базе, а не о правке. ### Решения, принятые внутри блока

**Язык стенда читается по месту, а не раздаётся аргументом через роутеры.**
`BOT_UI_LANG` разбирается в `texts.default_ui_lang()` и берётся оттуда же, где
раньше стояла константа. Альтернатива — протащить язык из `BotSettings` через
`build_dispatcher` в каждый роутер и в `chat_ui_lang(chat_id)` — выглядела
чище, но лгала бы: язык до начала проверки один на процесс, а параметр в пяти
подписях обещает, что он бывает разным у разных чатов одного бота. Проверка
значения при этом стоит не по месту чтения, а на старте (`load_bot_settings`):
до первого сообщения аудитору, а не вместо него.

**Умолчание осталось русским намеренно.** Соблазн был сделать умолчанием
английский — «продукт двуязычный, английский нейтральнее». Но боевой бот
говорит по-русски с T050, аудиторы на точке к этому привыкли, и смена языка
задним числом на молчащем стенде — ровно то молчаливое изменение поведения,
которого задача просила избежать. Английский включается одной строкой в
профиле, и демо это и делает.

**Демо ставит `en` в профиле, а не переменной `DEMO_BOT_UI_LANG` в `.env`.**
Остальные различия демо (токен, список ID, база) вынесены в `.env` под
префиксом `DEMO_`, потому что у них нет правильного значения — их знает только
запускающий. У языка демо правильное значение есть и оно одно: демо обязано
быть английским. Переменная в `.env` означала бы, что демо можно поднять
русским, забыв её заполнить, — и заметили бы это на показе.

**Вид проверки разведён по двум языкам, а не переведён на язык интерфейса.**
Одна строка `KIND_LABELS` служила и надписью кнопки, и значением, которое
уезжает в шапку отчёта партнёру. Перевести её «на язык интерфейса» значило бы
поставить в английский отчёт «Плановую» — что там до сих пор и стояло. Язык
отчёта известен на шаг позже кнопки, поэтому в состоянии мастера едет код, а
слово подставляется в самом конце, когда язык отчёта уже выбран.

**Названия языков на кнопке выбора не переводятся.** «Русский» остаётся
«Русским» и в английском интерфейсе демо: язык называют на нём самом — так
делают все, у кого есть переключатель языка, и так его находит глазами тот,
кому он нужен. Это единственная надпись мимо каталога текстов, и мимо она не
по недосмотру: перевода у неё нет по существу.

**Комментарий аудитора не попадает в отчёт партнёру.** Поле `comment` записи движок печатает в отчёте, а сказанное вслух на точке для партнёра не предназначено. В запись идёт только формулировка, собранная по правилам фиксации; сами слова аудитора остаются в переписке.

**Заметки бота лежат отдельным файлом, а не в `inspection.json`.** Список присланных кадров (T068) и последняя зона (D048) — сведения бота, а не проверки: в отчёт они не идут и партнёру не показываются. Класть их в поля движка значило бы либо засорить отчёт, либо завести вторую договорённость о формате состояния поверх чужого блока.

**Источник записи (D044) из заметок бота уехал — и это правильно.** Он казался сведением бота, пока читал его один бот. Как только источник понадобился в базе, стало видно: это свойство самой записи, а не переписки. Хранит его теперь блок `domain` внутри проверки (`add_finding(..., source=...)`, `Finding.source`), бот только называет источник при фиксации и читает при предвычитке. Второй копии в заметках нет намеренно: две копии одного факта расходятся, а спорили бы они о том, за какую формулировку отвечает аудитор. У проверок, начатых до переезда, источника в состоянии нет вовсе — такая запись читается как «неизвестно» и пометки не получает: выдать её за слова аудитора значило бы соврать, за догадку — оболгать.

**Что ждёт нажатия — только в памяти.** Предложения модели перезапуск не переживают намеренно: кнопка под ответом, которого больше никто не помнит, зафиксировала бы запись по устаревшему разбору. Нажатие на забытую кнопку — нормальный исход, бот отвечает «предложение устарело».

**Формулировка при ручном выборе без модели** берётся из комментария аудитора, а при его отсутствии — из вопроса пункта, и тут же правится кнопкой «Формулировка». Отдельный шаг «введите формулировку» на точке дороже: аудитор идёт с занятыми руками, а исправить он может сразу же и при завершении.

**Слова аудитора при фиксации словами не режутся предпросмотром.** Везде ещё комментарий сжимается до 160 знаков (`view.NOTE_PREVIEW_LIMIT`): аудитору нужна отметка, что бот услышал. Здесь ровно наоборот, и это главное в T117. Сверка отвечает по одной сработавшей строке карты, а второе нарушение фразы (правило 11) обычно стоит в конце — предпросмотр спрятал бы именно его, и потеря стала бы молчаливой. С T121 цена ещё выше: подтверждения нет, и своих слов рядом с записью аудитор больше нигде не увидит. Потолок всё же есть (`FAST_NOTE_LIMIT = 3000`), и причина у него одна: сообщение обязано влезть в лимит телеграма в 4096 знаков вместе с пунктом, строкой карты и подсказкой. Живым словам он не мешает — самая длинная формулировка боевых проверок 204 знака при медиане 124.

**Вопрос чек-листа при фиксации словами — на языке интерфейса, а не отчёта.** Ручной перечень (T034) берёт заголовки на языке отчёта намеренно: там заголовок пункта может стать текстом записи и уйти партнёру. Здесь стать текстом записи ему нечем — им всегда становятся слова аудитора, — поэтому заголовок остаётся чистой строкой интерфейса и слушается языка интерфейса.

**Граница D064 проходит по сверке со словами, а не по всему, что аудитор написал.** Решение снимает подтверждение с «фиксации словами» и оставляет его «для разбора кадра». Единственный путь, где запись целиком собрана человеком, — сверка со списком нарушений: зону назвал человек, строку карты он произнёс целиком, а текстом записи становятся его собственные слова. Разбор моделью, даже начатый с текста, устроен иначе: пункт и формулировку предлагает модель, кандидатов несколько, и нажатие там не подтверждение, а выбор — снять его было бы нечем. Поэтому изменился ровно один переход, а `classify`, ручной перечень и путь кадра остались как были.

**Формулировка пункта показывается при фиксации словами — вопреки «не пересказывать пункт».** Правило шага 5 `docs/06-mvp-bot.md` написано для записи, подтверждённой нажатием: пункт аудитор уже прочитал на кнопке. Без кнопки читать его негде, а строка `#1 CLN02 · D1 · Кассовая зона · 99,5 %` промах не показывает — код глазами не читается, формулировка читается. Так владелец риск и объяснял: «кассовая зона, просрочка чизкейк» напрашивается на `CLN02` («оборудование в зоне мойки без загрязнений») вместо верного `PRD10`, и разницу видно только по формулировке. Отступление одно и только здесь; таблицы после каждого кадра по-прежнему нет.

**«Разобрать моделью» переехало из предложения под саму запись — и это не оформление.** Правка записи (T056) меняет зону, класс, формулировку и удаляет запись, но **не код пункта**. Значит, промах по коду чинится только разбором заново, а те же слова снова поднимут тот же пункт: удаление и повтор дают петлю. Кнопка рядом с записью — единственный выход из неё. Запись при этом не трогается: разбор предлагает кандидатов, а прежнюю запись убирает аудитор кнопкой «Удалить». Удалять её молча было бы хуже — отказ модели оставил бы человека и без записи, и без разбора.

**Отказ движка при фиксации словами передаёт материал модели, а не заканчивается ничем.** Пара «пункт + зона» занимается по-настоящему часто: тот же пункт в той же зоне аудитор снимает дважды за обход. Раньше отказ приходил на нажатие, и рядом оставались кнопки; теперь нажатия нет, и молчаливый тупик был бы прямым следствием снятой кнопки. Причина названа строкой «Не записал: …», после чего материал идёт обычным разбором, где пункт можно выбрать другой.

**Предложение после фиксации словами не забирается из памяти.** Всюду ещё `take_proposal` вызывается сразу: запись сделана, второй раз по тем же кнопкам нельзя. Здесь предложение живёт дальше — ровно ради «Разобрать моделью» под записью. Опасных кнопок это не открывает: под записью показаны только правки и выход к модели, а нажатие на кандидата или ручной перечень из прошлого сообщения упирается в пустые списки и отвечает «предложение устарело».

**Кнопки «Не записывать» под записью нет.** Она была отказом от предложения, а отказываться больше не от чего: запись уже сделана, и её отменяет «Удалить» — та же кнопка, что у любой другой записи. Оставить обе значило бы дать два разных способа убрать одно и то же.

**`fast_path` вызывается через `asyncio.to_thread`, хотя ни сети, ни подпроцесса в нём нет.** Граница проходит не по «движок или не движок», а по цене: вызов читает с диска методику и карту кадров и стоит 2.3 мс на сработавшем комментарии против 0.046 мс у `get_state`, который в цикле оставлен. На двадцати аудиторах это та же растущая очередь, из-за которой в поток уехали вызовы движка (T101). Инвариант закреплён тем же тестом `tests/test_bot_event_loop.py`, и его смысл расширен с «дорогие вызовы домена» на «дорогие вызовы».

**На кадре без слов сверка не зовётся вовсе.** Формально она и так ответила бы отказом — сверять пустые слова не с чем. Но это был бы отказ ценой чтения двух файлов с диска на каждое нажатие «Разобрать» плюс строка в журнале о том, что аудитор ничего не говорил. Проверяется явно: тест считает вызовы, не подменяя саму сверку.

**Память о зоне — догадка, и в записи без подтверждения она названа вслух.** D048 разрешает подставлять последнюю названную зону, D064 снял подтверждение с фиксации словами — вместе это давало сообщение «записал по вашим словам» под записью, зона которой из слов не бралась вовсе. Врать тут дороже, чем шуметь: код пункта аудитор глазами не читает, а название зоны читает, и «Горячий цех» под словами «в зале» он заметит, только если сказать, откуда зона взялась. Поэтому в показе стоит оговорка, а не молчание, и стоит она ровно там, где подтверждения нет; на подтверждённой записи её нет — там зону аудитор прочитал на кнопке.

**Произносимые формы зон живут в коде, названия — в методике.** `data/zones.csv` правит управляющая компания, и переименованная зона обязана начать узнаваться сама, поэтому имена читаются оттуда на каждом обращении. Но «Зал ресторана / касса» вслух не произносят — говорят «в зале», и такой формы в методике нет и не появится. Список коротких форм в `src/bot/zones.py` намеренно крошечный, и источник у каждой строки только один из двух: слова владельца или формулировка боевой проверки в `examples/`. Слов «холодильник» и «морозильный шкаф» там нет специально — это оборудование, и в боевых проверках оно стоит в горячем цехе, а не в одноимённой камере.

**Отчёт не закрывает проверку.** Признака «завершена» у движка нет, и заводить его в боте — значит завести вторую правду о состоянии. После отчёта проверка остаётся открытой, и `/start` по-прежнему предложит продолжить или начать новую.

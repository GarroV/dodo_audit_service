# Блок: domain

## Назначение

Единственная точка доступа к предметной области: чек-лист, зоны, состояние проверки, вызов движка. Ни один другой блок не открывает `inspection.json` и не запускает `audit.py`.

## API-контракт

Всё перечисленное импортируется из `src.domain`. Обязательные параметры — как в техплане; всё, что добавлено сверх него, необязательно и имеет значение по умолчанию.

```python
check_environment() -> Settings                               # проверка окружения на старте продукта
settings_for(chat_id: int) -> Settings         # окружение с методикой ТОЙ проверки (T169)
# `chat_id` ниже необязателен и меняет ровно одно: читать издание методики, по
# которому идёт проверка этого чата, а не то, что лежит в каталоге сейчас.
# Без него — действующая методика, как и раньше: так читают там, где проверки
# ещё нет (справочники до её начала, инструменты методики, замеры)
list_items(zone: str | None = None, kind: str | None = None, *,
           chat_id: int | None = None) -> list[ChecklistItem]
list_zones(*, chat_id: int | None = None) -> list[Zone]
get_item(code: str, *, chat_id: int | None = None) -> ChecklistItem
allowed_levels(code: str, *, chat_id: int | None = None) -> list[str]
checklist_version() -> str                     # издание ДЕЙСТВУЮЩЕЙ методики
get_state(chat_id: int) -> Inspection | None
kind_title(code: str, lang: str) -> str        # вид проверки словами (T152)
INSPECTION_KINDS                               # код вида → слово на каждом языке
# `kind` ниже — КОД из этой таблицы (`planned`), а не формулировка: формулировки
# переводятся и правятся, коды нет. Слово на языке отчёта блок кладёт в шапку для
# движка сам, `Inspection.kind` отдаёт код. Неизвестный код и незаведённый язык —
# `ValidationError` до вызова движка, а не молчаливый возврат исходника
start_inspection(chat_id: int, unit: str, kind: str, report_lang: str, *,
                 ui_lang: str = "ru", speech_lang: str = "ru", date: str | None = None,
                 city: str = "", partner: str = "", contact: str = "", auditor: str = "",
                 tenant: str = "default") -> Inspection
add_finding(chat_id: int, code: str, level: str, zone: str, text: str, *,
            comment: str = "", source: str = "") -> Finding   # source: SOURCE_COMMENT | SOURCE_PHOTO
edit_finding(chat_id: int, n: int, **fields: str) -> Finding   # code, level, zone, text, comment
drop_finding(chat_id: int, n: int) -> None
attach_photo(chat_id: int, n: int, file_id: str) -> None
score(chat_id: int) -> Score
sync_checklist_version(chat_id: int) -> Inspection   # перевести проверку на действующую методику
drop_inspection(chat_id: int) -> bool                # убрать проверку ЧАТА (T201, D080)
```

`drop_inspection` убирает только копию проверки в чате — файл состояния. Отданный отчёт и
строка проверки в истории точки остаются: запечатанное не правится и не удаляется, а
доступа к истории у этого блока нет вовсе. Зовётся ботом на «Убрать из чата», когда сданная
проверка мешает начать следующую (решение владельца D080). `False` — убирать было нечего, и
это законный исход, а не отказ: аудитор нажимает кнопку и второй раз.

Типы (`src/domain/models.py`):

| Тип | Поля | Формулировки |
|---|---|---|
| `ChecklistItem` | `code`, `kind`, `levels`, `zones`, `days` | `process(lang)`, `question(lang)`, `applies_to(zone)` |
| `Zone` | `code`, `title_ru`, `title_en`, `share_pct` | `title(lang)` |
| `Finding` | `n`, `code`, `level`, `zone`, `text`, `comment`, `photos`, `zone_unusual`, `source` | — |
| `Inspection` | `chat_id`, `unit`, `kind`, `date`, `ui_lang`, `speech_lang`, `report_lang`, `checklist_version`, `tenant`, `city`, `partner`, `contact`, `auditor`, `findings` | `finding(n)` |
| `Score` | `pct`, `grade`, `counts`, `deductions`, `by_zone` | `label(lang)` |
| `ZoneScore` | `code`, `share`, `counts`, `loss`, `left`, `zeroed` | `name(lang)` |

**Язык — параметр, поэтому формулировки отдаются методом с языком, а не полем.** Неизвестный язык — отказ, а не молчаливый откат на русский: иначе партнёр получит отчёт, в котором часть текста внезапно не на его языке, и заметит это только он.

`Score` строится разбором вывода `audit.py score --json`. Собственного расчёта в блоке нет и быть не может — это проверяется контрактом `engine-not-imported` в `lint-imports`.

Данные читаются из каталога `AUDIT_DATA_DIR`. Переменная не задана или каталог неполный — падение на старте с внятным сообщением.

## Что нужно знать потребителям блока

- **Отказы.** `ConfigError` — окружение непригодно, продукт не должен подниматься. `ValidationError` — значение отвергнуто до вызова движка. `InspectionNotStarted` — в чате нет начатой проверки (бот предлагает начать). `EngineError` — отказ движка, `message` дословно от него. `ChecklistVersionMismatch` — проверку считают не по той методике, которой она помечена (`recorded`, `current`); бот спрашивает аудитора, а не решает сам.
- **Проверка идёт по тому изданию методики, при котором её начали (T169).** Издание снимается снимком на старте (`STATE_DIR/methodology/<издание>/`), и по нему идёт всё: запись, правка, подсчёт, сборка отчёта. Публикация версии (D049) переставляет каталог `AUDIT_DATA_DIR` под живой проверкой — для идущей проверки это перестало быть событием, а следующая начинается уже на новом издании. Отказа на записи нет и быть не может: аудитор стоит на точке, починить методику оттуда он не в силах, а выезд не переигрывается.
- **Смесь изданий стоит не отказа, а испорченного отчёта, и поэтому закрыта на записи, а не на подсчёте.** Запись по пункту, снятому переизданием, движок не отвергает: `compute` берёт `cl.get(qid, {})` — и партнёру уходит строка с пустой формулировкой и сроком «немедленно» вместо настоящего. Воспроизведено (см. «Проверено фактически»).
- **Чтобы читать методику ТОЙ проверки, назовите чат:** `list_items(chat_id=…)`, `get_item(code, chat_id=…)`, `allowed_levels(code, chat_id=…)`, `list_zones(chat_id=…)`. Без этого аудитору можно предложить пункт, которого в его издании нет, — и запись по нему движок не примет. Кто зовёт движок сам (сборка отчёта), берёт окружение через `settings_for(chat_id)`.
- **`score` считает только по той методике, которой проверка помечена (T148).** Снимка нет и издание другое — `ChecklistVersionMismatch`, а не тихий пересчёт: оценка по новой методике под старой отметкой уезжает в базу выглядящей сравнимой с соседними, не будучи ею. Без снимка остаются проверки, заведённые до T169, и те, чья полка снимков не пережила переезд. Пустая отметка расхождением не считается — так помечены проверки, заведённые до версионирования.
- **Выход из расхождения один и он явный — `sync_checklist_version`.** Переводит проверку на действующую методику (снимая заодно её снимок) и оставляет след в ней самой (`domain.version_history`: `from`, `to`, `at`) плюс строку в журнал процесса. Отдельным вызовом, а не поведением подсчёта: перевод меняет то, чем проверка измеряется, и это решение человека. Спросить обязан бот — задача блоку `bot`.
- **Текст отказов движка написан для командной строки.** Дубль пары советует «`audit.py photo 1 --add ...`». Аудитору такое показывать нельзя — переформулировать при показе обязан бот (задачи T055, T056).
- **`counts` содержит и `D0`** — информационные записи (замеры, настройки печи, фото продукта). Они не влияют на процент, но в отчёте нужны. Перечня классов в коде блока нет: список приходит от движка.
- **`source`** — откуда взялась запись (решение D044): `SOURCE_COMMENT` — со слов аудитора, `SOURCE_PHOTO` — распознано по кадру, пусто — источник не записан (проверки, заведённые до D044; выдавать их за слова аудитора нельзя). Ставится при фиксации и правкой не меняется: `edit_finding(source=…)` — отказ. В поля движка, которые печатаются партнёру, источник не попадает.
- **`zone_unusual`** — зона не из списка пункта. Движок такую запись пропускает и лишь помечает; бот показывает пометку аудитору.
- **Служебные пункты (`kind` = `aggregate`, `info`) блок не прячет.** Отсеивать их — работа разбора (`docs/03-recording-rules.md`, правило 8).
- **`start_inspection` не защищает от перезаписи начатой проверки** — движок затирает состояние целиком и молча. Спросить «продолжить или начать заново» обязан бот (задача T052).
- **Формулировка, начинающаяся с дефиса, доезжает целой:** движку всё передаётся видом `--ключ=значение`.
- **Идентификатор кадра с запятой отклоняется**: движок режет список фотографий по запятой, и один кадр молча превратился бы в два несуществующих.

## Где что лежит

- **Состояние** — `STATE_DIR/chat_<chat_id>/inspection.json`, папка на чат (решение D007). Рядом движок оставляет `inspection.json.lock`.
- **Поля, которых у движка нет**, — в том же файле под ключом `domain`: `schema`, `chat_id`, `tenant`, `checklist_version`, `ui_lang`, `speech_lang`, `sources` (номер записи → источник). Записываются под той же блокировкой, что берёт движок. Проверка должна быть одним объектом: при переезде на базу иначе теряется половина её сведений.
- **Язык отчёта — в шапке движка (`meta.lang`)**, потому что оттуда его берёт сборка отчёта. Второй копии у блока нет намеренно: две копии разошлись бы.
- **Снимки изданий методики** — `STATE_DIR/methodology/<издание>/`: копия файлов методики плюс `checklist_version.txt`. Каталог назван изданием, а издание выведено из содержимого (D050), поэтому две проверки на одном издании делят один снимок, а подложенный каталог не сходится отпечатком и в дело не идёт. Старые снимки не удаляются: по ним считаются идущие проверки, а после них — объяснимость отчёта (D050). Размер снимка — размер методики (боевая на 05.09.2026 — 192 КБ).
- **След перевода версии** — `domain.version_history` в том же файле: список записей `{from, to, at}`. В проверке, а не в логах стенда: отвечать «по какой методике это посчитали» придётся тогда, когда логов уже не будет, а проверка будет — она к тому времени уедет в базу целиком.
- **Версия методики** — составной идентификатор `имя-дата-отпечаток` (`imf-2026-09-01-3f5a91b2c7d0`, решение D050). Имя и дату управляющая компания кладёт в `checklist_version.txt` строкой «имя набора плюс дата»; отпечаток — 12 знаков sha256 по всем файлам методики, включая маршрут обхода. Файла нет — версия остаётся одним отпечатком (`local-…`). Файл есть, но не разбирается — отказ на старте: молчаливый откат на `local-…` потерял бы дату издания навсегда.
- **Порядок обхода** — `route.csv` в каталоге методики (`entity,code,order`), файл необязательный. Отдельным файлом, а не колонкой в `checklist.csv` и `zones.csv`, потому что `engine/manage.py` перезаписывает оба фиксированным списком колонок и стёр бы маршрут молча.
- **Движку передаются две переменные**: `INSPECTION_FILE` — путь к состоянию, `CHECKLIST_DIR` — каталог методики. Вторая обязательна: без неё движок берёт данные из своей копии рядом со скриптом или из форка `checklist_data/` в рабочей папке.

## Зависимости

`engine-fix`.

## Definition of Done блока

- [x] Чек-лист, зоны и допустимые классы читаются из `AUDIT_DATA_DIR`; отсутствие каталога — падение на старте, а не пустой чек-лист.
- [x] Состояние хранится в папке на чат, запись атомарна, одновременная запись двух кадров альбома не теряет запись и не портит файл (тест обязателен).
- [x] `add_finding` отклоняет дубль пары «код + зона» и класс, не разрешённый для этого пункта.
- [x] `score` возвращает то же, что печатает `audit.py score`, — сверено тестом на данных `examples/`.
- [x] Наличие форка `checklist_data/` в рабочем каталоге обнаруживается и приводит к отказу запуска.
- [x] Три языковых поля (интерфейс, речь аудитора, отчёт) хранятся раздельно; версия чек-листа записана в проверку.
- [x] `mypy --strict` чист, `lint-imports` зелёный.
- [x] Версия методики составная (имя, дата, отпечаток): правка данных под прежним именем даёт другой идентификатор, а проверки, заведённые до этого, читаются по-прежнему.
- [x] Порядок обхода задаётся данными и применяется к зонам и пунктам; методика без файла маршрута работает как раньше.
- [x] Проверка не может собраться из двух изданий методики: издание снимается на старте, запись и подсчёт идут по нему, переиздание посреди выезда не отказывает аудитору и не двигает цифру (T169).
- [x] У записи хранится источник — со слов аудитора или распознавание по кадру; источник живёт в самой проверке и доезжает до базы (проверено сливом в Postgres).

## Проверено фактически

- **Набор идёт БЕЗ боевых данных вообще** (T141): симлинки `data` и `examples` убраны из рабочей копии, полный прогон — **1204 passed, 195 skipped, 0 failed**. Пропускается ровно то, что боевых данных требует по существу; всё остальное идёт. До правки на такой машине молча пропускалась бы половина набора, и итог был бы зелёным.
- **Изоляция от боевой методики доказана подменой** (T141): каталог `data/` в рабочей копии переставлен на изменённую копию — новый пункт `CLN99` с критериями, новая строка карты кадров, переименованная зона `hot_kitchen`, изданная версия `imf 2026-09-05`. Полный прогон: **1175 passed, 0 failed**. Встречная проверка на том же подменённом каталоге: ставка `D1` поднята с 0.5 до 1.0 — боевой якорь покраснел (4 теста, включая `test_боевой_якорь_не_сдвинулся` и оба параметра `test_боевая_проверка_считается_как_прежде`), то есть связь с боевыми данными там, где она нужна, не перерезана. Симлинк возвращён, `data/` и `examples/` сверены по md5 до и после — 46 файлов не изменились. **Сверять надо и симлинки, а не только файлы**: обход `find -type f` их не видит, а внутри боевых каталогов заводится самоссылающийся мусор (`examples/examples`, до того такой же в `data/`) — его роняет `ln -s .../examples examples`, выполненный там, где `examples` уже каталог. Оба раза это след разведения рабочих копий, а не данные; диспетчер их убрал. Именно сверка по симлинкам показала, что один из них исчез между началом и концом работы, — по файлам это было бы незаметно.
- **Отказ считать по чужой методике** (T148) воспроизведён и на самодельной правке каталога, и на настоящем хранилище версий: `apply_change` + `publish_checklist_version` под живой проверкой → `local-b9e1adbc238e` в проверке против `smoke-2026-09-04-d2b012b6715e` на диске → отказ; после `sync_checklist_version` подсчёт идёт, а в проверке остаётся след `{from, to, at}`.

- **Дефект T169 воспроизведён до починки и не воспроизводится после** (05.09.2026). Опыт на копии синтетической методики: проверка начата, записан пункт, методика переиздана (пункт снят, вместо него заведён другой) — и запись по пункту НОВОГО издания легла в проверку без единого возражения. Дальше по T148 отказывал подсчёт, а разрешённый выход (`sync_checklist_version`) выдавал письмо партнёру, в котором у записи по снятому пункту стояла ПУСТАЯ формулировка процесса и срок «Устранить до: немедленно» вместо настоящих десяти дней. После починки тот же опыт: аудитору по-прежнему предлагается его пункт (а пункт нового издания — нет), запись принимается, подсчёт идёт без отказа, а в отчёте стоит формулировка процесса и срок «Устранить до: 15.09.2026».
- **Смоук на БОЕВОЙ методике** (её копия, временный `STATE_DIR`; исходный каталог сверен по md5 до и после — 6 файлов не изменились): старт проверки за 35–58 мс, снимок издания 183 872 байта; оценка 99.5 % A; переиздание посреди работы (снят пункт, ставка утроена) — письмо по той же проверке осталось байт в байт прежним; после переиздания прошли запись, правка и подсчёт (97.5 % B), тогда как **та же проверка по действующей методике дала бы 96.5 %** — этот 1 п.п. и есть то, что держит снимок. Следующая проверка началась уже на новом издании, на полке стало два снимка.
- **Цена снимка измерена, а не прикинута** (боевая методика, 192 КБ): первый снимок издания — 1,6 мс, повторный вызов при готовом снимке — 0,24 мс, подстановка каталога издания на один вызов движка — 0,13 мс при полном `score` в 26 мс (0,5 %). | Снимок издания методики — рядом с состоянием (`STATE_DIR/methodology/<издание>/`), а не в хранилище версий MCP | Хранилище (D049) для того и построено, но продукту оно недоступно: каталог методики смонтирован `:ro`, `MCP_CHECKLIST_STORE` в контейнере бота не смонтирован вовсе и по умолчанию пуст. Решение, опирающееся на него, закрывало бы дефект только в настройке, которой на стенде нет. Каталог состояния — записываемый том, переживающий пересоздание контейнера (D004), то есть ровно там же, где живут сами проверки. Полнота снимка отдельно не проверяется намеренно — пропавший файл в отпечаток не входит, и такой каталог отвергается тем же сравнением |

| Язык отчёта не дублируется в блоке `domain` | Его читает сборка отчёта из шапки движка. Одна копия — один источник правды |

Иначе проверку пришлось бы глушить списком исключений на весь контракт, и она перестала бы что-либо ловить. В таком виде она сразу нашла настоящий мёртвый код (`Finding.is_violation`), и он удалён |

## Что осталось соседним блокам

- **Боевая методика всё ещё цитируется в доке и в докстроках продукта.** Больше всего — `docs/02-domain.md` (там названия зон стоят по построению), плюс `docs/06-mvp-bot.md`, `docs/forge/blocks/bot.md` и докстроки `src/bot/zones.py` (три названия зон как пример) и `src/recognize/fastpath.py`/`cues.py` (строка карты «Печь | CLN05 | TEH05», словари слов про грязь и поломку). Канал тестов закрыт, этот — нет: он не чинится технически, это вопрос видимости репозитория к владельцу (так и записано в T146).
- **Расхождение версий надо показать аудитору и спросить.** `score` отдаёт `ChecklistVersionMismatch` с полями `recorded` и `current`; бот показывает человеческий текст и предлагает выбор: перевести проверку на действующую методику (`sync_checklist_version`) или разбираться с методикой. Сам блок за аудитора не решает. Задачи у блока `bot` под это пока нет.
- **Записи, добавленные после переиздания методики, сверкой не ловятся.** `add_finding` идёт через движок и проверяется уже новой методикой, а отметка в проверке остаётся прежней до подсчёта. Сверку на записи блок намеренно не ставил (см. решения), но это значит, что проверка через версию может оказаться смесью. Полностью закрывается только подсчётом по снимку версии из хранилища `mcp` — это уже вопрос архитектуры, а не правки блока.

- **Тексты отказов движка не годятся для показа аудитору** (`audit.py photo 1 --add ...`). Переформулировать — блоку `bot`, задачи T055 и T056.
- **`audit.py init` затирает начатую проверку молча.** Защита — на боте, задача T052.
- **Источник записи бот пока пишет себе, а не в проверку.** `src/bot/routers/record.py` зовёт `sidecar.remember_source(...)` после `domain.add_finding(...)`; теперь источник передаётся параметром — `add_finding(..., source=sidecar.SOURCE_PHOTO)`, а показ берёт его из `finding.source` вместо `notes.sources`. Пока этого нет, в базу уезжает пустой источник. Значения `SOURCE_COMMENT`/`SOURCE_PHOTO` совпадают дословно, поэтому переход — замена вызовов, а не данных.
- **В базу от записи без источника приходит пустая строка, а не `NULL`.** `db.push` кладёт `finding.source` как есть; если колонке нужен `NULL`, это одно слово в `push.py` (`or None`) — правка блока `db`.
- **`--lang en` даёт смешанный отчёт** (текст находки, пиццерия и аудитор остаются как введены). Ограничение движка, здесь не лечится: состояние не хранит две языковые версии текста находки.

# Блок: report

## Назначение

Собрать PDF-отчёт и текст письма партнёру так, чтобы это можно было отправить не редактируя.

## API-контракт

```python
build_pdf(chat_id: int, *,
          fetch_photo: Callable[[str], Path | str | None] | None = None,
          allow_missing_photos: bool = False) -> Path   # исключение, если файл не создан
build_letter(chat_id: int) -> str                       # шаблон по наличию D2/D3
```

Вызов из `docs/forge/plan.md` — `build_pdf(chat_id)` — работает как объявлен;
оба именованных параметра добавлены к нему, а не вместо него.

`fetch_photo` — как достать файл кадра по идентификатору телеграма (T043).
Скачивает бот: токен есть только у него, и слоем ниже его нет. Без резолвера
ссылка читается как путь — так движок запускают руками.

`allow_missing_photos` — собрать отчёт, даже если кадр потерян. По умолчанию
потеря отменяет сборку: `PhotoMissing` с полем `misses` — списком пар «номер
записи, ссылка», чтобы бот назвал аудитору записи. Разрешение оставлено
аудитору: он уже уехал с точки и переснять не может, а на месте кадра встанет
видимая отметка «Фотография не приложена».

## Зависимости

`domain`, `engine-fix`.

## Definition of Done блока

- [x] PDF собирается WeasyPrint внутри образа, без обращения к рендерерам на хосте.
- [x] Кириллица отрисована: шрифт лежит в образе, путь указан явно.
- [x] Нумерация страниц есть.
- [x] Вид отчёта сверен глазами с эталонами из `examples/` на тех же данных; расхождения устранены правкой CSS.
- [x] Отсутствующая фотография заметна: сборка сообщает о промахе, а не вставляет пустоту.
- [x] Провал сборки поднимает исключение (`sys.exit` движка → ненулевой код → `ReportError`/`PdfNotBuilt` в блоке); показ ошибки аудитору — на боте (T058), здесь готов только честный отказ.
- [x] Письмо для чистой проверки и письмо с нарушениями — два разных шаблона.
- [x] Имя файла остаётся прежним: `Аудит <пиццерия> - <аудитор> - <дд.мм.гггг>.pdf`.

## Как устроен блок

Наружу торчат две функции (`src/report/__init__.py`), остальное — внутренности:

| Файл | Что в нём |
|---|---|
| `src/report/build.py` | `build_pdf`, `build_letter` и проверка наблюдаемого результата |
| `src/report/engine.py` | вызов `engine/report.py` подпроцессом, окружение и рабочий каталог |
| `src/report/photos.py` | ссылка на кадр → файл: карта для движка и список потерь |
| `src/report/errors.py` | `ReportError`, `PdfNotBuilt`, `PhotoMissing` |

Разметки отчёта, выбора шаблона письма и расчёта оценки в блоке нет: всё это
делает движок, блок его зовёт. Состояние проверки блок сам не открывает — пути
и записи берёт у `domain`.

**Кадры резолвит блок, а не движок.** Движку уходит готовая карта
«ссылка → абсолютный путь» (`report.py pdf --photo-map`), всегда, даже пустая.
Идентификатор телеграма путём не является, поэтому при заданной карте движок
резолвит только по ней и ничего не ищет на диске сам. Правило «где лежит кадр»
живёт в одном месте, а промах ловится на сборке — единственном моменте, когда
ссылка вообще может быть проверена.

Отчёт кладётся в папку проверки (`STATE_DIR/chat_<id>/`) под именем, которое
даёт движок. Имя в блоке не повторяется намеренно: две копии правила разъехались
бы при первой же правке.

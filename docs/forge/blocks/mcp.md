# Блок: mcp

## Назначение

Дать возможность работать через Claude с двумя вещами: с накопленными проверками (спросить историю точки, найти повторяющиеся нарушения, собрать сводку по сети) и с самой методикой — чек-листом, по которому эти проверки считаются (D049). Делается по образцу работающего `swarm-mcp` — JSON-RPC по HTTP, личный токен, тот же мост stdio↔HTTP (D055).

Проверки — только на чтение. Методика — чтение и правка, и это единственное место, где блок перестаёт быть только чтением; включается оно отдельной настройкой и по умолчанию выключено целиком.

## API-контракт

Двадцать один инструмент: шесть о проверках и пятнадцать о методике. **Ни у одного из них нет аргумента `tenant`:** код арендатора приходит из личного токена (см. «Откуда берётся арендатор»). У инструментов методики нет и аргумента `store`: хранилище версий подставляет точка входа.

### Проверки — только чтение

```
list_inspections(unit?, date_from?, date_to?, limit?)   # проверки с фильтрами
unit_history(unit, limit?)                              # ряд записанных оценок точки
network_summary(date_from?, date_to?)                   # сводка по сети
get_inspection(id)                                      # одна проверка целиком с находками
findings_by_unit(unit, limit?)                          # записанные находки одной точки
inspection_letter(id, lang?)                            # письмо партнёру по записанной проверке
```

Инструмента, пишущего проверку или находку, нет и не будет: проверку заводит и завершает аудитор через бота, а в базу её кладёт слив (T093). Запись проверки через агента означала бы запись в отчёт партнёру мимо человека. Держится это не обещанием: `tests/test_mcp_server.py` требует, чтобы у всего, что не объявлено методикой, обработчик лежал в модуле чтения проверок.

### Методика — чтение версий и правка (T098, D049)

```
checklist_versions()                                    # какие версии есть, какая действует
checklist_items(version?, process?)                     # пункты версии и её зоны, без критериев
checklist_item(code, version?)                          # один пункт вместе с критериями D1/D2/D3
add_checklist_item(process, question_ru, levels, code?, process_en?, question_en?,
                   zones?, days?, criteria?, kind?, version_name?, note?)
edit_checklist_item(code, ...то же, кроме kind...)      # меняются только названные поля
remove_checklist_item(code, hard?, version_name?, note?)
restore_checklist_item(code, version_name?, note?)
add_zone(code, name_ru, name_en?, share?, equal_shares?, version_name?, note?)
remove_zone(code, keep_shares?, equal_shares?, version_name?, note?)
publish_checklist_version(version)                      # сделать версию той, что читает движок

photo_cues(version?)                                    # карта слов версии: разделы и строки
photo_cue_suggestions(date_from?, date_to?, min_confidence?, limit?, version?)
                                                        # где модель промахнулась и что предложить УК
add_photo_cue(section, phrase, codes, version_name?, note?)
edit_photo_cue(phrase, codes?, new_phrase?, version_name?, note?)
remove_photo_cue(phrase, version_name?, note?)
```

Девять правящих инструментов не меняют действующую методику: каждый кладёт рядом новую версию. Публикация — отдельный вызов, названный своим именем.

### Форма ответа

Ответ инструмента — JSON внутри текстового блока MCP. Ключи английские, как имена полей в `db.InspectionRow`: это машинная поверхность, её читает агент и пересказывает человеку на его языке сам. Отдельного слоя переводов у неё нет намеренно — переводить машинные ключи означало бы, что имя поля меняется от языка спрашивающего.

У каждой выдачи есть `status`, написанный словами: «ничего не найдено» отличимо от «не смогли прочитать», а `truncated` говорит, что чтение упёрлось в предел и за ответом остались ещё проверки.

`chat_id` наружу не отдаётся: это чат аудитора в телеграме, личный идентификатор, ни для одного вопроса агенту не нужный.

**Абсолютных путей в ответе нет ни в успешной выдаче, ни в отказе** (T120). Ответ уходит в модель, то есть за пределы машины, а по пути читается устройство каталогов деплоя и имя пользователя, под которым поднят сервер. Причина отказа при этом остаётся: она называет переменную окружения (`AUDIT_DATA_DIR`, `MCP_CHECKLIST_STORE`) и то, что с ней не так, — а сам путь печатается в лог процесса, который остаётся на машине.

## Зависимости

`db`.

## Откуда берётся арендатор

**Из токена, и ниоткуда больше.** Связка задаётся человеком в `.env`:

```
MCP_TOKENS=партнёр-а=<токен>,партнёр-б=<другой токен>
```

Разбирается один раз на старте; дальше запрос приносит токен в заголовке `Authorization`, сервер переводит его в код арендатора и передаёт инструментам сам. Аргументом вызова арендатор быть не может: аргумент назвал бы кто угодно, а слой чтения обязан фильтровать по арендатору, а не угадывать, откуда тот взялся (T110). Аргумент `tenant`, подсунутый в вызов, получает явный отказ, а не тихо отбрасывается: тихо отброшенный, он выглядел бы работающей защитой ровно до того дня, когда его добавят в разбор «для гибкости».

Из этого же следует остальное:

- один токен, названный дважды у разных арендаторов, — отказ на старте: иначе вопрос «чью историю открывает этот токен» решался бы порядком строк в файле;
- несколько токенов одного арендатора — законно: по человеку на токен, отзывается по одному;
- токен короче 24 знаков — отказ: перебор по локальной петле ничем не ограничен;
- токены не попадают ни в `repr` настроек (он уезжает в трейсбек, а трейсбек в лог), ни в текст отказа, ни в лог сервера;
- сверка идёт `secrets.compare_digest` и без досрочного выхода из перебора — обычное сравнение строк подбирается по времени ответа посимвольно;
- отказ не называет ни предъявленный токен, ни живых арендаторов: перечислять по нему партнёров не должен никто.

## Куда пишется правка методики и почему туда

**В файлы, рядом с боевой методикой, версиями.** Не в базу и не поверх действующего набора. Решение принято блоком, и вот из чего оно следует.

Оценку считает только движок, а движок читает **файлы** — каталог из `AUDIT_DATA_DIR` (`CHECKLIST_DIR` для самого движка). Методика, положенная в базу, оценкой бы не стала: её пришлось бы выгружать в те же файлы, и файлы остались бы источником истины, а база — второй копией, которая с ними разъезжается. Отпечаток версии по D050 тоже считается по байтам файлов методики. Поэтому источник истины остаётся один — файлы.

Устройство хранилища (`MCP_CHECKLIST_STORE`):

```
<хранилище>/versions/<версия>/   полный снимок методики: чек-лист, зоны, ставки, критерии, маршрут
<хранилище>/current              символическая ссылка на действующую версию
<хранилище>/journal.jsonl        журнал: кто, что, когда и чем кончилось
```

Порядок правки: снимок нужной версии → правка копии → проверка движком → въезд новой версии в хранилище переименованием. Боевой каталог не открывается на запись ни на одном шаге — это проверяется побайтовым сравнением до и после (`tests/test_mcp_checklist_store.py`).

**Правит методику движок, а не этот блок.** `engine/manage.py` вызывается подпроцессом с `CHECKLIST_DIR`, указывающим на копию. Иначе пришлось бы повторить здесь правила, которые в движок попали через боль: сохранение колонок управляющей компании при перезаписи файла (T109), запрет молча раздать доли зон (T112), отказ на неизвестный код зоны, отказ на дубль кода и нечисловой срок (T106). Повторённые, они разошлись бы с движком при первой же правке одного файла без другого. Контракт `lint-imports` запрещает `src.mcp` импортировать `engine`; подпроцесс — тот же приём, которым движок зовёт блок `domain`.

**Проверка идёт до записи, и она настоящая.** Кандидат принимается, только если `manage.py validate` не нашёл проблем (он показывает их все разом, а не падает на первой) И `audit.py init` + `score` посчитали по этой методике оценку. Второй шаг нужен: `validate` не читает ставки вычетов вовсе, а без них движок не посчитает ничего. Отказ приходит вызывающему **словами движка** — пересказ разошёлся бы с ними.

**Идентификатор версии — тот же, что штампуется в проверку.** Считает его `domain.version.compose`, тот самый код, который кладёт `checklist_version` в каждую слитую проверку. Второй экземпляр этой формулы означал бы, что проверка ссылается на версию, которой в хранилище нет. Проверено запуском: после публикации `domain.checklist_version()` возвращает ровно имя каталога опубликованной версии.

**Публикация — перестановка указателя, а не перезапись методики.** `current` — символическая ссылка, и меняется она одним `os.replace`: движок не может застать методику наполовину переписанной. Отсюда же обратимость: откат — это публикация прежней версии, а не восстановление из копии. Старые версии не удаляются никогда (D050), поэтому откатиться есть на что.

**Публикация, которой движок не увидит, — отказ.** Чтобы она работала, `AUDIT_DATA_DIR` должен указывать на сам `<хранилище>/current`. Пока он смотрит в обычный каталог методики, версии заводятся и проверяются, а публикация отказывает и объясняет, что поменять. Молчаливое «опубликовано» при движке, читающем другой каталог, — худший из возможных исходов: агент говорит человеку, что методика изменена, а отчёты продолжают считаться по прежней.

### Кому методика открыта

Методика **одна на всю сеть** — это документ управляющей компании, а не данные арендатора. Поэтому доступ к ней не выводится из токена партнёра: он задаётся отдельно, `MCP_CHECKLIST_TENANTS`, и по умолчанию не открыт никому. Заслон стоит на входе, рядом с границей арендаторов (`server._checklist_for` → `rpc.handle`): обработчики права не спрашивают вовсе, и обработчик, забывший спросить, дырой стать не может.

Названная наполовину настройка — отказ на старте, а не молчаливо выключенный доступ, и арендатор из списка обязан существовать среди токенов: опечатка в коде означала бы доступ, выданный никому, и выглядела бы как работающая настройка.

Перечень инструментов при этом один для всех: инструменты методики видны и тому, кому она не открыта, и получают внятный отказ при вызове. Перечень, зависящий от прав, сказал бы агенту «такого инструмента нет», и человек пошёл бы искать причину в коде вместо `.env`.

### Карта слов правится тем же ходом, но не движком (T144)

`photo-cues.md` — документ управляющей компании, по которому быстрый путь
(T113) решает, что записать **без подтверждения аудитора**. До T144 у неё не
было ни инструмента правки, ни отката: править было нечем, а вернуть прежнее
можно было только копией файла вне git.

Хранилище её уже видело: карта входит в отпечаток версии (`DATA_FILES`, с
04.09.2026), то есть её правка и так даёт новую версию. Поэтому ход правки
общий с чек-листом — он вынесен в `checklist.apply_edit`: снимок версии →
правка копии → проверка движком → новая версия рядом, публикация отдельно.
Второй экземпляр этого хода разошёлся бы с первым.

**Правит карту блок, а не движок, и это не исключение из правила.** Правило
звучало «правила живут в движке, повторять их здесь нельзя» — и оно про
`checklist.csv` и `zones.csv`, чьи правила держит `engine/manage.py`. Карту
движок не читает вовсе: её читает `src.recognize.cues`, команды для неё у
движка нет, повторять здесь нечего.

**Проверяет правку тот, кто карту читает.** Кандидат разбирается
`src.recognize.cues.load_cues` — тем же кодом, который работает в продукте, — и
результат сверяется с задуманным. Формат карты свободный, и строка, записанная
чуть не так, тихо перестаёт быть строкой: файл изменился, отпечаток изменился,
версия легла в хранилище, а подсказки нет. Свой разборщик формата означал бы,
что блок согласен сам с собой.

Отдельно проверяется то, чего у чек-листа не бывает:

- **коды сверяются с чек-листом той же версии** — подсказка на несуществующий
  пункт вывела бы модели код, которого в методике нет, а быстрый путь записал
  бы его без подтверждения аудитора;
- **неизвестный раздел — отказ, а не новый раздел**: опечатка завела бы
  раздел-двойник, и половина карты разъехалась бы по двум местам;
- **строка называется своей фразой целиком и дословно**, похожая не
  подставляется: правка не той строки меняет то, что уезжает партнёру;
- **ширина строки сверяется с заголовком таблицы**: колонки значат разное
  («грязь» и «поломка» — два вопроса про один объект), и строка другой ширины
  разъезжается.

### Предложения для управляющей компании (T165, D077)

`photo_cue_suggestions` собирает из уже записанного то, ради чего заводили
T164 и T181: рядом с каждой находкой лежит тройка, которую модель предложила
ДО фиксации, и разница между ней и тройкой самой записи — это и есть промах.
Инструмент складывает одинаковые промахи, называет строки карты слов, ведущие
к неверному коду, даёт готовый вызов правки — и цитирует фразу, которую
произнёс аудитор (T194).

**Боевой список слов он не пополняет, и это условие самого решения.** По карте
слов быстрый путь (T113) записывает пункт БЕЗ подтверждения аудитора (D064):
строка, дописанная автоматически, уехала бы в отчёт партнёру без чьего-либо
ведома. Поэтому ответ несёт `applied: false`, а применяет предложение человек
отдельным вызовом `edit_photo_cue` — который к тому же кладёт новую версию
рядом и НЕ публикует её, то есть между предложением и отчётом партнёру стоят
два решения человека, а не ноль.

Что важно в устройстве:

- **Отбор по уверенности написан как «порога нет ИЛИ уверенности нет ИЛИ она
  не ниже порога».** Средняя часть здесь главная: сверка со списком слов
  уверенности не считает вовсе, поэтому записи быстрого пути идут без неё — а
  это самые ценные строки, промах без подтверждения. Отбор «уверенность выше
  порога» потерял бы ровно их.
- **Предложенный вызов правки исполним, и это проверено запуском.** Коды в
  карте лежат ПО КОЛОНКАМ, колонки значат разное («грязь» и «поломка» — два
  вопроса про один объект), а правка принимает ровно столько ячеек, сколько
  колонок в разделе. Плоский список кодов дал бы предложение, которое
  `edit_photo_cue` отклоняет по ширине строки; код дописывается в ТУ колонку,
  где стоит промахнувшийся. Тест на настоящей базе берёт собранный вызов и
  скармливает его правке.
- **Класс и зона считаются отдельно и правки карты не предлагают.** Классы
  живут в разделе порогов и в `criteria.md`, зоны в карте не задаются вовсе —
  предложение правки было бы советом чинить не то место. Класс при
  поправленном ПУНКТЕ в счёт не идёт: предложенный класс относился к другому
  вопросу, и сравнивать его не с чем.
- **Пусто бывает трёх разных видов, и ответ их различает словами.** «Находок
  нет», «предложений рядом с находками нет» и «промахов нет» — разные вещи, а
  слитые в один пустой список они читались бы агентом как измеренное качество
  модели. Сегодня чаще всего верен второй: предложения хранятся только с T181.
- **Долей попаданий инструмент не считает.** «Модель права в 73%» никто не
  записывал, а в пересказе агента такое число немедленно пошло бы как
  измеренное качество. Наружу идут счёт и выбранные записанные значения
  (самая низкая и самая высокая уверенность выборки).
- **Фраза аудитора и строка карты идут рядом, и одна другую не заменяет
  (T194).** Требование владельца звучало именно про фразу: «если пользователь
  добавит что-то в духе "ГРЯЗЬ НА ПОЛКЕ В ГОРЯЧЕМ ЦЕХЕ, ЭТО ЧИСТОТА" то мы
  дополняем наш список терминов». Управляющей компании нужна строка — понять,
  что править; аудитору нужна фраза — увидеть, что он сказал. Поэтому у
  каждого промаха стоит `heard`: сказанное дословно и целиком, с числом
  повторов. Слова складываются только совпавшие буква в букву: склейка
  «почти одинаковых» показала бы формулировку, которой никто не произносил.
- **«Слов нет» и «сказано пустое» — разные вещи.** Слов не бывает у записей до
  T183 и у записей, где аудитор не говорил ничего: разбор голого кадра, выбор
  пункта кнопкой. Такие записи считаются числом (`without_words` — и у
  промаха, и по всей выборке) и пустой фразой не показываются: пустая строка
  среди сказанного читалась бы как произнесённое молчание. Это та же развилка,
  что три вида пустоты выше.
- **Готового вызова `add_photo_cue` нет, и это решение.** Когда строки карты за
  промахом не стоит вовсе, завести её можно только новой фразой — но сказанное
  аудитором это предложение целиком, а строка карты термин; раздел, куда её
  класть, из слов не выводится вовсе. Собранный за человека вызов подставил бы
  и формулировку, и раздел, то есть решил бы за управляющую компанию ровно то,
  ради чего D077 оставляет решение ей. Ответ вместо этого отсылает к `heard`.
- **Оговорки уходят в ответ списком, а не остаются в коде.** Главная теперь про
  границу выборки, а не про отсутствие слов: слова записаны с T183 (колонка —
  T185), но у записей старше и у записей без речи их нет.
- **Хвост фраз обрезан числом на месте, а не общим `truncated`.** За одним
  промахом может стоять сотня формулировок; названо десять
  (`PHRASES_PER_MISS`), остальные посчитаны в `other_phrases`. Общий
  `truncated` говорит про непрочитанные проверки, и подмена одного другим
  сказала бы неправду.

Читается это чтение так же, как чтения проверок, — через официальный контракт
блока `db`, с фильтром по арендатору из токена. Запросов получается один плюс
по одному на ТОЧКУ, а не на проверку: чтения «дай находки всей сети за период»
слой чтения сегодня не отдаёт (названо ниже), а перебор по проверкам стоил бы
до тысячи запросов вместо десятка. Право спрашивать — то же, что на методику
(`MCP_CHECKLIST_TENANTS`): карта слов документ управляющей компании, и токен
партнёра её не открывает.

### Чего правка методики не умеет

- **Завести зону с неравной долей одним вызовом.** Движок умеет либо уравнять доли всех зон, либо задать долю новой, не трогая остальные, — и второе оставляет сумму мимо 100%, то есть методику, которую движок считать откажется. Такая версия не принимается, и отказ говорит об этом словами. Неравные доли по-прежнему расставляет человек в `zones.csv`; команды «задать доли зон списком» у движка нет, а писать `zones.csv` мимо него этот блок не станет.
- **Пересобрать чек-лист из выгрузки IMF** (`manage.py import-xlsx`): через MCP файл передать нечем.
- **Завести раздел карты слов.** Раздел — это заголовок и таблица со своим
  смыслом колонок; заводить его вслепую значит решать за управляющую компанию,
  как устроена карта. Разделы расставляет человек, инструменты правят строки.
- **Ветвиться от произвольной версии.** Хранилище это умеет, но наружу не объявлено: правка отсчитывается от последней записанной версии, а откат делается публикацией. Лишний аргумент на каждом из шести инструментов стоил бы дороже, чем даёт.

## Отчёты и письма: что здесь есть и чего здесь нет (T171)

**Отчёт наружу не отдаётся, и это не недоделка.** PDF по MCP не проходит:
ответ инструмента — текст, а абсолютных путей в нём быть не должно (T120),
поэтому «вот файл» сказать нечем. Сам PDF при этом и не нужен второй раз: его
собирает бот в момент завершения и отдаёт аудитору, а заморожен он решением
D033. Всё, ради чего отчёт открывают через агента, уже отвечают
`list_inspections` (найти по точке и дате), `get_inspection` (что в нём:
шапка, разбивка оценки, находки) и поле `checklist_version` (по какой версии
методики посчитан).

**Письмо отдаётся, потому что письмо — текст, и его отправляет человек.**
Q010: письмо формируется в почте и уходит партнёру руками; D035: история
проверок И ПИСЕМ хранится в системе. Второе сегодня не выполнено — письмо
живёт один раз, сообщением в чате при завершении, и больше нигде. Хранить его
здесь блок не может (это запись в базу, а в базу ходит только `db`), поэтому
письмо **пересобирается** из записанного.

Опасность у пересборки ровно одна, и она проверена запуском, а не рассуждением:
`engine/report.py` считает оценку заново, по методике из `CHECKLIST_DIR` в
момент вызова. Белград-1 с поднятой ставкой D1 даёт не «97.5%, A», а «90%, B» —
то есть наивная пересборка отдала бы партнёру другую букву под прежней датой.
Поэтому:

- методика прибивается к версии, которой помечена ПРОВЕРКА: снимок из
  хранилища версий (D050 — старые версии не удаляются никогда), а хранилища
  нет — годится боевая, и только если она и есть эта версия;
- посчитанное движком сверяется с записанным в проверке, и расхождение это
  отказ, а не письмо. Имя каталога версии доказательством не считается:
  каталог кладёт не только этот блок;
- наружу уходит ЗАПИСАННАЯ оценка, а не посчитанная при сверке;
- незнакомый язык — отказ: движок на такой молча собирает письмо по-русски,
  и отправитель узнал бы об этом от партнёра.

**Письмо сегодня не готово к отправке, и ответ говорит это словами.**
`db.InspectionRow` не отдаёт аудитора, город, партнёра и контакт (в базе они
есть — их пишет слив), поэтому движок подписывает письмо прочерком и выходит с
нулевым кодом. Ответ несёт `ready_to_send: false` и перечень `not_restored`.
Перечень выводится из строки чтения, а не переписан списком: как только слой
чтения отдаст эти поля, письмо станет полным само.

## Стенд без базы — законная настройка, а не сбой (T171)

Продукт поднят на боевом сервере с намеренно не поднятой базой: бот проводит
проверку и отдаёт отчёт с письмом, истории у него нет. Отвечать на это
пустой выдачей нельзя — «проверок не найдено» агент пересказывает человеку как
факт о точке, хотя история цела и просто лежит не здесь. Отвечать общим «Не
удалось выполнить проверки (ConfigError)» тоже нельзя: тем же текстом
отвечает упавшая база, и человек идёт искать поломку, которой нет.

Поэтому `db.ConfigError` — «окружения для базы нет» — превращается в
собственный отказ, который называет переменную и говорит, что настройка
законная. Недоступная или упавшая база приходит другим типом и остаётся общим
отказом чтения: это разные события. Держится не текстом одного инструмента, а
перебором всего каталога в `tests/test_mcp_no_history.py`.

## Вердикт движка и его отсутствие — разные события (T187)

Хранилище считало ЛЮБОЙ ненулевой код возврата движка отказом МЕТОДИКИ.
Ненулевым он бывает и тогда, когда до разбора методики дело не дошло: процесс
снят (на занятой машине нехватка памяти — обычное дело), вышел срок,
интерпретатор не стартовал. Все три случая приходили вызывающему как «движок
вашу методику не принял», ложились в журнал строкой `refused` — и машинная
беда выглядела ровно как дефект методики. Отличить одно от другого было нечем,
и разбор такого падения уже стоил владельцу трёх часов.

Теперь `_run` различает вердикт и его отсутствие:

- **процесс снят сигналом** (`returncode < 0`) — проверяется ПЕРВЫМ и это
  главное из трёх. Убитый на полуслове движок успевает напечатать начало
  вывода, и по одному коду возврата он неотличим от разбора, кончившегося
  отказом: обрывок уехал бы вызывающему как «движок сказал вот что»;
- **вышел срок** (`ENGINE_TIMEOUT_SEC`) — `subprocess.TimeoutExpired` наружу не
  пересказывается: он печатает всю командную строку, вместе с путём к
  интерпретатору и к скрипту движка (T120);
- **ненулевой код при пустом выводе** — движок объясняет словами каждый свой
  отказ, поэтому молчание означает, что до разбора он не дошёл.

Все три дают `EngineNoVerdictError` — отдельный тип, а не оттенок текста, — и
ложатся в журнал исходом **`failed`**, а не `refused`: первое чинится на
машине, второе в методике, и одним словом они отправили бы читающего журнал
чинить не то. Версии от несостоявшейся правки не остаётся.

**Тест, упавший на таком отказе, теперь говорит, что случилось.** Утверждение
`assert итог.accepted` печатало постоянную строку `Outcome.status` («the change
was refused, no new version was stored») — одну и ту же у любого отказа, — и
упавший тест не сообщал ничего. Печатается `Outcome.refusal`, то есть слова
движка.

### Настоящая причина, найденная полным прогоном

Синтетической нагрузкой воспроизвести не удавалось: 24 прогона файлов
хранилища при load average до 179 на 10 ядрах — 0 падений; 10 прогонов с
покрытием — 0; 120 правок методики из восьми параллельных процессов — 0
отклонений. Поймал её полный прогон, когда машина ушла на load average 609, и
поймал ровно потому, что утверждение стало печатать слова движка. Вот они:

```
Exception ignored error evaluating path:
Traceback (most recent call last):
  File "<frozen getpath>", line 353, in <module>
InterruptedError: [Errno 4] Interrupted system call
Fatal Python error: error evaluating path
Python runtime state: core initialized
```

**Интерпретатор питона умирает на старте.** Под нагрузкой системный вызов
внутри `getpath` — вычисления путей интерпретатора, ещё до первой строки
скрипта — прерывается сигналом, `InterruptedError` не перехватывается, процесс
умирает с ненулевым кодом. Ни гонки, ни таймаута, ни зависимости от времени:
подпроцессу просто не дают стартовать.

Отсюда лечение: **несостоявшийся старт повторяется** (`ENGINE_ATTEMPTS`).
Повтор безопасен ровно потому, что старт не состоялся — ни `manage.py`, ни
`audit.py` не выполнили ни строки, кандидат не тронут. Отличает этот случай
сам интерпретатор своим `Python runtime state: core initialized`, а не догадка
по коду возврата: умерший ПОСЛЕ инициализации мог успеть переписать половину
кандидата, и он не повторяется никогда. Текст `Fatal Python error` при этом
вызывающему не уезжает ни в каком виде — до T187 человек шёл искать дефект
методики по сообщению интерпретатора.

**Трёх немедленных повторов не хватило (T190).** Настоящий движок умирал до
первой строки три раза подряд: попытки без паузы укладываются в одно занятое
окно машины. Длина окна измерена (нагрузка 600 на 10 ядрах, 240 окон за 90 с):
медиана 405 мс, p90 768 мс, максимум 1919 мс. Поэтому попыток пять, а между
ними растущая пауза, перешагивающая окно. Числа и `pause_before_retry` живут в
одном месте на весь продукт — `src/domain/engine.py`; своей копии здесь нет
намеренно, разойдясь, три места вызова движка повели бы себя по-разному в
одинаковой беде.

**Это не только наша беда.** В том же прогоне тем же способом упали восемь
тестов из девяти — в блоках `bot`, `domain` и `recognize` тоже: каждый из них
зовёт движок подпроцессом и читает его отказ как отказ продукта («Не записал:
… Сбой на моей стороне»). Здесь это вылечено, там — нет; названо в отчёте
блока.

## Чего не хватило в слое чтения

Блок читает только через `src/db/queries.py` и своих запросов к Postgres не пишет (`docs/forge/blocks/db.md`: никто, кроме `db`, в базу не ходит). Ко второй очереди слой чтения дорос: `get_inspection` по идентификатору, чтение находок и отбор по датам в SQL появились в `db` (T115, T116, T119), и пять инструментов чтения проверок работают.

**Открытый долг один, и он появился на T171: шапка проверки.** Колонки
`inspections.auditor`, `.city`, `.partner`, `.contact` в базе есть и
заполняются сливом (`src/db/push.py`), но `db.InspectionRow` их не возвращает,
и `_LIST_ALL_SQL` / `_LIST_BY_UNIT_SQL` / `_GET_INSPECTION_SQL` их не выбирают.
Из-за этого пересобранное письмо подписано прочерком: движок печатает `___`
вместо имени аудитора и выходит с нулевым кодом (проверено запуском). Нужны
четыре колонки в выборке `get_inspection` и четыре поля в `InspectionRow`;
`letters.py` подхватит их сам — перечень недостающего он выводит из строки
чтения через `getattr`, а не из переписанного списка.

- **Чтения «находки арендатора за период»** (T165). Сегодня собирается
  перебором точек: список проверок периода даёт названия точек, дальше по
  запросу на точку. Правильный запрос — один, с фильтром по датам на стороне
  базы; тогда не нужен ни перебор, ни отбор по набору проверок окна.

## Технические заметки

- **Сервер поднимается локально, а не Edge Function.** D055 задаёт форму (JSON-RPC, личный токен, мост), а не площадку; площадку задаёт D061 — база проверок сегодня локальный Postgres, доступов к облаку не нужно. Разбор протокола и инструменты от транспорта отделены (`rpc.py` не знает про сокеты), поэтому переезд в Edge Function позже — замена транспорта при тех же инструментах.
- **Слушаем только петлю, и это проверка, а не договорённость.** Адрес вне петли (`0.0.0.0`, адрес в локальной сети) сервер не принимает и не поднимается: площадка общая, рядом живут чужие проекты. Наружу блок не публикуется вовсе.
- **Своей библиотеки MCP нет.** Ни SDK, ни новой зависимости: сервер — это разбор десятка методов JSON-RPC поверх `http.server` из стандартной библиотеки. Ровно так же устроен работающий `swarm-mcp`, и его мост на `bash`+`curl` перенесён почти дословно.
- **Незнакомый аргумент — отказ.** Опечатка в имени фильтра (`unit_name` вместо `unit`) вернула бы проверки всей сети под видом одной точки; `tenant` в аргументах вернул бы историю соседа. Оба случая — один и тот же отказ по одному правилу, а не два частных запрета.
- **Отказ инструмента приходит как отказ, а не как пустая выдача.** Недоступная база даёт ответ, помеченный `isError`, с текстом «это отказ чтения, а не отсутствие проверок». Наружу при этом уходит только ТИП исключения: в тексте драйвера базы может оказаться строка подключения, а в трейсбеке — пути на машине.
- **Путь на диске — в лог, причина — агенту.** Отказы блока называют переменную окружения и то, что с ней не так, а абсолютный путь печатается в `stderr` рядом с отказом (`checklist._to_log`). Держится это не перечнем четырёх сообщений, а общим утверждением в тесте: все инструменты каталога прогоняются на семи стендах двумя наборами аргументов, и ни один ответ не содержит абсолютного пути. Вывод упавшего движка попадает под то же правило — трейсбек печатает путь к файлам продукта, поэтому корень продукта из него отрезается, а «engine/audit.py» остаётся.
- **Выведенных чисел в ответах нет.** Ни среднего процента по сети, ни разницы между двумя проверками точки. Такого числа никто не записывал, а в ответе агента оно немедленно начинает цитироваться как официальная оценка. Счёт (сколько проверок, точек, находок), распределение записанных букв и ссылки на лучшую и худшую записанные проверки несут тот же сигнал, ничего не выдумывая.
- **Период задаётся двумя датами, а не словом.** «За квартал» пришлось бы разбирать догадкой о том, что имел в виду человек; спрашивающий агент знает сегодняшнее число и назовёт границы точно. Обе границы включительно, фильтр идёт по дате обхода точки, а не по дате попадания в базу.
- **Предел выдачи и его потолок не переписаны в этот блок.** И значение по умолчанию, и проверка границ живут в одном месте — в `src/db/queries.py`; здесь только прокидывание. Второй экземпляр числа разошёлся бы с первым.
- **Тесты блока требуют настоящий Postgres** (`requires_db`), как и у `db`. Протокольная часть (авторизация, разбор сообщений, коды ошибок) базы не требует и идёт всегда: HTTP-запросы в тестах настоящие, через сокет на порту, который выбирает система.

  не нашлось: кода в ней полсотни строк, остальное решения.
- Оговорка «сырых слов в истории нет» снята сразу в трёх местах, а не в одном:
  в списке оговорок ответа, в заметке промаха мимо карты и в описании
  инструмента для агента (`catalogue.py`). Последнее важнее прочих: пока
  описание говорило, что фразы нет, агент про неё и не спросил бы.
- Решение, принятое самостоятельно: **готового вызова `add_photo_cue` из фразы не
  собираю**. Сказанное — предложение целиком, строка карты — термин, а раздел
  из слов не выводится вовсе; собранный вызов подставил бы за управляющую

- Фраза кладётся дословно и целиком — то же правило, что у строки карты (T144)

- Найдено по ходу и исправлено тем же заходом: заметка промаха печатала

- Семь порч, каждая — снятие ровно одной защиты, все пойманы: пустые слова

## Открытые вопросы к владельцу

- **Партнёрские наборы методики.** Сегодня методика одна на всю сеть, и правка не разделена по арендаторам: хранилище одно, доступ к нему — привилегия, названная в `.env`. `docs/02-domain.md` говорит, что «у партнёров со временем появятся свои наборы»; когда это случится, хранилищу понадобится измерение арендатора, а инструментам — понимание, чей набор они правят. Сейчас этого нет намеренно: делать разделение под предположение о будущем — значит угадывать форму, которой ещё нет.

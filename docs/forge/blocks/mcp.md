# Блок: mcp

## Назначение

Дать возможность работать через Claude с двумя вещами: с накопленными проверками (спросить историю точки, найти повторяющиеся нарушения, собрать сводку по сети) и с самой методикой — чек-листом, по которому эти проверки считаются (D049). Делается по образцу работающего `swarm-mcp` — JSON-RPC по HTTP, личный токен, тот же мост stdio↔HTTP (D055).

Содержимое проверки не пишет ни один инструмент. Мест, где блок перестаёт быть только чтением, два, оба включаются отдельной настройкой и по умолчанию выключены целиком: правка методики (D049) и снятие проверки из истории (D086/D089) — отзыв уже выданного документа пометкой, без единого знака правки внутри него.

## API-контракт

Двадцать два инструмента: шесть о проверках, один о снятии проверки и пятнадцать о методике. **Ни у одного из них нет аргумента `tenant`:** код арендатора приходит из личного токена (см. «Откуда берётся арендатор»). У инструментов методики нет и аргумента `store`: хранилище версий подставляет точка входа.

### Проверки — только чтение

```
list_inspections(unit?, date_from?, date_to?, limit?)   # проверки с фильтрами
unit_history(unit, limit?)                              # ряд записанных оценок точки
network_summary(date_from?, date_to?)                   # сводка по сети
get_inspection(id, lang?)                               # одна проверка целиком: находки и информационная часть
findings_by_unit(unit, limit?)                          # записанные находки одной точки
inspection_letter(id, lang?)                            # письмо партнёру по записанной проверке
```

Инструмента, пишущего проверку или находку, нет и не будет: проверку заводит и завершает аудитор через бота, а в базу её кладёт слив (T093). Запись проверки через агента означала бы запись в отчёт партнёру мимо человека. Держится это не обещанием: `tests/test_mcp_server.py` требует, чтобы у всего, что не объявлено методикой или снятием, обработчик лежал в модуле чтения проверок, — и чтобы инструмент снятия был ровно один.

### Снятие проверки из истории (T211, D086/D089)

```
retract_inspection(id, reason, confirm_unit, confirm_date)   # снять сданную проверку
```

Единственный инструмент, который меняет уже выданный документ, — и содержимого проверки он не трогает ничем: ставит пометку и записывает причину. Аргументов, правящих проверку, у него нет и не будет: неверный отчёт не правится, а заводится новый (D086).

### Методика — чтение версий и правка (T098, D049)

```
checklist_versions()                                    # какие версии есть, какая действует
checklist_items(version?, process?)                     # пункты версии и её зоны, без критериев
checklist_item(code, version?)                          # один пункт вместе с критериями D1/D2/D3
add_checklist_item(process, question_ru, levels, code?, process_en?, question_en?,
                   zones?, days?, criteria?, kind?, version_name?, note?)
edit_checklist_item(code, ...то же, кроме kind...)      # меняются только названные поля
remove_checklist_item(code, hard?, version_name?, note?)
restore_checklist_item(code, version_name?, note?)
add_zone(code, name_ru, name_en?, share?, equal_shares?, version_name?, note?)
remove_zone(code, keep_shares?, equal_shares?, version_name?, note?)
publish_checklist_version(version)                      # сделать версию той, что читает движок

photo_cues(version?)                                    # карта слов версии: разделы и строки
photo_cue_suggestions(date_from?, date_to?, min_confidence?, limit?, version?)
                                                        # где модель промахнулась и что предложить УК
add_photo_cue(section, phrase, codes, version_name?, note?)
edit_photo_cue(phrase, codes?, new_phrase?, version_name?, note?)
remove_photo_cue(phrase, version_name?, note?)
```

Девять правящих инструментов не меняют действующую методику: каждый кладёт рядом новую версию. Публикация — отдельный вызов, названный своим именем.

### Форма ответа

Ответ инструмента — JSON внутри текстового блока MCP. Ключи английские, как имена полей в `db.InspectionRow`: это машинная поверхность, её читает агент и пересказывает человеку на его языке сам. Отдельного слоя переводов у неё нет намеренно — переводить машинные ключи означало бы, что имя поля меняется от языка спрашивающего.

У каждой выдачи есть `status`, написанный словами: «ничего не найдено» отличимо от «не смогли прочитать», а `truncated` говорит, что чтение упёрлось в предел и за ответом остались ещё проверки.

`chat_id` наружу не отдаётся: это чат аудитора в телеграме, личный идентификатор, ни для одного вопроса агенту не нужный.

**Абсолютных путей в ответе нет ни в успешной выдаче, ни в отказе** (T120). Ответ уходит в модель, то есть за пределы машины, а по пути читается устройство каталогов деплоя и имя пользователя, под которым поднят сервер. Причина отказа при этом остаётся: она называет переменную окружения (`AUDIT_DATA_DIR`, `MCP_CHECKLIST_STORE`) и то, что с ней не так, — а сам путь печатается в лог процесса, который остаётся на машине.

## Зависимости

`db`.

## Откуда берётся арендатор

**Из токена, и ниоткуда больше.** Связка задаётся человеком в `.env`:

```
MCP_TOKENS=партнёр-а=<токен>,партнёр-б=<другой токен>
```

Разбирается один раз на старте; дальше запрос приносит токен в заголовке `Authorization`, сервер переводит его в код арендатора и передаёт инструментам сам. Аргументом вызова арендатор быть не может: аргумент назвал бы кто угодно, а слой чтения обязан фильтровать по арендатору, а не угадывать, откуда тот взялся (T110). Аргумент `tenant`, подсунутый в вызов, получает явный отказ, а не тихо отбрасывается: тихо отброшенный, он выглядел бы работающей защитой ровно до того дня, когда его добавят в разбор «для гибкости».

Из этого же следует остальное:

- один токен, названный дважды у разных арендаторов, — отказ на старте: иначе вопрос «чью историю открывает этот токен» решался бы порядком строк в файле;
- несколько токенов одного арендатора — законно: по человеку на токен, отзывается по одному;
- токен короче 24 знаков — отказ: перебор по локальной петле ничем не ограничен;
- токены не попадают ни в `repr` настроек (он уезжает в трейсбек, а трейсбек в лог), ни в текст отказа, ни в лог сервера;
- сверка идёт `secrets.compare_digest` и без досрочного выхода из перебора — обычное сравнение строк подбирается по времени ответа посимвольно;
- отказ не называет ни предъявленный токен, ни живых арендаторов: перечислять по нему партнёров не должен никто.

**С задачи T253 у токена есть вторая дверь** (решения D098, D099): личный токен, который выпускает бот на конкретного человека и хранит отпечатком в базе (`src/db/mcp_access.py`, миграция `0011`). `resolve_access` проверяет обе двери по порядку — сперва карту `MCP_TOKENS` из `.env` (она в памяти и стоит одного сравнения), затем личные токены (поход в базу). Токен из второй двери отвечает то же самое, что и токен из первой, — код арендатора и ничего больше: аргумент вызова по-прежнему не читается никем. Право на снятие проверки (`may_retract`) личным токенам не выдаётся: оно спрашивается только у карты `MCP_RETRACTION_TOKENS`, где личного токена нет, — раздавать необратимое право вместе с обычным доступом, выпускаемым в чате, никто не решал.

Проверено живым запуском поверх своей базы: с кодом из `main` письмо отказывало «не похоже на версию методики», карточка сообщала «version is not at hand» при методике на месте; после починки письмо собрано, подпись поля пришла из методики.

## Куда пишется правка методики и почему туда

**В файлы, рядом с боевой методикой, версиями.** Не в базу и не поверх действующего набора. Решение принято блоком, и вот из чего оно следует.

Оценку считает только движок, а движок читает **файлы** — каталог из `AUDIT_DATA_DIR` (`CHECKLIST_DIR` для самого движка). Методика, положенная в базу, оценкой бы не стала: её пришлось бы выгружать в те же файлы, и файлы остались бы источником истины, а база — второй копией, которая с ними разъезжается. Отпечаток версии по D050 тоже считается по байтам файлов методики. Поэтому источник истины остаётся один — файлы.

Устройство хранилища (`MCP_CHECKLIST_STORE`):

```
<хранилище>/versions/<версия>/   полный снимок методики: чек-лист, зоны, ставки, критерии, маршрут
<хранилище>/current              символическая ссылка на действующую версию
<хранилище>/journal.jsonl        журнал: кто, что, когда и чем кончилось
```

Порядок правки: снимок нужной версии → правка копии → проверка движком → въезд новой версии в хранилище переименованием. Боевой каталог не открывается на запись ни на одном шаге — это проверяется побайтовым сравнением до и после (`tests/test_mcp_checklist_store.py`).

**Правит методику движок, а не этот блок.** `engine/manage.py` вызывается подпроцессом с `CHECKLIST_DIR`, указывающим на копию. Иначе пришлось бы повторить здесь правила, которые в движок попали через боль: сохранение колонок управляющей компании при перезаписи файла (T109), запрет молча раздать доли зон (T112), отказ на неизвестный код зоны, отказ на дубль кода и нечисловой срок (T106). Повторённые, они разошлись бы с движком при первой же правке одного файла без другого. Контракт `lint-imports` запрещает `src.mcp` импортировать `engine`; подпроцесс — тот же приём, которым движок зовёт блок `domain`.

**Проверка идёт до записи, и она настоящая.** Кандидат принимается, только если `manage.py validate` не нашёл проблем (он показывает их все разом, а не падает на первой) И `audit.py init` + `score` посчитали по этой методике оценку. Второй шаг нужен: `validate` не читает ставки вычетов вовсе, а без них движок не посчитает ничего. Отказ приходит вызывающему **словами движка** — пересказ разошёлся бы с ними.

**Идентификатор версии — тот же, что штампуется в проверку.** Считает его `domain.version.compose`, тот самый код, который кладёт `checklist_version` в каждую слитую проверку. Второй экземпляр этой формулы означал бы, что проверка ссылается на версию, которой в хранилище нет. Проверено запуском: после публикации `domain.checklist_version()` возвращает ровно имя каталога опубликованной версии.

**Публикация — перестановка указателя, а не перезапись методики.** `current` — символическая ссылка, и меняется она одним `os.replace`: движок не может застать методику наполовину переписанной. Отсюда же обратимость: откат — это публикация прежней версии, а не восстановление из копии. Старые версии не удаляются никогда (D050), поэтому откатиться есть на что.

**Публикация, которой движок не увидит, — отказ.** Чтобы она работала, `AUDIT_DATA_DIR` должен указывать на сам `<хранилище>/current`. Пока он смотрит в обычный каталог методики, версии заводятся и проверяются, а публикация отказывает и объясняет, что поменять. Молчаливое «опубликовано» при движке, читающем другой каталог, — худший из возможных исходов: агент говорит человеку, что методика изменена, а отчёты продолжают считаться по прежней.

**Занятое имя версии — это два разных случая, и отказы у них разные (T218).**
Имя каталога считается по содержимому, поэтому кандидат, совпавший с уже
лежащей версией, — либо повтор той же правки от той же основы, либо **возврат**
к состоянию другой версии: строку карты завели и тут же сняли, пункт выключили
и включили обратно. Совпадает при этом не запрос, а получившееся состояние.
Различает случаи журнал: событие «из основы X получилась версия Y» есть только
у повтора. Одно слово на оба означало «ровно эта правка уже сделана» там, где
она не сделана вовсе, — агент управляющей компании читал это как «убрано,
повторять нечего», и правка молча оставалась невыполненной (#166). Возврат
отказом остаётся (двух каталогов с одним содержимым, набором и датой быть не
может), но отказ называет оба выхода: опубликовать эту версию — это и есть
откат — или записать состояние под другим именем набора.

### Кому методика открыта

Методика **одна на всю сеть** — это документ управляющей компании, а не данные арендатора. Поэтому доступ к ней не выводится из токена партнёра: он задаётся отдельно, `MCP_CHECKLIST_TENANTS`, и по умолчанию не открыт никому. Заслон стоит на входе, рядом с границей арендаторов (`server._checklist_for` → `rpc.handle`): обработчики права не спрашивают вовсе, и обработчик, забывший спросить, дырой стать не может.

Названная наполовину настройка — отказ на старте, а не молчаливо выключенный доступ, и арендатор из списка обязан существовать среди токенов: опечатка в коде означала бы доступ, выданный никому, и выглядела бы как работающая настройка.

Перечень инструментов при этом один для всех: инструменты методики видны и тому, кому она не открыта, и получают внятный отказ при вызове. Перечень, зависящий от прав, сказал бы агенту «такого инструмента нет», и человек пошёл бы искать причину в коде вместо `.env`.

### Карта слов правится тем же ходом, но не движком (T144)

`photo-cues.md` — документ управляющей компании, по которому быстрый путь
(T113) решает, что записать **без подтверждения аудитора**. До T144 у неё не
было ни инструмента правки, ни отката: править было нечем, а вернуть прежнее
можно было только копией файла вне git.

Хранилище её уже видело: карта входит в отпечаток версии (`DATA_FILES`, с
04.09.2026), то есть её правка и так даёт новую версию. Поэтому ход правки
общий с чек-листом — он вынесен в `checklist.apply_edit`: снимок версии →
правка копии → проверка движком → новая версия рядом, публикация отдельно.
Второй экземпляр этого хода разошёлся бы с первым.

**Правит карту блок, а не движок, и это не исключение из правила.** Правило
звучало «правила живут в движке, повторять их здесь нельзя» — и оно про
`checklist.csv` и `zones.csv`, чьи правила держит `engine/manage.py`. Карту
движок не читает вовсе: её читает `src.recognize.cues`, команды для неё у
движка нет, повторять здесь нечего.

**Проверяет правку тот, кто карту читает.** Кандидат разбирается
`src.recognize.cues.load_cues` — тем же кодом, который работает в продукте, — и
результат сверяется с задуманным. Формат карты свободный, и строка, записанная
чуть не так, тихо перестаёт быть строкой: файл изменился, отпечаток изменился,
версия легла в хранилище, а подсказки нет. Свой разборщик формата означал бы,
что блок согласен сам с собой.

Отдельно проверяется то, чего у чек-листа не бывает:

- **коды сверяются с чек-листом той же версии** — подсказка на несуществующий
  пункт вывела бы модели код, которого в методике нет, а быстрый путь записал
  бы его без подтверждения аудитора;
- **неизвестный раздел — отказ, а не новый раздел**: опечатка завела бы
  раздел-двойник, и половина карты разъехалась бы по двум местам;
- **строка называется своей фразой целиком и дословно**, похожая не
  подставляется: правка не той строки меняет то, что уезжает партнёру;
- **ширина строки сверяется с заголовком таблицы**: колонки значат разное
  («грязь» и «поломка» — два вопроса про один объект), и строка другой ширины
  разъезжается.

### Предложения для управляющей компании (T165, D077)

`photo_cue_suggestions` собирает из уже записанного то, ради чего заводили
T164 и T181: рядом с каждой находкой лежит тройка, которую модель предложила
ДО фиксации, и разница между ней и тройкой самой записи — это и есть промах.
Инструмент складывает одинаковые промахи, называет строки карты слов, ведущие
к неверному коду, даёт готовый вызов правки — и цитирует фразу, которую
произнёс аудитор (T194).

**Боевой список слов он не пополняет, и это условие самого решения.** По карте
слов быстрый путь (T113) записывает пункт БЕЗ подтверждения аудитора (D064):
строка, дописанная автоматически, уехала бы в отчёт партнёру без чьего-либо
ведома. Поэтому ответ несёт `applied: false`, а применяет предложение человек
отдельным вызовом `edit_photo_cue` — который к тому же кладёт новую версию
рядом и НЕ публикует её, то есть между предложением и отчётом партнёру стоят
два решения человека, а не ноль.

Что важно в устройстве:

- **Отбор по уверенности написан как «порога нет ИЛИ уверенности нет ИЛИ она
  не ниже порога».** Средняя часть здесь главная: сверка со списком слов
  уверенности не считает вовсе, поэтому записи быстрого пути идут без неё — а
  это самые ценные строки, промах без подтверждения. Отбор «уверенность выше
  порога» потерял бы ровно их.
- **Предложенный вызов правки исполним, и это проверено запуском.** Коды в
  карте лежат ПО КОЛОНКАМ, колонки значат разное («грязь» и «поломка» — два
  вопроса про один объект), а правка принимает ровно столько ячеек, сколько
  колонок в разделе. Плоский список кодов дал бы предложение, которое
  `edit_photo_cue` отклоняет по ширине строки; код дописывается в ТУ колонку,
  где стоит промахнувшийся. Тест на настоящей базе берёт собранный вызов и
  скармливает его правке.
- **Класс и зона считаются отдельно и правки карты не предлагают.** Классы
  живут в разделе порогов и в `criteria.md`, зоны в карте не задаются вовсе —
  предложение правки было бы советом чинить не то место. Класс при
  поправленном ПУНКТЕ в счёт не идёт: предложенный класс относился к другому
  вопросу, и сравнивать его не с чем.
- **Пусто бывает трёх разных видов, и ответ их различает словами.** «Находок
  нет», «предложений рядом с находками нет» и «промахов нет» — разные вещи, а
  слитые в один пустой список они читались бы агентом как измеренное качество
  модели. Сегодня чаще всего верен второй: предложения хранятся только с T181.
- **Долей попаданий инструмент не считает.** «Модель права в 73%» никто не
  записывал, а в пересказе агента такое число немедленно пошло бы как
  измеренное качество. Наружу идут счёт и выбранные записанные значения
  (самая низкая и самая высокая уверенность выборки).
- **Фраза аудитора и строка карты идут рядом, и одна другую не заменяет
  (T194).** Требование владельца звучало именно про фразу: «если пользователь
  добавит что-то в духе "ГРЯЗЬ НА ПОЛКЕ В ГОРЯЧЕМ ЦЕХЕ, ЭТО ЧИСТОТА" то мы
  дополняем наш список терминов». Управляющей компании нужна строка — понять,
  что править; аудитору нужна фраза — увидеть, что он сказал. Поэтому у
  каждого промаха стоит `heard`: сказанное дословно и целиком, с числом
  повторов. Слова складываются только совпавшие буква в букву: склейка
  «почти одинаковых» показала бы формулировку, которой никто не произносил.
- **«Слов нет» и «сказано пустое» — разные вещи.** Слов не бывает у записей до
  T183 и у записей, где аудитор не говорил ничего: разбор голого кадра, выбор
  пункта кнопкой. Такие записи считаются числом (`without_words` — и у
  промаха, и по всей выборке) и пустой фразой не показываются: пустая строка
  среди сказанного читалась бы как произнесённое молчание. Это та же развилка,
  что три вида пустоты выше.
- **Готового вызова `add_photo_cue` нет, и это решение.** Когда строки карты за
  промахом не стоит вовсе, завести её можно только новой фразой — но сказанное
  аудитором это предложение целиком, а строка карты термин; раздел, куда её
  класть, из слов не выводится вовсе. Собранный за человека вызов подставил бы
  и формулировку, и раздел, то есть решил бы за управляющую компанию ровно то,
  ради чего D077 оставляет решение ей. Ответ вместо этого отсылает к `heard`.
- **Оговорки уходят в ответ списком, а не остаются в коде.** Главная теперь про
  границу выборки, а не про отсутствие слов: слова записаны с T183 (колонка —
  T185), но у записей старше и у записей без речи их нет.
- **Хвост фраз обрезан числом на месте, а не общим `truncated`.** За одним
  промахом может стоять сотня формулировок; названо десять
  (`PHRASES_PER_MISS`), остальные посчитаны в `other_phrases`. Общий
  `truncated` говорит про непрочитанные проверки, и подмена одного другим
  сказала бы неправду.

Читается это чтение так же, как чтения проверок, — через официальный контракт
блока `db`, с фильтром по арендатору из токена. Запросов получается один плюс
по одному на ТОЧКУ, а не на проверку: чтения «дай находки всей сети за период»
слой чтения сегодня не отдаёт (названо ниже), а перебор по проверкам стоил бы
до тысячи запросов вместо десятка. Право спрашивать — то же, что на методику
(`MCP_CHECKLIST_TENANTS`): карта слов документ управляющей компании, и токен
партнёра её не открывает.

### Чего правка методики не умеет

- **Завести зону с неравной долей одним вызовом.** Движок умеет либо уравнять доли всех зон, либо задать долю новой, не трогая остальные, — и второе оставляет сумму мимо 100%, то есть методику, которую движок считать откажется. Такая версия не принимается, и отказ говорит об этом словами. Неравные доли по-прежнему расставляет человек в `zones.csv`; команды «задать доли зон списком» у движка нет, а писать `zones.csv` мимо него этот блок не станет.
- **Пересобрать чек-лист из выгрузки IMF** (`manage.py import-xlsx`): через MCP файл передать нечем.
- **Завести раздел карты слов.** Раздел — это заголовок и таблица со своим
  смыслом колонок; заводить его вслепую значит решать за управляющую компанию,
  как устроена карта. Разделы расставляет человек, инструменты правят строки.
- **Ветвиться от произвольной версии.** Хранилище это умеет, но наружу не объявлено: правка отсчитывается от последней записанной версии, а откат делается публикацией. Лишний аргумент на каждом из шести инструментов стоил бы дороже, чем даёт.

## Снятие проверки: кому открыто и чем подтверждается (T211, D086/D089)

Неверный отчёт не правится: заводится новый, а старый снимается — и снимается через MCP, не в боте (D086). Пометкой, а не удалением строки, с обязательной причиной, и снятая проверка базово видна только администраторам (D089).

Всё, что ниже уровня инструмента, делает блок `db` (`src/db/retract.py`, миграция `0010`): пометка одной транзакцией, уборка кадров из хранилища, вторая непривилегированная роль `dodo_audit_admin` и построчные политики, которыми снятая проверка прячется от обычной роли. Здесь — граница инструмента.

### Право на снятие даётся ТОКЕНУ, а не арендатору

Это единственное место блока, где право личное, и отличие от методики не случайное.

У методики вопрос стоит «какая сторона»: методика одна на всю сеть, её правит управляющая компания, и `MCP_CHECKLIST_TENANTS` называет арендаторов. У снятия сторона уже названа предъявленным токеном — снимается проверка того же арендатора, — и назвать его второй раз значит не ответить ни на что. Открытым остаётся другой вопрос: **кто именно.** Он не риторический: у одного арендатора токенов несколько, по человеку на токен, а снятие необратимо для партнёра — отчёт и письмо у него на руках, кадры уезжают из хранилища насовсем. Право, выданное стороне, досталось бы и тому токену, который отдали агенту на чтение.

Поэтому `MCP_RETRACTION_TOKENS` перечисляет сами токены. Токен оказывается в `.env` дважды, и это осознанная цена: разойтись копии молча не могут — токен, названный здесь и отсутствующий в `MCP_TOKENS`, отказ на старте, и отказ называет **номер записи, а не значение** (отказ настроек уходит в лог, а токен из лога пришлось бы менять). Пусто — снятие закрыто всем.

Заслон стоит на входе (`rpc._call_tool` по виду инструмента), а не в обработчике: обработчик, забывший спросить о правах, был бы дырой, которую видно только чтением всех обработчиков подряд. Перечень инструментов от права не зависит — `retract_inspection` виден и тому, кому снятие не открыто, и получает внятный отказ при вызове.

### Подтверждение — механизм, а не обещание

Снять вслепую нельзя: вызов обязан назвать точку и дату обхода так, как они записаны (`confirm_unit`, `confirm_date`). Идентификатор — тридцать шесть знаков, которые человек глазами не читает; подтверждение — это то, что человек видит на самом документе. Не сошлось — не снято, а в отказе написано, чем эта проверка является на самом деле: точка, дата, записанная оценка, число находок. Попасть в чужую строку с первого раза становится нельзя, и держится это не тем, что агент пообещал спросить человека.

Имя точки сверяется тем же ключом сопоставления, которым продукт сводит точки (`db.units.normalize_unit_name`): своё второе правило означало бы, что подтверждение не принимает имя, под которым проверка и лежит.

### Отказы называют причину, но чужой текст наружу не уходит

Блок `db` отвечает одним типом (`RetractionError`) и на отказ по существу — причина не названа, проверка не запечатана, на неё уже сослались, — и на беду окружения; во втором случае он приводит сообщение драйвера целиком, а в сообщении psycopg о неудачном подключении стоят адрес, порт и имя базы. Ответ инструмента уходит в модель, то есть за пределы машины (T120).

Различаются они **по происхождению текста, а не разбором строки**: `__cause__` есть ровно там, где чужое исключение обёрнуто, то есть ровно там, где в текст подставлен чужой текст. Отказы по существу написаны блоком `db` целиком и доезжают до человека его словами — пересказывать их здесь нельзя, второй экземпляр разошёлся бы с первым при первой же правке.

Три отказа инструмент пишет сам, потому что они про его собственную работу: проверки у этого доступа нет (один текст на «нет такой» и «чужая» — иначе перебор идентификаторов читал бы состав чужой истории), подтверждение не сошлось, и проверка снята раньше.

**Снятая раньше — это отказ, а не «готово».** Причина снятия не переписывается никогда, иначе снятие стало бы способом править основание задним числом; ответ «готово» агент однажды перескажет человеку как «новая причина принята». Уборка кадров при этом доделывается — снятие и уборка идут разными транзакциями, и повторный вызов единственное, что убирает кадры отозванного документа из хранилища, — и об этом сказано в самом отказе: отказ, молча сделавший работу, хуже отказа.

### Проверено там, куда смотрит спрашивающий

Что снятая проверка пропадает из истории, держит база, и в блоке `db` это проверено политиками под обеими ролями. Но спрашивающий видит не политику, а ответ инструмента, и между ними лежит слой, который однажды прочитает историю вторым способом — под подключением администратора, «чтобы было полнее». Поэтому `tests/test_mcp_retraction.py` перебирает читающие инструменты через них самих: `list_inspections`, `unit_history`, `findings_by_unit`, `network_summary`, `get_inspection`, `inspection_letter`.

## Отчёты и письма: что здесь есть и чего здесь нет (T171)

**Отчёт наружу не отдаётся, и это не недоделка.** PDF по MCP не проходит:
ответ инструмента — текст, а абсолютных путей в нём быть не должно (T120),
поэтому «вот файл» сказать нечем. Сам PDF при этом и не нужен второй раз: его
собирает бот в момент завершения и отдаёт аудитору, а заморожен он решением
D033. Всё, ради чего отчёт открывают через агента, уже отвечают
`list_inspections` (найти по точке и дате), `get_inspection` (что в нём:
шапка, разбивка оценки, находки и информационная часть — ответы аудитора в
конце обхода, T207) и поле `checklist_version` (по какой версии методики
посчитан).

**Письмо отдаётся, потому что письмо — текст, и его отправляет человек.**
Q010: письмо формируется в почте и уходит партнёру руками; D035: история
проверок И ПИСЕМ хранится в системе. Второе сегодня не выполнено — письмо
живёт один раз, сообщением в чате при завершении, и больше нигде. Хранить его
здесь блок не может (это запись в базу, а в базу ходит только `db`), поэтому
письмо **пересобирается** из записанного.

Опасность у пересборки ровно одна, и она проверена запуском, а не рассуждением:
`engine/report.py` считает оценку заново, по методике из `CHECKLIST_DIR` в
момент вызова. Белград-1 с поднятой ставкой D1 даёт не «97.5%, A», а «90%, B» —
то есть наивная пересборка отдала бы партнёру другую букву под прежней датой.
Поэтому:

- методика прибивается к изданию, которым помечена ПРОВЕРКА, и годным
  считается каталог, чьё СОДЕРЖИМОЕ и есть это издание (см. ниже, T236);
- посчитанное движком сверяется с записанным в проверке, и расхождение это
  отказ, а не письмо. Имя каталога версии доказательством не считается:
  каталог кладёт не только этот блок;
- наружу уходит ЗАПИСАННАЯ оценка, а не посчитанная при сверке;
- незнакомый язык — отказ: движок на такой молча собирает письмо по-русски,
  и отправитель узнал бы об этом от партнёра.

**Готовность письма ответ говорит словами, а не молчанием.** Шапку проверки
(аудитор, город, партнёр, контакт) слой чтения отдаёт с T176 — пустой она
приезжает теперь только там, где пуста в базе, — но пустое поле шапки движок
печатает прочерком и выходит с нулевым кодом, то есть письмо выглядит готовым.
Поэтому ответ несёт `ready_to_send` и перечень `not_restored`, а перечень шапки
выводится из СТРОКИ ЧТЕНИЯ, а не переписан списком: поле, пропавшее из неё,
станет недостающим в ответе, а не отказом инструмента.

Шапкой невосстановленное не исчерпывается. **Срок плана действий называет
аудитор** — это поле информационной части (T200), и в письме печатается его
ответ. Информационной части у проверки может не быть вовсе (слита до T200 либо
аудитор пропустил все поля, D070), и тогда движок подставляет свой расчёт: дата
обхода плюс стандартный срок. Такое письмо отдаётся, но с `ready_to_send:
false` и словом о сроке отдельным предложением: пустая шапка видна прочерком, а
подставленная дата читается как ответ аудитора и ничем себя не выдаёт.

**Письмо не на языке записи смешивает языки, и это третье невосстановленное**
(T220). Шапку и названия зон движок переводит, а формулировки находок печатает
как записаны — это слова аудитора, и переводить их не полагается никому:
машинный перевод отправил бы партнёру чужую формулировку под подписью
аудитора. Правило остаётся; менялось молчание о нём. Такое письмо связное,
подписанное и с верной оценкой, то есть выглядит готовым — а половина его
написана на языке, которого получатель может не знать, и отправителю,
который язык записи не читает, заметить это не по чему. Поэтому язык находок
попадает в тот же перечень `not_restored`, а `status` называет оба языка:
на каком собрано письмо и на каком записаны находки. Сверяется язык находок
(`FindingRow.lang` — язык речи проверки) именно с языком ПИСЬМА, а не с языком
отчёта: языка у проверки три, они разные поля, и письмо, никем отдельно не
заказанное, смешано ровно так же, если аудитор говорил не на языке отчёта.
Находок нет вовсе — смешивать нечего, и перечень молчит.

## Каталог издания опознаётся отпечатком, и ответ на это один (T236)

«Где каталог издания X» — вопрос, который в продукте задают двое: полка снимков домена (`src/domain/edition.py`, T169 — снимок, снятый ботом на старте проверки) и хранилище версий MCP (`letters.pinned`). До T236 ответов было два. Полка сверяла отпечаток: годен тот каталог, чьё содержимое и есть это издание. Хранилище довольствовалось **именем** каталога.

Для письма это было наполовину скомпенсировано: движок пересчитывает оценку (`letters._verify`), и подмена методики выдала бы другую букву. **У карточки проверки компенсации не было вовсе.** `info_part._titles` берёт каталог у того же `pinned` и читает из него подписи полей, не считая ничего: каталог с правильным именем и чужим содержимым подписал бы ответы аудитора формулировками другой методики молча.

Сведено это одним ответом, а не согласованием двух: `domain.version.edition_of` — рядом с `compose`, той самой формулой, которой издание штампуется в проверку. Полка и хранилище зовут его оба.

**Полка домена стала третьим местом, где `pinned` ищет издание.** Это вторая половина сведения, и порядок здесь важен: брать каталог с чужой полки, доверяя его имени, значило бы расширить дефект, а не закрыть его; со сверкой источник перестаёт быть вопросом доверия. На полке лежат издания, которых в хранилище MCP нет и не будет: хранилище наполняет правка методики через агента, полку — каждый выезд на точку. Читается она только на чтение и только по имени, выведенному из содержимого; писать туда блок не имеет права ничем — полка принадлежит идущим проверкам.

Мест теперь три (хранилище версий, боевая методика, полка бота), и на правильность порядок между ними не влияет: годность каждого решает отпечаток. Порядок задаёт только то, чем подписан ответ человеку.

**Каталог, названный изданием и им не являющийся, пишется в лог** (`[mcp] каталог назван изданием проверки, но им не является`). Отказ агенту остаётся прежним — «этого издания на машине нет», путь с диска в ответ не уходит (T120), — но человек, у которого на полке лежит подменённый или недоразложенный каталог, обязан узнать, какой именно. До сверки такой каталог доходил до чтения `checklist.csv` и оставлял след там; сверка отвергает его раньше, и след обязан был переехать сюда, иначе закрытие дефекта заодно спрятало бы его причину.

Жалоба идёт **и тогда, когда ответ всё-таки нашёлся** — на соседней полке, например. Найдено живым смоуком: самозванец, оставшийся за спиной удачного ответа, — это по-прежнему сломанное хранилище, и молчать о нём оттого, что выручила полка, значит откладывать поломку до дня, когда полки не окажется. Стоит это одного лишнего чтения методики и только когда оба каталога на месте. Про боевую методику лог молчит намеренно: она не выдаёт себя за издание проверки, она просто им не является — обычное дело после переиздания, и жалоба на каждое такое чтение утопила бы настоящую подмену в шуме.

**Дефект воспроизведён живым запуском до починки, и это важнее рассуждения.** На стенде: проверка помечена изданием, снимок которого лежит на полке бота; в хранилище MCP положен каталог с ТЕМ ЖЕ именем и содержимым другого издания. С поведением до T236 письмо собралось по самозванцу — и **сверка оценки движком его пропустила**: подменённый пункт ни в одну находку не входил, проценты и буква сошлись (99.5 % A). То есть компенсация, на которую опиралось письмо, ловит только ту подмену, что двигает цифру; формулировки в документе партнёру она не защищает вовсе, а карточку проверки, которая не считает ничего, не защищает ничем. После починки то же письмо собирается по полке бота, пункт чужого издания в него не попадает, а самозванец назван в логе.

**Сторож имени сверка не заменяет.** Имя издания приезжает из базы и подставляется в путь каталога, поэтому `_check_version` стоит там же, где стоял: отпечаток отвечает, то ли это содержимое, а сторож — куда мы вообще пошли смотреть. Само правило этого сторожа сведено в одно место следующей задачей — T243, ниже.

## Годность ИМЕНИ издания — тоже одно правило (T243)

Продолжение T236 на соседнем вопросе. Там расходились сверки **содержимого** каталога издания, здесь — сверки его **имени**, и расходились так же молча.

Имя набора методики задаёт управляющая компания файлом `checklist_version.txt`, и **оно бывает не латиницей**. Полка снимков домена такое издание принимала: список запрещённого — `.`, `..` и разделители пути. Сторож MCP был белым списком латиницы (`VERSION_PATTERN = ^[a-z0-9][a-z0-9._-]{0,80}$`). Для проверки, помеченной изданием вроде `имф-2026-09-01-99cdb94ee821`, инструменты MCP не отдавали **ничего**: ни письма, ни подписей полей в карточке.

Хуже самого отказа было то, **что** он говорил.

- Письмо: «не похоже на версию методики», и рядом латинский пример. То есть человека посылали переименовывать законное издание его же управляющей компании.
- Карточка: «the methodology version this inspection was scored by is not at hand» — прямая неправда. Методика лежала на месте, и после починки то же письмо собирается по ней с пометкой `live methodology, which is that exact version`.

**Правило сведено в `domain.version.is_one_segment`** — рядом с `compose` и `edition_of`, то есть там же, где живёт формула самого идентификатора и ответ на вопрос «то ли это издание». Зовут его оба: полка домена (`domain.edition`) и сторож MCP (`checklist._check_version`). Латиница в MCP была нужна не сама по себе, а как охрана пути — эту задачу решает запрет разделителей и `.`/`..`, то есть ровно то, что у домена и было.

**Длина осталась частью правила, но мерится пределом файловой системы**, а не выдуманным числом: `NAME_MAX` = 255 **байт**. Не политика, а факт — имя длиннее каталогом не станет нигде. Мерка байтовая, а не знаковая, именно из-за нелатинских имён: кириллица стоит два байта на букву, и предел в знаках пропустил бы имя вдвое длиннее — оно дошло бы до `os.replace` и упало голым `ENAMETOOLONG` посреди правки методики.

**Белый список у ИМЕНИ НАБОРА остался, и это не непоследовательность.** `NAME_PATTERN` сторожит имя, которое агент **придумывает здесь и сейчас**, заводя новый набор: выбор ещё есть, и отказ с примером стоит человеку одного слова. Имя уже изданного набора приходит от управляющей компании, наследуется `_resolve_name` как есть и выбором не является вовсе — отвергнутое, оно означало бы, что продукт не читает методику своего заказчика.

**Негодное имя стало отказом, а не `None`.** Раньше `pinned` глотал отказ сторожа молча, и «идентификатор не может быть именем каталога» приезжало обоим потребителям тем же ответом, что «издания на машине нет». Теперь отказы разные и по причине разные:

- письмо отказывает словами про имя каталога, а не про пропавший снимок;
- карточка по-прежнему **отдаёт записанные ответы** (она читается без единого файла методики, и отказ прятал бы от человека документ, который уже ушёл партнёру), но приписка называет настоящую беду: чинить надо запись проверки, а не искать снимок на диске.

Тип отказа при этом у поверхностей свой и это намеренно: `ChecklistError` означает «движок не принял правку методики», а на пути чтения проверок ни правки, ни движка нет — там `ToolError` (`letters.check_version`).

**Третья поверхность — правка методики через агента.** Наследованное нелатинское имя ловилось белым списком в самом конце `apply_edit` — после снимка, после правки движком и после проверки движком, у имени каталога новой версии. Правка при этом теряется целиком, а отказ говорит про «не похоже на версию». Теперь такая правка доходит до записи.

**Дефект воспроизведён живым запуском до починки.** Стенд на порту 8670 поверх своей базы `dodo_audit_mcp11`: копия боевой методики с `checklist_version.txt` = «имф 2026-09-01», проверка заведена доменом и слита `push_inspection` (издание `имф-2026-09-01-99cdb94ee821`). С кодом из `main` `inspection_letter` отдал отказ «не похоже на версию методики», а `get_inspection` — поля без подписей с припиской «is not at hand». После починки на том же стенде: письмо собрано (`ready_to_send: true`, `not_restored: []`), подпись поля `INF07` пришла из методики. Третья поверхность проверена там же: `add_checklist_item` через HTTP завёл версию `имф-2026-09-06-110bcb6aa2bb` от основы `имф-2026-09-01-99cdb94ee821`, унаследовав нелатинское имя набора. Каталог методики стенда сверен по md5 до и после — не изменился.

## Находка без формулировки: письмо подставляет вопрос методики (T237)

Задача заведена как «письмо печатает находку с пустой формулировкой и молчит». **Молчание оказалось верной половиной, а пустая формулировка — нет**, и разница здесь не в оттенке.

`db.FindingRow.text` объявлен `str | None` намеренно: `None` значит «строки перевода нет вовсе», и подменять её пустой строкой в слое чтения запрещено — иначе «перевода нет» становится неотличимо от «аудитор ничего не написал». `letters.state_json` отдаёт движку `text or ""`, то есть до движка обе беды доезжают одинаково — пустым `evidence`.

**Пустого места в письме при этом не появляется.** Движок подставляет вместо недостающих слов формулировку ВОПРОСА методики по коду пункта (`engine/report.py`: `evidence or clean_q(question)`), и подставляет её **на языке письма** — колонка выбирается по `lang`. Проверено запуском на боевой методике: находка `PRD01/D1/freezer`, у которой удалена строка перевода, печатается в письме строкой «Морозильная камера: Замороженные продукты размораживаются в соответствии со стандартом».

Отсюда три свойства, каждое хуже предыдущего:

- строка **связная и законченная** — она не выглядит недоделанной ничем;
- вопрос методики сформулирован как **утверждение нормы**, поэтому у отклонения оказывается текст, читающийся как «всё в порядке», — в документе, который выставляет партнёру требования;
- подстановка **переводится**, тогда как настоящая формулировка находки не переводится никогда (T220). Значит в английском письме по русской проверке подменённая строка выглядит **нативнее** честной: она на языке письма, а соседняя, настоящая, остаётся по-русски.

Пустое место хотя бы видно. Эта подмена не видна ничем — поэтому `status` называет **номера** находок: кода пункта письмо не печатает вовсе, и найти строку в тексте иначе нечем.

**С T220 не сливается, и это главное утверждение задачи.** Там формулировка есть, но не на языке письма: нужен переводчик. Здесь её нет ни на каком языке: переводить нечего, нужен сам аудитор. Одно имя на оба случая отправило бы человека переводить пустоту, поэтому имя своё (`BLANK_TEXT_FIELD`) и предложение в `status` своё.

Меряются `None`, пустая строка и пробелы вместе: происхождение у них разное, а письму все три обходятся одинаково — перечень описывает ПИСЬМО, а не происхождение строки. Само письмо по-прежнему отдаётся, а не отказывает: правило блока «отдаётся, но НЕ молча» здесь то же, что у подставленного срока (T200) и смешанных языков (T220). `state_json` и `_wording_langs` не тронуты — меняется молчание, а не то, что печатается.

**Штатным путём такая находка не получается** — слив пишет строку на языке речи аудитора, — но слой чтения к ней готов по объявлению, и строка из базы не имеет права заставить письмо соврать.

## Отказы хранилища версий — тоже события журнала (T238)

Два отказа уходили наверх мимо `_refused`: пустая правка (отпечаток не изменился) и занятое имя версии. По журналу не было видно, что агент управляющей компании приходил и получил отказ, — хотя рядом стояло объяснение, почему отклонённую правку записывать надо.

Дороже всего это у **возврата** (T218): методика осталась ровно в том состоянии, из которого её пытались вывести, и следа попытки не оставалось вовсе. Читающий журнал через год видит «сняли пункт» и не видит, что его тут же пытались вернуть.

**Контракт возврата при этом не менялся**, и это решение, а не экономия правки. Блок mcp9 не чинил задачу именно потому, что напрашивающийся ход — превратить оба отказа в `Outcome(accepted=False)` — шире задачи. Он ещё и хуже:

- `Outcome` объявлен как **вердикт движка** («версия записана» либо «движок эту методику не принял»). Здесь движок не сказал ничего — отказало хранилище, и по одному полю `accepted` эти случаи не различить: понадобилось бы новое поле и разбор его у каждого потребителя;
- **ответ агенту стал бы неверным по автору**: `checklist_tools._accepted` пересказывает отклонённую правку словами «Движок сказал: …», и отказ хранилища получил бы неверного автора — на блоке, где отказ обязан называть причину правдиво;
- **снаружи не меняется ничего**: `_accepted` и так превращает отклонённый `Outcome` в `ChecklistError`. То есть ломать контракт пришлось бы ради одинакового наблюдаемого поведения.

Поэтому разделено другое: `_refused` делал два дела — писал событие и собирал ответ. Событие — свойство ХРАНИЛИЩА и одно на всех, оно уехало в `_write_refusal`. Форма ответа — свойство того, кто отказал: движок отвечает `Outcome`, хранилище отвечает отказом. `_store_refuses` пишет событие и **возвращает** отказ, чтобы `raise` остался виден глазом на месте вызова.

`version` в записи об отказе остаётся пустым и там, где имя занятой версии известно: поле означает «версия, которая появилась», а не появилось ничего. Слово `refused` при этом не размывается — отказ окружения (T187) по-прежнему пишется `failed`: первое чинят в методике или в запросе, второе на машине.

**Проверено живым запуском.** На стенде 8670 через HTTP: `add_checklist_item` → принято; `edit_checklist_item` с прежним значением → отказ «правка ничего не изменила»; `remove_checklist_item` → принято; `restore_checklist_item` → отказ «это ВОЗВРАТ». С кодом предшествующего коммита журнал содержал три строки — только принятые события; после починки пять, и обе отклонённые несут арендатора, инструмент, пояснение и ту же причину, что получил вызывающий.

## Стенд без базы — законная настройка, а не сбой (T171)

Продукт поднят на боевом сервере с намеренно не поднятой базой: бот проводит
проверку и отдаёт отчёт с письмом, истории у него нет. Отвечать на это
пустой выдачей нельзя — «проверок не найдено» агент пересказывает человеку как
факт о точке, хотя история цела и просто лежит не здесь. Отвечать общим «Не
удалось выполнить проверки (ConfigError)» тоже нельзя: тем же текстом
отвечает упавшая база, и человек идёт искать поломку, которой нет.

Поэтому `db.ConfigError` — «окружения для базы нет» — превращается в
собственный отказ, который называет переменную и говорит, что настройка
законная. Недоступная или упавшая база приходит другим типом и остаётся общим
отказом чтения: это разные события. Держится не текстом одного инструмента, а
перебором всего каталога в `tests/test_mcp_no_history.py`.

## Вердикт движка и его отсутствие — разные события (T187)

Хранилище считало ЛЮБОЙ ненулевой код возврата движка отказом МЕТОДИКИ.
Ненулевым он бывает и тогда, когда до разбора методики дело не дошло: процесс
снят (на занятой машине нехватка памяти — обычное дело), вышел срок,
интерпретатор не стартовал. Все три случая приходили вызывающему как «движок
вашу методику не принял», ложились в журнал строкой `refused` — и машинная
беда выглядела ровно как дефект методики. Отличить одно от другого было нечем,
и разбор такого падения уже стоил владельцу трёх часов.

Теперь `_run` различает вердикт и его отсутствие:

- **процесс снят сигналом** (`returncode < 0`) — проверяется ПЕРВЫМ и это
  главное из трёх. Убитый на полуслове движок успевает напечатать начало
  вывода, и по одному коду возврата он неотличим от разбора, кончившегося
  отказом: обрывок уехал бы вызывающему как «движок сказал вот что»;
- **вышел срок** (`ENGINE_TIMEOUT_SEC`) — `subprocess.TimeoutExpired` наружу не
  пересказывается: он печатает всю командную строку, вместе с путём к
  интерпретатору и к скрипту движка (T120);
- **ненулевой код при пустом выводе** — движок объясняет словами каждый свой
  отказ, поэтому молчание означает, что до разбора он не дошёл.

Все три дают `EngineNoVerdictError` — отдельный тип, а не оттенок текста, — и
ложатся в журнал исходом **`failed`**, а не `refused`: первое чинится на
машине, второе в методике, и одним словом они отправили бы читающего журнал
чинить не то. Версии от несостоявшейся правки не остаётся.

**Тест, упавший на таком отказе, теперь говорит, что случилось.** Утверждение
`assert итог.accepted` печатало постоянную строку `Outcome.status` («the change
was refused, no new version was stored») — одну и ту же у любого отказа, — и
упавший тест не сообщал ничего. Печатается `Outcome.refusal`, то есть слова
движка.

### Настоящая причина, найденная полным прогоном

Синтетической нагрузкой воспроизвести не удавалось: 24 прогона файлов
хранилища при load average до 179 на 10 ядрах — 0 падений; 10 прогонов с
покрытием — 0; 120 правок методики из восьми параллельных процессов — 0
отклонений. Поймал её полный прогон, когда машина ушла на load average 609, и
поймал ровно потому, что утверждение стало печатать слова движка. Вот они:

```
Exception ignored error evaluating path:
Traceback (most recent call last):
  File "<frozen getpath>", line 353, in <module>
InterruptedError: [Errno 4] Interrupted system call
Fatal Python error: error evaluating path
Python runtime state: core initialized
```

**Интерпретатор питона умирает на старте.** Под нагрузкой системный вызов
внутри `getpath` — вычисления путей интерпретатора, ещё до первой строки
скрипта — прерывается сигналом, `InterruptedError` не перехватывается, процесс
умирает с ненулевым кодом. Ни гонки, ни таймаута, ни зависимости от времени:
подпроцессу просто не дают стартовать.

Отсюда лечение: **несостоявшийся старт повторяется** (`ENGINE_ATTEMPTS`).
Повтор безопасен ровно потому, что старт не состоялся — ни `manage.py`, ни
`audit.py` не выполнили ни строки, кандидат не тронут. Отличает этот случай
сам интерпретатор своим `Python runtime state: core initialized`, а не догадка
по коду возврата: умерший ПОСЛЕ инициализации мог успеть переписать половину
кандидата, и он не повторяется никогда. Текст `Fatal Python error` при этом
вызывающему не уезжает ни в каком виде — до T187 человек шёл искать дефект
методики по сообщению интерпретатора.

**Трёх немедленных повторов не хватило (T190).** Настоящий движок умирал до
первой строки три раза подряд: попытки без паузы укладываются в одно занятое
окно машины. Длина окна измерена (нагрузка 600 на 10 ядрах, 240 окон за 90 с):
медиана 405 мс, p90 768 мс, максимум 1919 мс. Поэтому попыток пять, а между
ними растущая пауза, перешагивающая окно. Числа и `pause_before_retry` живут в
одном месте на весь продукт — `src/domain/engine.py`; своей копии здесь нет
намеренно, разойдясь, три места вызова движка повели бы себя по-разному в
одинаковой беде.

**Это не только наша беда.** В том же прогоне тем же способом упали восемь
тестов из девяти — в блоках `bot`, `domain` и `recognize` тоже: каждый из них
зовёт движок подпроцессом и читает его отказ как отказ продукта («Не записал:
… Сбой на моей стороне»). Здесь это вылечено, там — нет; названо в отчёте
блока.

## Чего не хватило в слое чтения

Блок читает только через `src/db/queries.py` и своих запросов к Postgres не пишет (`docs/forge/blocks/db.md`: никто, кроме `db`, в базу не ходит). Ко второй очереди слой чтения дорос: `get_inspection` по идентификатору, чтение находок и отбор по датам в SQL появились в `db` (T115, T116, T119), и пять инструментов чтения проверок работают.

**Долг T171 — шапка проверки — закрыт блоком `db` на T176:** `auditor`,
`city`, `partner` и `contact` есть и в `InspectionRow`, и во всех трёх
выборках слоя чтения, и письмо подписывается именем аудитора, а не прочерком.
`letters.py` подхватил их сам, без правки перечня: недостающее он выводит из
строки чтения через `getattr`. Информационную часть слой чтения отдаёт с T200
(`InspectionDetail.info`), и карточка проверки показывает её с T207.

**Открытый долг остался один.**

- **Чтения «находки арендатора за период»** (T165). Сегодня собирается
  перебором точек: список проверок периода даёт названия точек, дальше по
  запросу на точку. Правильный запрос — один, с фильтром по датам на стороне
  базы; тогда не нужен ни перебор, ни отбор по набору проверок окна.

## Технические заметки

- **Сервер поднимается локально, а не Edge Function.** D055 задаёт форму (JSON-RPC, личный токен, мост), а не площадку; площадку задаёт D061 — база проверок сегодня локальный Postgres, доступов к облаку не нужно. Разбор протокола и инструменты от транспорта отделены (`rpc.py` не знает про сокеты), поэтому переезд в Edge Function позже — замена транспорта при тех же инструментах.
- **Слушаем только петлю, и это проверка, а не договорённость.** Адрес вне петли (`0.0.0.0`, адрес в локальной сети) сервер не принимает и не поднимается: площадка общая, рядом живут чужие проекты. Наружу блок не публикуется вовсе.
- **Своей библиотеки MCP нет.** Ни SDK, ни новой зависимости: сервер — это разбор десятка методов JSON-RPC поверх `http.server` из стандартной библиотеки. Ровно так же устроен работающий `swarm-mcp`, и его мост на `bash`+`curl` перенесён почти дословно.
- **Незнакомый аргумент — отказ.** Опечатка в имени фильтра (`unit_name` вместо `unit`) вернула бы проверки всей сети под видом одной точки; `tenant` в аргументах вернул бы историю соседа. Оба случая — один и тот же отказ по одному правилу, а не два частных запрета.
- **Отказ инструмента приходит как отказ, а не как пустая выдача.** Недоступная база даёт ответ, помеченный `isError`, с текстом «это отказ чтения, а не отсутствие проверок». Наружу при этом уходит только ТИП исключения: в тексте драйвера базы может оказаться строка подключения, а в трейсбеке — пути на машине.
- **Путь на диске — в лог, причина — агенту.** Отказы блока называют переменную окружения и то, что с ней не так, а абсолютный путь печатается в `stderr` рядом с отказом (`checklist._to_log`). Держится это не перечнем четырёх сообщений, а общим утверждением в тесте: все инструменты каталога прогоняются на семи стендах двумя наборами аргументов, и ни один ответ не содержит абсолютного пути. Вывод упавшего движка попадает под то же правило — трейсбек печатает путь к файлам продукта, поэтому корень продукта из него отрезается, а «engine/audit.py» остаётся.
- **Информационная часть карточки подписана методикой ТОЙ версии, которой помечена проверка** (T207). Поля связаны кодами (`INF01`, `INF07`), а подпись человеку берётся по коду из методики и на языке, который назвали аргументом `lang`; не названный — язык отчёта. Версии нет на машине — подписи нет вовсе (`null`), и это сказано в `status`: формулировка из соседней версии выглядела бы настоящей, а `null` виден. Отказом отсутствие методики при этом не становится — ответы аудитора читаются и без единого её файла, иначе переставленный `AUDIT_DATA_DIR` прятал бы от человека записанное в базе. Поиск каталога версии общий с письмом (`letters.pinned`), а решение «отказ или пусто» — своё у каждого потребителя.
- **Пустая информационная часть — это ответ, написанный словами.** Пустота значит две разные вещи, и различить их изнутри нечем: аудитор пропустил все поля (D070) либо проверка слита до T200. Пустой раздел молча читался бы как первое, поэтому `status` называет оба варианта.
- **Выведенных чисел в ответах нет.** Ни среднего процента по сети, ни разницы между двумя проверками точки. Такого числа никто не записывал, а в ответе агента оно немедленно начинает цитироваться как официальная оценка. Счёт (сколько проверок, точек, находок), распределение записанных букв и ссылки на лучшую и худшую записанные проверки несут тот же сигнал, ничего не выдумывая.
- **Период задаётся двумя датами, а не словом.** «За квартал» пришлось бы разбирать догадкой о том, что имел в виду человек; спрашивающий агент знает сегодняшнее число и назовёт границы точно. Обе границы включительно, фильтр идёт по дате обхода точки, а не по дате попадания в базу.
- **Предел выдачи и его потолок не переписаны в этот блок.** И значение по умолчанию, и проверка границ живут в одном месте — в `src/db/queries.py`; здесь только прокидывание. Второй экземпляр числа разошёлся бы с первым.
- **Тесты блока требуют настоящий Postgres** (`requires_db`), как и у `db`. Протокольная часть (авторизация, разбор сообщений, коды ошибок) базы не требует и идёт всегда: HTTP-запросы в тестах настоящие, через сокет на порту, который выбирает система.

## Журнал работы

**T095 — MCP-сервер поверх базы, только чтение (03.09.2026).**

- Окружение, связка «токен → арендатор», разбор заголовка — **сам**: это граница арендаторов, главное свойство блока.
- Три инструмента чтения — **сам**: каждый упирается в ту же границу, и делить её было нельзя.
- Каталог инструментов для `tools/list` (объявления и JSON Schema) — **исполнитель** (`forge-executor`): механическая декларация по готовому контракту, границы не касается; сверка схем с сигнатурами обработчиков задана тестом.
- JSON-RPC, HTTP-транспорт и авторизация — **сам**: это вход.
- Найдено и починено по ходу: предел выдачи, названный вместе с периодом, до слоя чтения не доезжал вовсе — отбор по датам идёт уже здесь, и `limit=0` тихо обрезал бы прочитанное в пустой список, то есть ответ читался бы как «за этот период проверок нет». Теперь предел проверяется до чтения, а число потолка по-прежнему живёт только в `src/db/queries.py`.
- Все новые тесты проверены порчей, восстановление — копией файла, снятой до порчи. Граница арендаторов испорчена в обоих местах, где она держится: подмена арендатора по дороге к слою чтения валит 15 тестов инструментов, аргумент `tenant`, перебивающий токен на входе, — тесты сервера. Порча контракта границ модулей (импорт движка из `src.mcp`) ловится `lint-imports`.
- Живой смоук: поднятый `python -m src.mcp` на порту 8265, запросы `curl`. Без токена — 401; один и тот же запрос двумя токенами даёт две разные истории; `tenant` аргументом — отказ `-32602`; проценты, буквы и число находок сошлись с прямым `select` к базе; `GET` отвечает 405.

**T098 — правка методики через агента (03.09.2026).**

- Куда пишем — **сам**, и это главное решение задачи: файлы рядом с боевой методикой, версиями, а не база. Разбор — раздел «Куда пишется правка методики и почему туда». Ответа владельца задача не потребовала: движок читает файлы, отпечаток версии считается по их байтам, и остальное из этого следует.
- Хранилище версий, вызов движка подпроцессом, проверка до записи, журнал, публикация — **сам**: это запись в методику управляющей компании, делить её было нельзя.
- Право на методику и заслон на входе — **сам**: это граница арендаторов.
- Десять инструментов методики поверх хранилища — **сам**: каждый упирается в ту же запись.
- Каталог инструментов для `tools/list` (десять объявлений, JSON Schema, описания для агента) и правка теста каталога — **исполнитель** (`forge-executor`): механическая декларация по готовым сигнатурам обработчиков, записи и границы не касается; расхождение схемы с кодом ловится тестом, который уже стоял.
- Найдено и решено по ходу: правка по умолчанию отсчитывается **не от действующей версии, а от последней записанной**. Публикация отдельная (D049), поэтому действующая версия после первой правки остаётся прежней — и вторая правка подряд, отсчитанная от неё, молча потеряла бы первую, а опубликован оказался бы набор без неё.
- Найдено и решено по ходу: правка, не изменившая ни байта, — отказ, а не «новая версия» с тем же отпечатком. Иначе в журнале появлялась бы правка, которой не было.
- Два теста T095 пришлось переписать: они утверждали «инструментов пять» и «пишущих инструментов нет». Первое стало неверным, второе сузилось до того, что осталось верным и важным, — **проверки** по-прежнему только читаются, и проверяется это по виду инструмента, а не по списку имён.
- Все новые тесты проверены порчей (14 порч, каждая — снятие ровно одной защиты). Одна порча сначала **не поймалась**: снятие проверки имени версии не меняло поведения, потому что ниже стоял второй сторож «такого каталога нет». Тест был переписан так, чтобы проверять настоящий побег — за `..` кладётся существующий каталог с настоящим `checklist.csv`, — и после этого порча ловится. Побег без проверки имени работает: это была не формальность.
- Живой смоук: поднятый `python -m src.mcp` на порту 8266 поверх **копии** боевой методики (136 пунктов), запросы `curl`. Пункт без критериев — отказ словами движка; пункт с критериями — версия `imf-2026-09-03-6d5c230f24b8` рядом с `local-9aa0d34cea21`; публикация до перенастройки `AUDIT_DATA_DIR` — отказ; после перенастройки публикация прошла, и `audit.py index` начал показывать новый пункт; откат на прежнюю версию убрал его обратно. `domain.checklist_version()` совпал с именем каталога опубликованной версии. Боевая `data/` сверена по md5 до и после — не изменилась.

## Открытые вопросы к владельцу

- **Партнёрские наборы методики.** Сегодня методика одна на всю сеть, и правка не разделена по арендаторам: хранилище одно, доступ к нему — привилегия, названная в `.env`. `docs/02-domain.md` говорит, что «у партнёров со временем появятся свои наборы»; когда это случится, хранилищу понадобится измерение арендатора, а инструментам — понимание, чей набор они правят.

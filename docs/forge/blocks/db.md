# Блок: db

## Назначение

Дать проверкам место, где они живут после завершения: Postgres (сегодня и до отдельного решения — локальный, D061) плюс S3-совместимое хранилище под кадры. Идущая проверка остаётся в файле — база принимает уже завершённую (D027, D053).

**Площадка — только переменные окружения.** База через `DATABASE_URL`, хранилище через `S3_*`; зашитых адресов нет, и это сторожится проверкой, а не обещанием (`tests/test_db_stand.py`). Переезд на Supabase — правка значений в `.env`, без изменений в коде (D061).

## API-контракт

```python
push_inspection(chat_id: int) -> str          # id проверки в базе; повторный вызов не создаёт дубль
upload_photos(inspection_id: str, *, fetch: Callable[[str], bytes | None],
              allow_missing: bool = False) -> int   # сколько кадров выгружено в хранилище
list_inspections(*, tenant: str, unit: str | None = None,
                 date_from: date | None = None, date_to: date | None = None,
                 limit: int = 100) -> list[InspectionRow]   # арендатор обязателен (T110)

# чтение проверки целиком и находок (T114); арендатор так же обязателен
get_inspection(inspection_id: str, *, tenant: str) -> InspectionDetail | None
findings_by_unit(*, tenant: str, unit: str,
                 limit: int = 100) -> list[FindingRow]

# справочник точек и карта синонимов (T092)
upsert_unit(name: str, *, code: str | None = None,
            aliases: tuple[str, ...] = (), tenant: str = "default") -> str   # id точки
resolve_unit(name: str, *, tenant: str = "default") -> Unit | None           # по любому написанию
list_units(*, tenant: str = "default") -> list[Unit]
```

**Почему у `upload_photos` появился `fetch`, которого не было в первой записи контракта.**
Байты кадра берутся у вызывающего, а не качаются этим блоком: токен телеграма
есть только у бота (`src/bot/photos.py`), а контракт границ модулей запрещает
`db` импортировать `bot` — прогон падает на `lint-imports`. Тот же приём уже
применён в сборке отчёта: `report.build_pdf` принимает готовую карту
«ссылка → файл». `allow_missing` повторяет там же принятое решение: пропавший
кадр по умолчанию останавливает работу и называется поимённо, а залить без
него можно только явно.

Никто, кроме `domain`, не открывает `inspection.json`; никто, кроме `db`, не ходит в базу.

`upload_photos` реализован (T094) и новой миграции не потребовал: `photos.storage_path`/`uploaded_at` были заложены формой ещё в `0001`.

`domain`.

## Definition of Done блока

- [x] Схема заведена миграциями, а не руками: арендатор, точка, проверка, находка, кадр, версия чек-листа. — `src/db/migrations/0001_initial_schema.sql`, раннер `src/db/migrate.py` (`make migrate`), накат проверен на пустой базе и повторно (идемпотентно), правка уже применённого файла задним числом останавливает накат явной ошибкой.
- [x] В каждой проверке записана версия методики, по которой она посчитана — отчёт остаётся объяснимым после правки чек-листа (D033, D050). — колонка `inspections.checklist_version`, то же значение, что даёт `domain.checklist_version()`.
- [x] Формулировки хранятся строками `(entity_id, lang, text)`, сущности связаны кодами — добавление языка не требует миграции (D025). — таблица `translations(entity_type, entity_id, field, lang, text)`: текст и комментарий находки, подпись оценки. Методика чек-листа (процессы/вопросы, `data/checklist.csv`) в базу не переносится — это не проверка, а справочник домена, вне контракта этого блока.
- [x] Заложена связь повторной проверки с исходной. Функция удвоения не строится: снята решением команды до следующего года (D029). — колонка `inspections.repeat_of_id`, всегда `NULL`: домен пока не отдаёт эту связь (форма есть, источника данных нет).
- [x] Слив идёт на завершении проверки и повторяем: второй вызов не создаёт дубль. — `push_inspection` (T093), идемпотентность через уникальный отпечаток содержимого (`source_fingerprint`), не через локальную отметку в файле.
- [x] Падение базы не роняет проверку на точке: аудитор получает PDF, непролитая проверка видна и доливается позже. — любой отказ слива (нет связи, оборвалась транзакция) уходит одним типом `PushError`, файл состояния не трогается; сборка PDF (`report.build_pdf`) от `db` не зависит вовсе.
- [x] Кадры выгружаются в хранилище за S3-совместимым интерфейсом; смена хранилища — правка конфига (D004, D054). — `upload_photos` (T094), драйвер `src/db/storage.py`, доступ из `S3_*`. В `photos.storage_path` ложится `s3://корзина/inspections/<id проверки>/<id кадра>.jpg`, `telegram_file_id` остаётся историей. Подписанный URL в базу не пишется намеренно: он протухает и стал бы новой мёртвой ссылкой.
- [x] Настоящие данные не трогаются проверками: смоук идёт на своей схеме и убирается за собой. — каждый тест поднимает одноразовую базу (`dodo_audit_test_<hex>`) и удаляет её в teardown; проектная база (`dodo_audit_service`) тестами не используется, только вручную для `make migrate`.

## Технические заметки

- **Драйвер — `psycopg[binary]==3.2.13` (синхронный), не SQLAlchemy/Alembic.** Черновое исследование стека (`docs/forge/research-report.md`) называло SQLAlchemy 2.x + asyncpg + Alembic для сценария «Postgres с первого дня под состояние проверки» — сценарий, от которого в итоге отказались (D007: состояние осталось файлом). Здесь другая задача: редкий синхронный слив по готовому срезу данных, без ORM и без async-контекста — весь остальной код блоков синхронный (`OpenAI`, не `AsyncOpenAI`, в `src/recognize/client.py`). Миграции — пронумерованные `.sql`-файлы и раннер на полсотни строк (`src/db/migrate.py`) с таблицей `schema_migrations` и проверкой отпечатка вместо Alembic: рассматривался `yoyo-migrations`, но его postgres-экстра тянет `psycopg2` — второй драйвер Postgres рядом с уже выбранным `psycopg3` ради экономии полусотни строк не оправдан.
- **`src/db/__init__.py` не импортирует `push_inspection`/`list_inspections` заранее** — они лениво подгружаются через `__getattr__` (PEP 562) при первом обращении. Иначе любой импорт из блока (даже `src.db.units`, чистая функция без Postgres) требовал бы установленного `psycopg` — проверено: без этого приёма сбор тестов падает целиком в окружении, где зависимость ещё не поставлена.
- **Точка сопоставляется через справочник и карту синонимов** (T092): сперва
  каноничное название, потом синоним, оба по одному правилу нормализации
  (`normalize_unit_name`: обрезка краёв, схлопывание внутренних пробелов,
  `casefold`). «БГ2» и «Белград 2» ложатся в одну точку, если синоним заведён.
  Порядок ветвей в запросе задан **явной колонкой приоритета**, а не тем, что
  название написано в запросе раньше: `union all` порядка строк не обещает, и
  на этом же коде проверка «каноничное название сильнее синонима» то проходила,
  то падала, пока приоритет не стал явным. Справочник может быть пуст — тогда
  точка заводится по нормализованному названию, как до T092: незаполненный
  справочник не повод отказать в сливе проверки, которая уже сделана.
- **Ввод названия текстом задачей T092 не отменяется** (D051). Форма данных и
  связывание по идентификатору — здесь; выбор точки из списка вместо ввода
  строкой это работа блока `bot`, и она не делалась. Боту для неё достаточно
  `list_units()` (каноничное название + синонимы) и `resolve_unit()` для
  подсказки по введённой строке; `start_inspection` при этом продолжает
  принимать строку — идентификатор проверка получает при сливе.
- **Хранилище — `boto3` по S3-совместимому интерфейсу, а не SDK поставщика.**
  Привязываться к Supabase нельзя (D061), а S3-совместимый интерфейс есть и у
  него, и у AWS, и у локального сервера — поэтому переезд остаётся правкой
  `S3_*` в `.env`. Рассматривался `minio` (втрое легче: 2,9 МБ против 15 МБ с
  botocore, и несёт свои типы), но отклонён по тестуемости: `moto` подменяет
  именно `botocore`, поэтому с `minio` прогон блока требовал бы поднятого
  сервера и пропускался бы там, где Docker недоступен. Корзины драйвер не
  создаёт: в настоящем хранилище таких прав у продукта нет и быть не должно.
- **В базу пишется `s3://корзина/ключ`, а не подписанный URL.** Подписанный
  протухает за часы и стал бы ровно той мёртвой ссылкой, ради которой задача и
  заводилась. Открытая ссылка для человека собирается из этой в момент показа —
  когда появится веб; в контракт блока это не входит.
- **Локальное хранилище для смоука — `adobe/s3mock` профилем `storage`.**
  MinIO не взят осознанно: его репозиторий архивирован в апреле 2026, новых
  патчей community-издание не получит, и корзину там пришлось бы заводить
  отдельным контейнером. У s3mock корзина создаётся переменной `initialBuckets`,
  лицензия Apache-2.0, образ есть под arm64 (проверено запуском). Тома у стенда
  нет намеренно: это площадка для смоука, а не место, где можно держать кадры.
- **Разделение арендаторов держится схемой, а не дисциплиной запросов.** И
  синоним, и сама проверка ссылаются на точку составной ссылкой
  `(tenant_code, unit_id) → units (tenant_code, id)`. До этого ссылка шла на
  один `units.id`, то есть синоним арендатора A мог указывать на точку
  арендатора B, и `resolve_unit(name, tenant="A")` отдал бы чужую пиццерию,
  ничем себя не выдав. Живого дефекта не было только потому, что арендатор в
  продукте один, — а это соглашение в коде, которое нечем проверить.
- **RLS в схеме нет, и это осознанно** (D061): база сегодня локальная, к ней
  ходит один процесс бота под одной ролью, и политик не на что вешать. Как
  только к базе получит доступ клиент (PostgREST в Supabase, будущий веб для
  партнёров) — построчные политики становятся обязательными, и обязательными
  же становятся два свойства, которых сегодня нет: запрет правки уже
  завершённой проверки статусом в самой политике, а не соглашением в коде, и
  `as restrictive` там, где политика должна сужать (разрешающие политики в
  PostgreSQL объединяются через ИЛИ, поэтому «сужающая» разрешающая не сужает
  ничего). Это работа отдельной задачи, не этой волны.
- **Арендатор в чтении — обязательный параметр, а не фильтр** (T110). Миграция
  `0002` сделала связи мультиарендными, а точка чтения осталась общей на всех:
  `_LIST_ALL_SQL` не фильтровал по `tenant_code` вовсе, а фильтр по точке шёл по
  `u.name_normalized` без арендатора — то есть мимо ведущей колонки составного
  индекса и мимо разделения арендаторов сразу. Живого дефекта не было только
  потому, что арендатор один; но читает через этот слой MCP-сервер (T095),
  который мы сами даём в руки агенту партнёра. Необязательный фильтр там
  однажды не передадут, поэтому у `tenant` нет значения по умолчанию: вызов без
  него падает `TypeError`, а не отдаёт молча чужую историю. Пустая строка —
  отдельный отказ: она не совпала бы ни с чем и вернула бы «проверок нет»
  вместо ошибки. Соединение с точкой идёт составной ссылкой
  `(tenant_code, id)`, той же, что завела `0002`: чужую точку оно не подтянет,
  даже если фильтр когда-нибудь потеряется.
- **Предел выдачи есть всегда, и у него есть потолок.** `limit` по умолчанию
  100, больше `MAX_LIMIT = 1000` — отказ: `limit=10_000_000` это тот же полный
  проход, только записанный так, будто ограничение есть. Под запрос заведён
  индекс: сперва `inspections_tenant_pushed_at_idx (tenant_code, pushed_at desc)`
  (миграция `0003`, прежний односоставный `inspections_tenant_idx` снят там же
  как избыточный префикс), с T114 — `inspections_tenant_date_idx`, потому что
  порядок выдачи стал считаться по дате обхода (см. заметку про D035 ниже).
  План закреплён тестом, а не замером в отчёте: убранный индекс валит его.
- **Период отбирает база, а не потребитель поверх прочитанной страницы**
  (T114). До этой задачи `date_from`/`date_to` разбирал у себя блок `mcp`: он
  читал страницу по потолку и фильтровал её в памяти. Это работало ровно до
  D035 — историю за три года зальют одним заходом программно, и `pushed_at` у
  всей истории окажется одной датой. После этого «первая страница по дате
  слива» и «проверки за период» не связаны никак, и потерянные проверки видны
  не будут: ответ выглядит обычным списком, просто не тем. Границы стоят в
  тексте запроса ВСЕГДА, незаданная подставляется как `-infinity`/`infinity`:
  так текст один и тот же при любых аргументах, а его план — проверяемый (иначе
  под каждое сочетание фильтров пришлось бы держать свой текст, и проверять
  пришлось бы восемь планов вместо двух).
- **«Свежие впереди» считается по дате ОБХОДА точки, а не по дате слива**
  (T114). Это то же следствие D035, и без него перенос фильтра в SQL был бы
  половиной починки: при одинаковом `pushed_at` порядок строк ничем не задан,
  и «последние сто проверок» превращаются в случайную сотню, ничем себя не
  выдающую. Порядок теперь `inspection_date desc, pushed_at desc` — вторым
  ключом дата слива разводит проверки одного дня. Проверено на залитой истории
  в 1200 проверок с одной датой слива: до правки первыми шли самые старые.
- **Индексы под чтение переставлены, старый снят** (миграция `0005`).
  `(tenant_code, inspection_date desc, pushed_at desc)` — «проверки арендатора
  за период», `(tenant_code, unit_id, inspection_date desc, pushed_at desc)` —
  «история одной точки» и находки точки (они идут через те же проверки).
  Проверено планировщиком на 10 000 проверок у двух арендаторов и сорока точках
  (одна точка на арендатора планировщику не показательна: с ней он выбирает не
  тот план, что на настоящих данных): выборка за месяц — `Index Scan using
  inspections_tenant_date_idx`, 31 строка, 0,080 мс; выборка без периода —
  тот же индекс, без сортировки, 0,164 мс; история точки за период — `Index
  Scan using inspections_tenant_unit_date_idx`. Что второй индекс не украшение,
  проверено его снятием на той же базе: без него планировщик уходит на
  `Bitmap Index Scan on inspections_unit_idx` и читает ВСЮ историю точки
  (200 строк вместо сотни отданных), а с тремя годами истории разрыв только
  растёт. Индекс `0003` по `pushed_at` снят: после этой задачи по нему не
  сортирует и не отбирает ни один запрос (проверено поиском по `src/`), а
  неиспользуемый индекс стоит записи на каждом сливе. Планы закреплены тестами по ТЕКСТУ ЗАПРОСА ИЗ МОДУЛЯ, а не по
  переписанной от руки копии: копия обещает не то, что выполняет код.
- **Находки читаются вместе с проверкой, а не отдельным запросом на строку.**
  В `FindingRow` лежат `inspection_id`, `unit_name` и `inspection_date`:
  находка без даты и точки не отвечает ни на один вопрос, ради которого её
  читают. Формулировка и комментарий берутся из `translations` подзапросами по
  первичному ключу той же таблицы и **на языке речи той проверки**, в которой
  находка записана, — язык отдаётся полем `lang`, а не подразумевается.
  Проверено планировщиком: `Index Scan using translations_pkey`, и выполняются
  подзапросы только для строк, попавших в выдачу (`loops=100` при пределе 100),
  а не для всех прочитанных.
- **`text`/`comment` могут быть `None`, и это не то же самое, что пустая
  строка.** `None` — строки перевода нет вовсе; ненаписанный комментарий и
  ненайденный перевод обязаны различаться, иначе «искать надо в другом месте»
  выглядит как «аудитор ничего не написал». А вот у `source` NULL и пустая
  строка склеены намеренно: «источник не записан» не бывает двух разных видов.
- **У `get_inspection` арендатор проверяется в ОДНОМ месте, и это осознанно.**
  Находки достаются вторым запросом уже по идентификатору проверки, без
  повторного фильтра по арендатору: проверку с чужим арендатором первый запрос
  не вернёт вовсе, а находка не может принадлежать другой проверке — это
  внешний ключ. Второй заслон поверх первого нельзя было бы снять и увидеть
  красное, то есть проверить, что он работает, стало бы нечем (тот же довод,
  что в миграции `0004` про один заслон вместо двух). У `findings_by_unit`
  арендатор, наоборот, единственный заслон — и он проверяется снятием.
- **Чужая проверка по настоящему идентификатору отвечает «нет», а не
  «не ваша».** Разные ответы подтверждали бы существование чужого документа
  тому, кто перебирает идентификаторы. Кривой идентификатор при этом — отказ,
  а не «не найдено»: опечатка в аргументе, спрятанная за правдоподобным
  ответом, не чинится, потому что её никто не замечает.
- **Предел `findings_by_unit` ограничивает выдачу, но не всегда обрывает
  чтение.** Порядок внутри проверки — по номеру записи `f.n`, а его из индекса
  не возьмёшь, поэтому планировщик досортировывает: на прогоне видели оба
  исхода — полную сортировку отобранного (200 находок точки, 3,9 мс) и
  инкрементальную, которая с пределом останавливается сама. У точки с тремя
  годами истории первый случай означает тысячи строк ради сотни отданных.
  Оставлено как есть осознанно: убрать `f.n` из порядка значило бы отдавать
  находки одной проверки вперемешку, а `n` — это ровно тот номер, которым
  запись названа в отчёте у человека.
- **Весь слой чтения остался одним файлом.** Разнести находки в отдельный
  модуль не вышло без третьего файла под сторожа: `get_inspection` возвращает и
  шапку, и находки, поэтому разбор строк нужен обоим модулям, а сторожа
  арендатора и предела — тоже обоим. Два модуля, ссылающиеся друг на друга,
  дали бы круговой импорт, три — лишнюю прослойку ради ста строк. Файл ~400
  строк, потолок проекта 800.
- **Карту синонимов (T092) выборка не спрашивает.** `list_inspections(unit="БГ2")`
  не найдёт проверок точки «Белград 2», хотя слив их связал бы. Это осознанно
  оставлено как есть: потребителя у такого поиска пока нет, а расширять чтение
  заодно с починкой утечки — значит смешать в одном изменении две разные вещи.
- **`list_units` сортирует по названию средствами базы, и на кириллице с
  цифрой порядок не тот, что ожидает глаз.** Проверено на Postgres 16 с
  коллейшном `en_US.UTF-8`: `'Белград' < 'Ниш'` истинно, а `'Белград 2' <
  'Ниш 1'` — уже нет. Потребителя у порядка пока нет (список точек боту не
  показывается), поэтому здесь ничего не подкручено; когда список пойдёт
  человеку, сортировать его придётся осознанно, а не полагаться на `order by`.
- **Шапка письма читается вместе с проверкой** (T176). `auditor`, `city`,
  `partner`, `contact` пишутся сливом с самого T091, но три запроса чтения их
  не выбирали, а `InspectionRow` их не отдавал. Наружу это выходило не отказом
  и не пустым списком, а испорченным документом: письмо, пересобранное по
  записанной проверке (`src/mcp/letters.py`), подписывалось прочерком вместо
  имени аудитора, и движок при этом выходил с нулевым кодом. Пустая строка и
  здесь означает «поле не заполнено», а не «поля нет» (колонки объявлены
  `not null default ''`, мастер бота даёт их пропустить): `None` вместо неё
  напечатался бы у потребителя словом «None» в подписи документа партнёру —
  это тот же довод, по которому `source` склеивает NULL с пустой строкой, и
  обратный тому, по которому `text`/`comment` его не склеивают.
- **Вид проверки в базе — КОД, и отказ на расхождении версии методики теперь
  отличим по типу** (T178). Код в колонке `inspections.kind` был там с T152, но
  схема об этом молчала: рядом стоит `units.name` с человеческим названием, и
  `kind text not null` читается так же — а слово в этой колонке не отказывает,
  оно молча перестаёт переводиться (ровно так партнёр получал письмо со словом
  на чужом языке до T152). Миграция `0006` объясняет колонку в самой базе;
  ограничения `check (kind in (...))` намеренно нет — перечень видов живёт в
  `domain.kinds`, и переписанный в схему он стал бы второй копией, забытая
  половина которой отказывала бы на сливе, то есть на точке. Отдельно проверено,
  что смена значения в отпечатке не сломала идемпотентность: повторный слив
  считается ПЕРЕСЧЁТОМ СТРОК арендатора, а не совпадением возвращённых
  идентификаторов — дубль отдал бы другой id, и сверка id с id о числе строк не
  говорит ничего.

  Вторая половина задачи — `push_inspection` зовёт подсчёт оценки, а тот
  отказывает при расхождении версии методики (T148). Ловилось это вместе со
  всеми `DomainError` и уходило общим `PushError`: бот разбирает исходы слива
  по ТИПУ (`ConfigError` — базы нет, прочий `DbError` — база не приняла), и
  расхождение попадало во вторую ветку, то есть аудитор получал сообщение про
  базу, которая в полном порядке. Заведён `VersionMismatchError(PushError)` с
  полями `recorded`/`current`: наследник, а не сосед, — ловящий блок целиком не
  должен падать от появления более точного типа, а разбирать этот случай
  отдельно ему придётся. Полями, а не текстом: текст пишется человеку и
  правится, ветка кода обязана выбираться типом.
- **Предложение модели лежит рядом с записью, а «что аудитор изменил»
  считается сравнением** (T164, D077). До этой задачи сигнал о промахе терялся
  целиком: ни предложенного пункта, ни уверенности, ни того, что аудитор
  поправил. Теперь у находки четыре колонки (`suggested_code`,
  `suggested_level`, `suggested_zone`, `suggested_confidence`), а «что
  поправлено» отдаёт `FindingRow.corrections()` — сравнением двух троек ОДНОЙ
  строки. Хранить это третьей копией нельзя: она разъехалась бы с парой, из
  которой считается, и разъехалась бы молча, потому что сверять её было бы не с
  чем.

  Три различения, каждое из которых стоит того, чтобы их не слить:
  `NULL` (модель не предлагала ничего — ручная запись или запись до T164)
  против `NONE`/`UNKNOWN` (модель ответила «ничего не подходит» / «места не
  видно» — это её ответ); пустая строка склеена с `NULL` ещё на сливе, иначе
  она выглядела бы ответом модели и не совпала бы с записанным пунктом, то есть
  попала бы в выборку промахов, где модели не было вовсе; и «модель попала»
  (предложение есть, `corrections()` пуст) против «модели не спрашивали» —
  различает их наличие предложения, а не пустота списка правок.

  **Предложение НЕ входит в отпечаток проверки** — в отличие от `source`.
  Отпечаток — содержимое документа, а предложение это метаданные о том, как
  запись появилась. Попади оно в отпечаток, проверка, слитая до появления
  предложения и слитая после, дала бы две строки в истории точки — ровно то,
  от чего отпечаток и стоит. Проверено тестом, а не рассуждением.

  Уверенность проверяется дважды и намеренно: `numeric(4, 3)` плюс
  `check ... between 0 and 1` в схеме (заслон в коде снимается вместе с кодом, а
  историю за прошлые годы зальют программно, D035) и разбор в сливе — чтобы
  отказ назвал число и номер записи. У нарушенного `check` psycopg показывает
  имя ограничения и точность типа, а не то, что чинить: проверено снятием
  разбора — отказ стал «numeric field overflow ... precision 4, scale 3».
  Булево значение отвергается отдельной ветвью: `bool` — подкласс числа, и
  `float(True)` тихо дал бы 1.0, то есть «модель уверена полностью».

  **Боевой список слов этим не пополняется, и это запрет, а не недоделка**
  (D077): быстрый путь показывает пункт без подтверждения (D064), поэтому
  неверное слово уехало бы в отчёт партнёру без чьего-либо ведома. Собирать
  предложения для управляющей компании — задача T165 блока `mcp`. Индекса под
  такую выборку здесь нет: какой вопрос она задаст, сегодня неизвестно, а
  индекс под воображаемый запрос стоит записи на каждом сливе.
- **Сырые слова аудитора — колонка у находки, а не строка перевода** (T185,
  T183). Материал, из которого выросла запись (подпись к кадру, отдельное
  сообщение, расшифровка голоса), лежит в `findings.words` и читается обоими
  запросами находок полем `FindingRow.words`. В `translations` ему не место, и
  это не вопрос удобства: там живут ФОРМУЛИРОВКИ — их переводят, и добавление
  языка не должно требовать миграции (D025). Слова аудитора не формулировка, а
  показание о моменте: язык у них ровно один — тот, на котором говорили
  (`inspections.speech_lang`, наружу — поле `lang` рядом), — и перевод от
  сигнала о промахе не оставил бы ничего. Положенные в `translations`, они
  получили бы вместе с местом и повадки соседей: слив пишет туда
  `on conflict do update set text = excluded.text`, то есть речь стала бы
  перезаписываемой ровно там, где её нельзя переписывать.

  **Пишутся один раз и не меняются, и держит это схема.** Правят такое ровно
  тогда, когда промах уже заметили, — то есть стирают сигнал в момент его
  появления. Своего заслона под слова не заведено намеренно: запись
  запечатанной проверки заморожена целиком политикой
  `findings_frozen_with_inspection` из `0004`, и слова замерзают вместе с ней.
  Второй запрет на том же месте нельзя было бы снять и увидеть красное —
  тот же довод, что в `0004` про права и политику. Проверено под ролью
  приложения (не суперпользователем, тот обходит RLS всегда): `UPDATE` слов
  завершённой проверки даёт ноль строк, значение остаётся прежним, а
  разрешающая политика вместо ограничивающей валит проверку.

  **Пустота одна.** `NULL` в базе и пустая строка наружу означают одно — слов
  не записано; двух видов у этого нет, поэтому они склеены, как у `source`.
  Отличить «слов не было вовсе» (разбор голого кадра) от «запись сделана до
  T183» можно самим `source` — так же, как это делает домен. Пробельная строка
  считается пустотой: молчание не речь, а пробелы в колонке выглядели бы
  фразой аудитора, у которой не прочитать ни слова. Всё остальное пишется
  ДОСЛОВНО, без обрезки краёв: расшифровка голоса приходит несколькими
  строками, и подправленное по дороге показание сверять уже не с чем.

  **В отпечаток проверки слова НЕ входят** — как и предложение модели, и по
  той же причине: отпечаток это содержимое документа, ушедшего партнёру, а
  сказанное на точке партнёру не предназначено вовсе. Попади слова в
  отпечаток — одна и та же проверка, слитая до этой задачи и слитая после,
  дала бы две строки в истории одной точки. Закреплено тестом и проверено на
  живой базе: та же проверка со словами и без них даёт один отпечаток и один
  идентификатор.

  Асимметрия с `source` **снята задачей T193 (#158)**: источник записи ушёл из
  отпечатка тем же доводом. Как это сделано безопасно — следующая заметка.
- **Смена рецепта отпечатка совместима с уже слитым (T193, #158).** Отпечаток —
  не просто число, а идентичность строки, которая УЖЕ лежит в базе. Сменив
  рецепт, мы объявляем каждую слитую проверку неизвестной: повторный слив не
  найдёт её и положит второй строкой в историю точки. Разделить эти две строки
  обратно нечем — миграция `0004` запрещает запечатанную проверку и править, и
  удалять. Ошибка необратима, в отличие почти от любой другой в этом блоке.

  Пересчитать отпечатки в базе миграцией **нельзя**, и это не лень: раннер
  накатывает чистый SQL, а рецепт — `json.dumps(..., sort_keys=True,
  ensure_ascii=False)` поверх данных, часть которых лежит в другой таблице
  (`text` и `comment` находки — в `translations`, строкой на язык). Повторить
  это в SQL байт в байт можно, а вот убедиться, что повторено верно, — только
  сравнением с тем же Python; цена ошибки при этом та же необратимая двойная
  строка.

  Поэтому рецепты не переписываются, а **накапливаются**:
  `fingerprint.previous_fingerprints` отдаёт ту же проверку по вышедшим из
  употребления рецептам, а `push._push` сверяется с ними ДО любой записи —
  проверка, лежащая под прежним отпечатком, находится и отдаёт свой прежний
  `id`. Строк в базе сегодня ноль, но убедиться в этом можно только на своей
  машине: базы владельца и площадки отсюда не видны, а правило дешевле такой
  проверки и не зависит от неё. Запись уходит из списка рецептов не когда
  рецепт надоел, а когда известно, что строк того рецепта не осталось нигде.
- **Тесты блока требуют настоящий Postgres.** `DATABASE_URL` не задан в окружении прогона — тесты пропускаются (`requires_db` в `tests/conftest.py`), как и `requires_data` у домена. Локально проверено на Postgres 16.14, база `dodo_audit_service`, создана этим блоком (`CREATE DATABASE ... OWNER garva`), соседние базы `dodo_pnl_*` не тронуты.

## Как устроен блок

Наружу торчат слив, чтение и справочник точек (`src/db/__init__.py`, лениво
через `__getattr__`), остальное — внутренности:

| Файл | Что в нём |
|---|---|
| `src/db/push.py` | `push_inspection` — сборка отпечатка, транзакция, идемпотентная запись |
| `src/db/queries.py` | `list_inspections`, `get_inspection`, `findings_by_unit` — только чтение |
| `src/db/photos.py` | `upload_photos` — выгрузка кадров, отметка ссылки в базе |
| `src/db/storage.py` | `PhotoStorage` (узкий интерфейс) и драйвер S3 |
| `src/db/fingerprint.py` | `compute_fingerprint` — чистая функция, без базы; `previous_fingerprints` — те же данные по прежним рецептам, чтобы смена рецепта не задваивала слитое (T193) |
| `src/db/units.py` | `normalize_unit_name` — ключ сопоставления точки |
| `src/db/migrate.py` | раннер миграций, таблица `schema_migrations`, `python -m src.db.migrate` / `make migrate` |
| `src/db/migrations/0001_initial_schema.sql` | схема целиком |
| `src/db/migrations/0002_unit_directory.sql` | справочник точек, карта синонимов, составные ссылки на арендатора |
| `src/db/migrations/0003_tenant_scoped_reads.sql` | индекс под арендаторское чтение с пределом |
| `src/db/migrations/0004_finalized_write_protection.sql` | статус проверки, роль приложения, построчные политики: завершённую проверку нельзя переписать |
| `src/db/migrations/0005_reads_by_period.sql` | индексы под чтение за период и по точке; снят индекс по дате слива |
| `src/db/migrations/0006_kind_is_a_code.sql` | пояснение к колонке вида проверки: там код, а не слово (перечень и переводы — в `domain.kinds`) |
| `src/db/migrations/0007_model_suggestion.sql` | предложение модели рядом с записью: пункт, класс, зона, уверенность (T164, D077) |
| `src/db/migrations/0008_auditor_words.sql` | сырые слова аудитора рядом с записью: показание о моменте, из которого выросла запись (T185, T183) |
| `src/db/config.py` | `DATABASE_URL` → `Settings`, `S3_*` → `StorageSettings` |
| `src/db/errors.py` | `DbError`, `ConfigError`, `PushError`, `StorageError` |
| `src/db/models.py` | `InspectionRow`, `FindingRow`, `InspectionDetail` |

Расчёта оценки в блоке нет и быть не может: `push_inspection` берёт `Score` из
`domain.score()` как есть и кладёт в `inspections.pct`/`grade`/`counts`/`by_zone`
без единой операции над числами.

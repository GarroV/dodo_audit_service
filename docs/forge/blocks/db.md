# Блок: db

## Назначение

Дать проверкам место, где они живут после завершения: Postgres (сегодня и до отдельного решения — локальный, D061) плюс S3-совместимое хранилище под кадры. Идущая проверка остаётся в файле — база принимает уже завершённую (D027, D053).

**Площадка — только переменные окружения.** База через `DATABASE_URL`, хранилище через `S3_*`; зашитых адресов нет, и это сторожится проверкой, а не обещанием (`tests/test_db_stand.py`). Переезд на Supabase — правка значений в `.env`, без изменений в коде (D061).

## API-контракт

```python
push_inspection(chat_id: int) -> str          # id проверки в базе; повторный вызов не создаёт дубль
upload_photos(inspection_id: str, *, fetch: Callable[[str], bytes | None],
              allow_missing: bool = False) -> int   # сколько кадров выгружено в хранилище
list_inspections(unit: str | None = None) -> list[InspectionRow]

# справочник точек и карта синонимов (T092)
upsert_unit(name: str, *, code: str | None = None,
            aliases: tuple[str, ...] = (), tenant: str = "default") -> str   # id точки
resolve_unit(name: str, *, tenant: str = "default") -> Unit | None           # по любому написанию
list_units(*, tenant: str = "default") -> list[Unit]
```

**Почему у `upload_photos` появился `fetch`, которого не было в первой записи контракта.**
Байты кадра берутся у вызывающего, а не качаются этим блоком: токен телеграма
есть только у бота (`src/bot/photos.py`), а контракт границ модулей запрещает
`db` импортировать `bot` — прогон падает на `lint-imports`. Тот же приём уже
применён в сборке отчёта: `report.build_pdf` принимает готовую карту
«ссылка → файл». `allow_missing` повторяет там же принятое решение: пропавший
кадр по умолчанию останавливает работу и называется поимённо, а залить без
него можно только явно.

Никто, кроме `domain`, не открывает `inspection.json`; никто, кроме `db`, не ходит в базу.

`upload_photos` реализован (T094) и новой миграции не потребовал: `photos.storage_path`/`uploaded_at` были заложены формой ещё в `0001`.

`domain`.

## Definition of Done блока

- [x] Схема заведена миграциями, а не руками: арендатор, точка, проверка, находка, кадр, версия чек-листа. — `src/db/migrations/0001_initial_schema.sql`, раннер `src/db/migrate.py` (`make migrate`), накат проверен на пустой базе и повторно (идемпотентно), правка уже применённого файла задним числом останавливает накат явной ошибкой.
- [x] В каждой проверке записана версия методики, по которой она посчитана — отчёт остаётся объяснимым после правки чек-листа (D033, D050). — колонка `inspections.checklist_version`, то же значение, что даёт `domain.checklist_version()`.
- [x] Формулировки хранятся строками `(entity_id, lang, text)`, сущности связаны кодами — добавление языка не требует миграции (D025). — таблица `translations(entity_type, entity_id, field, lang, text)`: текст и комментарий находки, подпись оценки. Методика чек-листа (процессы/вопросы, `data/checklist.csv`) в базу не переносится — это не проверка, а справочник домена, вне контракта этого блока.
- [x] Заложена связь повторной проверки с исходной. Функция удвоения не строится: снята решением команды до следующего года (D029). — колонка `inspections.repeat_of_id`, всегда `NULL`: домен пока не отдаёт эту связь (форма есть, источника данных нет).
- [x] Слив идёт на завершении проверки и повторяем: второй вызов не создаёт дубль. — `push_inspection` (T093), идемпотентность через уникальный отпечаток содержимого (`source_fingerprint`), не через локальную отметку в файле.
- [x] Падение базы не роняет проверку на точке: аудитор получает PDF, непролитая проверка видна и доливается позже. — любой отказ слива (нет связи, оборвалась транзакция) уходит одним типом `PushError`, файл состояния не трогается; сборка PDF (`report.build_pdf`) от `db` не зависит вовсе.
- [x] Кадры выгружаются в хранилище за S3-совместимым интерфейсом; смена хранилища — правка конфига (D004, D054). — `upload_photos` (T094), драйвер `src/db/storage.py`, доступ из `S3_*`. В `photos.storage_path` ложится `s3://корзина/inspections/<id проверки>/<id кадра>.jpg`, `telegram_file_id` остаётся историей. Подписанный URL в базу не пишется намеренно: он протухает и стал бы новой мёртвой ссылкой.
- [x] Настоящие данные не трогаются проверками: смоук идёт на своей схеме и убирается за собой. — каждый тест поднимает одноразовую базу (`dodo_audit_test_<hex>`) и удаляет её в teardown; проектная база (`dodo_audit_service`) тестами не используется, только вручную для `make migrate`.

## Технические заметки

- **Драйвер — `psycopg[binary]==3.2.13` (синхронный), не SQLAlchemy/Alembic.** Черновое исследование стека (`docs/forge/research-report.md`) называло SQLAlchemy 2.x + asyncpg + Alembic для сценария «Postgres с первого дня под состояние проверки» — сценарий, от которого в итоге отказались (D007: состояние осталось файлом). Здесь другая задача: редкий синхронный слив по готовому срезу данных, без ORM и без async-контекста — весь остальной код блоков синхронный (`OpenAI`, не `AsyncOpenAI`, в `src/recognize/client.py`). Миграции — пронумерованные `.sql`-файлы и раннер на полсотни строк (`src/db/migrate.py`) с таблицей `schema_migrations` и проверкой отпечатка вместо Alembic: рассматривался `yoyo-migrations`, но его postgres-экстра тянет `psycopg2` — второй драйвер Postgres рядом с уже выбранным `psycopg3` ради экономии полусотни строк не оправдан.
- **`src/db/__init__.py` не импортирует `push_inspection`/`list_inspections` заранее** — они лениво подгружаются через `__getattr__` (PEP 562) при первом обращении. Иначе любой импорт из блока (даже `src.db.units`, чистая функция без Postgres) требовал бы установленного `psycopg` — проверено: без этого приёма сбор тестов падает целиком в окружении, где зависимость ещё не поставлена.
- **Точка сопоставляется через справочник и карту синонимов** (T092): сперва
  каноничное название, потом синоним, оба по одному правилу нормализации
  (`normalize_unit_name`: обрезка краёв, схлопывание внутренних пробелов,
  `casefold`). «БГ2» и «Белград 2» ложатся в одну точку, если синоним заведён.
  Порядок ветвей в запросе задан **явной колонкой приоритета**, а не тем, что
  название написано в запросе раньше: `union all` порядка строк не обещает, и
  на этом же коде проверка «каноничное название сильнее синонима» то проходила,
  то падала, пока приоритет не стал явным. Справочник может быть пуст — тогда
  точка заводится по нормализованному названию, как до T092: незаполненный
  справочник не повод отказать в сливе проверки, которая уже сделана.
- **Ввод названия текстом задачей T092 не отменяется** (D051). Форма данных и
  связывание по идентификатору — здесь; выбор точки из списка вместо ввода
  строкой это работа блока `bot`, и она не делалась. Боту для неё достаточно
  `list_units()` (каноничное название + синонимы) и `resolve_unit()` для
  подсказки по введённой строке; `start_inspection` при этом продолжает
  принимать строку — идентификатор проверка получает при сливе.
- **Хранилище — `boto3` по S3-совместимому интерфейсу, а не SDK поставщика.**
  Привязываться к Supabase нельзя (D061), а S3-совместимый интерфейс есть и у
  него, и у AWS, и у локального сервера — поэтому переезд остаётся правкой
  `S3_*` в `.env`. Рассматривался `minio` (втрое легче: 2,9 МБ против 15 МБ с
  botocore, и несёт свои типы), но отклонён по тестуемости: `moto` подменяет
  именно `botocore`, поэтому с `minio` прогон блока требовал бы поднятого
  сервера и пропускался бы там, где Docker недоступен. Корзины драйвер не
  создаёт: в настоящем хранилище таких прав у продукта нет и быть не должно.
- **В базу пишется `s3://корзина/ключ`, а не подписанный URL.** Подписанный
  протухает за часы и стал бы ровно той мёртвой ссылкой, ради которой задача и
  заводилась. Открытая ссылка для человека собирается из этой в момент показа —
  когда появится веб; в контракт блока это не входит.
- **Локальное хранилище для смоука — `adobe/s3mock` профилем `storage`.**
  MinIO не взят осознанно: его репозиторий архивирован в апреле 2026, новых
  патчей community-издание не получит, и корзину там пришлось бы заводить
  отдельным контейнером. У s3mock корзина создаётся переменной `initialBuckets`,
  лицензия Apache-2.0, образ есть под arm64 (проверено запуском). Тома у стенда
  нет намеренно: это площадка для смоука, а не место, где можно держать кадры.
- **Разделение арендаторов держится схемой, а не дисциплиной запросов.** И
  синоним, и сама проверка ссылаются на точку составной ссылкой
  `(tenant_code, unit_id) → units (tenant_code, id)`. До этого ссылка шла на
  один `units.id`, то есть синоним арендатора A мог указывать на точку
  арендатора B, и `resolve_unit(name, tenant="A")` отдал бы чужую пиццерию,
  ничем себя не выдав. Живого дефекта не было только потому, что арендатор в
  продукте один, — а это соглашение в коде, которое нечем проверить.
- **RLS в схеме нет, и это осознанно** (D061): база сегодня локальная, к ней
  ходит один процесс бота под одной ролью, и политик не на что вешать. Как
  только к базе получит доступ клиент (PostgREST в Supabase, будущий веб для
  партнёров) — построчные политики становятся обязательными, и обязательными
  же становятся два свойства, которых сегодня нет: запрет правки уже
  завершённой проверки статусом в самой политике, а не соглашением в коде, и
  `as restrictive` там, где политика должна сужать (разрешающие политики в
  PostgreSQL объединяются через ИЛИ, поэтому «сужающая» разрешающая не сужает
  ничего). Это работа отдельной задачи, не этой волны.
- **`list_units` сортирует по названию средствами базы, и на кириллице с
  цифрой порядок не тот, что ожидает глаз.** Проверено на Postgres 16 с
  коллейшном `en_US.UTF-8`: `'Белград' < 'Ниш'` истинно, а `'Белград 2' <
  'Ниш 1'` — уже нет. Потребителя у порядка пока нет (список точек боту не
  показывается), поэтому здесь ничего не подкручено; когда список пойдёт
  человеку, сортировать его придётся осознанно, а не полагаться на `order by`.
- **Тесты блока требуют настоящий Postgres.** `DATABASE_URL` не задан в окружении прогона — тесты пропускаются (`requires_db` в `tests/conftest.py`), как и `requires_data` у домена. Локально проверено на Postgres 16.14, база `dodo_audit_service`, создана этим блоком (`CREATE DATABASE ... OWNER garva`), соседние базы `dodo_pnl_*` не тронуты.

## Как устроен блок

Наружу торчат две функции (`src/db/__init__.py`, лениво через `__getattr__`), остальное — внутренности:

| Файл | Что в нём |
|---|---|
| `src/db/push.py` | `push_inspection` — сборка отпечатка, транзакция, идемпотентная запись |
| `src/db/queries.py` | `list_inspections` — только чтение |
| `src/db/photos.py` | `upload_photos` — выгрузка кадров, отметка ссылки в базе |
| `src/db/storage.py` | `PhotoStorage` (узкий интерфейс) и драйвер S3 |
| `src/db/fingerprint.py` | `compute_fingerprint` — чистая функция, без базы |
| `src/db/units.py` | `normalize_unit_name` — ключ сопоставления точки |
| `src/db/migrate.py` | раннер миграций, таблица `schema_migrations`, `python -m src.db.migrate` / `make migrate` |
| `src/db/migrations/0001_initial_schema.sql` | схема целиком |
| `src/db/config.py` | `DATABASE_URL` → `Settings`, `S3_*` → `StorageSettings` |
| `src/db/errors.py` | `DbError`, `ConfigError`, `PushError`, `StorageError` |
| `src/db/models.py` | `InspectionRow` |

Расчёта оценки в блоке нет и быть не может: `push_inspection` берёт `Score` из
`domain.score()` как есть и кладёт в `inspections.pct`/`grade`/`counts`/`by_zone`
без единой операции над числами.

# Предметная область

## Чек-лист

`data/checklist.csv` — 136 строк. Одна строка = один проверяемый пункт.

| Колонка | Что в ней |
|---|---|
| `id` | Код пункта: `CLN05`, `PRD09`, `INF10`. Код — единственный способ ссылаться на пункт |
| `kind` | `violation` — обычный пункт; `aggregate` и `info` — служебные, аудитору не предлагать |
| `process_ru` / `process_en` | Процесс: Чистота, Работа с продуктом, Персонал и т. д. |
| `question_ru` / `question_en` | Формулировка пункта |
| `levels` | Какие классы допустимы для этого пункта: `D1;D2`, `D2`, `D1;D2;D3` |
| `zones` | В каких зонах пункт применим |
| `days` | Срок устранения в днях |

**Никогда не связывать сущности по формулировке — только по `id`.** Формулировки переводятся и правятся, коды нет.

## Классы критичности

D1, D2, D3 — критерии управляющей компании, а не общая шкала. Что именно делает пункт D1, а что D2, записано в `data/criteria.md` по каждому пункту отдельно. Модель не имеет права выводить класс из «серьёзности на глаз» — только из критериев.

- **D1** — отклонение, требующее исправления. Вычет 0,5 п.п.
- **D2** — существенное нарушение. Вычет 2 п.п.
- **D3** — критическое. Сжигает долю зоны целиком.
- **D0** — не класс нарушения, а приём: см. «Информационные записи» ниже.

## Зоны

`data/zones.csv` — 10 физических зон, каждая весит 10 %.

```
facade        Фасад / прилегающая территория
dining        Зал ресторана / касса
dry_storage   Сухой склад
freezer       Морозильная камера
fridge        Холодильная камера
hot_kitchen   Горячий цех
cold_kitchen  Холодный цех
dough         Тестомесильный цех
dishwashing   Мойка / моповая
staff         Зона для персонала и курьерская зона
```

Зона — это место, а не смысл. Грязный стол в холодном цехе и грязный запайщик на кассе — разные зоны, значит разные нарушения, даже если пункт чек-листа один и тот же.

## Уникальность нарушения

**Нарушение уникально по паре «пункт + зона».**

Несколько однотипных объектов в одной зоне — одно нарушение с несколькими фотографиями и одним вычетом. Тот же пункт в другой зоне — отдельное нарушение с отдельным вычетом.

Это не формальность. В альтернативной, взвешенной модели расчёта вопрос засчитывается один раз независимо от того, сколько зон он затронул, — и несколько нарушений там стоят столько же, сколько одно. Проверено на живых данных: снятие одного из двух `CLN06` меняло результат с 97,5 % на 97,0 % в плоской модели и не меняло ничего во взвешенной.

## Расчёт оценки

`data/scoring.json`. Плоская модель:

- старт — 100 %;
- каждый D1 — минус 0,5 п.п.;
- каждый D2 — минус 2 п.п.;
- D3 сжигает всю долю своей зоны (10 %), и остальные нарушения внутри этой зоны уже не вычитаются — зона потеряна.

Буквы проверяются строго по порядку, первое совпадение выигрывает:

| Буква | Условие |
|---|---|
| D | хотя бы один D3 |
| C | два и более D2 |
| C | меньше 90 % |
| A | 95 % и выше и ни одного D2 |
| B | 90 % и выше и не больше одного D2 |
| C | всё остальное |

Все цифры лежат в `scoring.json` и меняются там. **В коде их не дублировать.**

## Сроки

Срок устранения берётся из колонки `days` чек-листа. В `scoring.json` заданы потолки по классам: D1 — 14 дней, D2 — 10, D3 — немедленно. Срок плана действий в письме — дата отчёта плюс 10 дней.

## Информационные записи

Замеры температур, настройки печи, фотографии продукта — это не нарушения, но в отчёте они нужны: партнёру для сверки, нам для истории.

Механика простая и уже работает: такие записи заводятся с уровнем `D0`. Этого уровня нет в `scoring.json`, а вычет берётся как `penalty.get(level, 0)` — значит, ноль. Запись принимает фотографии и зону, попадает в приложение отчёта и на оценку не влияет.

Пункты для них: `INF09` настройки печи, `INF10` температуры холодильного и морозильного оборудования, `INF11` фото продукта.

**Хранить информационные записи в одном месте — среди `findings` с уровнем `D0`.** В движке есть ещё отдельный блок `info` (команда `audit.py info`) — им не пользоваться. Он не показывается ни в `list`, ни в `score`, и дубль обнаруживается только в готовом PDF у партнёра. Ровно это и произошло на Белград-1.

## Источник записи

У каждой записи хранится, откуда она взялась (решение D044): `comment` — со слов аудитора, `photo` — распознана моделью по кадру. За формулировку, сказанную аудитором, отвечает аудитор; за догадку по картинке не отвечает никто, поэтому при предвычитке отчёта распознанные записи помечены — их перечитывают в первую очередь.

Источник лежит в самой проверке (`domain.sources` в файле состояния), а не рядом с ней: он уезжает в базу вместе с проверкой и остаётся ответом на вопрос «чья это была формулировка» через год. Пусто — источник не записан; так выглядят проверки, заведённые до D044, и выдавать их за слова аудитора нельзя.

**В отчёт партнёру источник не попадает.** Это внутренняя кухня: в поле `comment`, которое печатается в отчёте, его нет.

## Порядок обхода

`data/route.csv` — в каком порядке аудитор идёт по точке. Файл необязательный; без него зоны и пункты остаются в том порядке, в котором лежат в методике.

```csv
entity,code,order
zone,facade,10
zone,dining,20
item,CLN05,10
```

| Колонка | Что в ней |
|---|---|
| `entity` | `zone` — зона, `item` — пункт чек-листа. Строка, начинающаяся с `#`, — пометка человека, она пропускается |
| `code` | Код зоны или пункта. Кодом, никогда формулировкой |
| `order` | Целое число. Шаг 10 оставлен намеренно: вставить зону между соседними можно, не перенумеровывая файл |

Что в маршруте не названо, идёт следом за названным, сохраняя порядок методики. Код, которого в методике нет, — отказ: опечатка иначе просто ничего не переставит, и заметить это можно было бы только на обходе.

**Почему отдельным файлом, а не колонкой в `checklist.csv`.** Причина была в том, что `engine/manage.py` перезаписывал и чек-лист, и зоны фиксированным списком колонок: любая правка методики через него стирала лишнюю колонку молча, вместе со всем маршрутом. **С задачей T109 это уже не так** — чужие колонки сохраняются, — но файл остаётся отдельным по другой причине, которая никуда не делась: маршрут обхода описывает и зоны, и пункты внутри них, то есть не помещается в колонку ни того, ни другого файла.

## Версионирование чек-листа

Чек-лист версионируется целиком, и версия хранится в каждой проверке: у партнёров со временем появятся свои наборы, а отчёт годичной давности обязан сходиться и через год.

**Идентификатор составной** (решение D050): `имя-дата-отпечаток`, например `imf-2026-09-01-3f5a91b2c7d0`.

| Часть | Откуда | Зачем |
|---|---|---|
| имя набора | `data/checklist_version.txt` | человеку: по нему набор опознаётся без базы и без кода |
| дата публикации | оттуда же, в конце строки | человеку: «железно новая версия с новой датой» на любую правку |
| отпечаток данных | sha256 по файлам методики, 12 знаков | машине: не даёт выпустить изменённую методику под прежним именем, если дату поднять забыли |

Файл версии — одна строка «имя набора плюс дата»: `imf 2026-09-01`, `imf-2026-09-01`. Пустые строки и строки с `#` пропускаются. Файла нет — набор никто не издавал, и версия остаётся одним отпечатком: `local-3f5a91b2c7d0`. Файл есть, но не разбирается (нет даты, даты нет в календаре, нет имени) — отказ на старте, а не молчаливый откат на `local-…`.

В отпечаток входит вся методика: чек-лист, зоны, ставки, критерии и маршрут обхода. Правка любого из этих файлов — новая версия.
